# مخطط مرجعي — هيكلية قسم "المصاريف والمستهلكات" (Blueprint قابل لإعادة الاستخدام)

> **الغرض من هالملف:** توثيق كل الأنماط المعمارية والتصميمية يلي بُني عليها قسم المستهلكات والمصاريف بالكامل، حتى تصير مرجع جاهز عند بناء أي قسم تاني بالنظام (مبيعات، مشتريات منتجات، رواتب...) — نفس الهيكل العام، مع مراعاة خصوصية كل قسم.

---

## ١. نظام الألوان (Color System)

قاعدة ثابتة تنطبق على **أي جدول بيانات** بالنظام (رؤوس أعمدة + خلايا البيانات مع بعض):

| اللون | الكود | المعنى | أمثلة |
|---|---|---|---|
| 🔵 أزرق | `#1e3a8a` | **المعرّف/الرقم** (Identifier) | رقم الفاتورة، رقم الأمر، رقم التحويل، اسم المادة (لو ما في رقم مستند) |
| 🟢 أخضر | `#16a34a` | **المصدر** (Source) | المورد، المستودع المصدر، حساب الدفع (مصدر المال) |
| 🔴 أحمر | `#dc2626` | **الهدف/الوجهة** (Destination) | المستودع الهدف، الجهة المستلمة، حساب المصروف (وجهة المال) |
| 🟡 أصفر | `#ca8a04` | **الكمية/العدد** (Quantity) | عدد المواد، عدد البنود |
| ⚫ أسود/افتراضي | — | **القيمة المالية** (Value) | الإجمالي، التكلفة — **بدون لون خاص عمداً**، حتى يبرز عن باقي الأعمدة الملوّنة |

**قاعدة تطبيق مهمة:** لو عمود عنده لون منطقي أذكى من القاعدة العامة (متل "الرصيد" بكتالوج المستهلكات: أحمر=نفد، برتقالي=منخفض، أخضر=جيد — Traffic Light Pattern حسب حد التنبيه)، **يُبقى كما هو** ولا يُستبدل بلون القاعدة العامة الجامد. القاعدة للاسترشاد، مش لتفويت منطق أذكى موجود أصلاً.

## ٢. مكوّنات UI/UX الموحّدة

### أ) شريط التبويبات الموحّد (Tab Bar)
كل صفحات القسم (حتى المشتركة مع أقسام تانية زي `warehouse.php`/`movements.php`) بتعرض **نفس شريط التبويبات بالضبط** (نفس الأسماء، الألوان، الترتيب) — بس بروابط نسبية تتأقلم حسب موقع كل ملف الفعلي. الصفحة المشتركة (dual-purpose) بتعرض الشريط **شرطياً** بس لما السياق يطابق القسم (مثال: `warehouse.php` بيعرض شريط المستهلكات بس لما `?type=consumables`).

### ب) Breadcrumb مشترك
مكوّن واحد (`includes/breadcrumb.php` → `renderBreadcrumb()`) بيُستدعى بكل صفحة "قسم واحد ثابت"، وبيبني تلقائياً من جدول `modules` (`$menu`/`$currentModule` الجاهزين من `sidebar.php`) — **بدون** تكرار HTML يدوي بكل صفحة. **استثناء:** الصفحات مزدوجة الغرض (`warehouse.php`, `movements.php`) — عندها breadcrumb يدوي مخصص، لأنه القسم نفسه بيتغيّر ديناميكياً بنفس الصفحة.

### ج) الجداول: كلاس موحّد + فرز بالنقر
- كلاس `mtbl` (مش Bootstrap العام `table table-hover`) لكل جداول القوائم الرئيسية.
- **فرز عند النقر على أي رأس عمود** (ما عدا عمود "إجراءات" — `data-no-sort`): دالة JS عامة واحدة (`makeSortable()`/`sortTableByColumn()`) بتتكرر بكل ملف، بتتعرّف تلقائياً على نوع البيانات (**تاريخ ISO أولاً** `YYYY-MM-DD` → مقارنة زمنية حقيقية، بعدين رقم صرف كامل المطابقة، وأخيراً نص عربي عادي) — **تحذير:** لا تستخدم `parseFloat()` مباشرة على تاريخ، بيتوقف عند أول شرطة ويرجّع رقم غلط.

### د) المودالات
- حجم `modal-lg`/`modal-xl` دايماً للنماذج الحقيقية (إنشاء/تعديل مستند) — مودال بلا كلاس حجم = ضيق جداً وحقول متكدّسة.
- كل حقل بعنوان (`field-lbl`) ثابت فوقه، مش placeholder بيختفي.
- الحقول المرتبطة ببعضها (تاريخ/عملة/سعر صرف/مبلغ) بأعمدة متساوية العرض (`col-md-3` لكل وحد)، مش توزيع عشوائي.

### هـ) إدراج بنود المستند (Line Items) — نفس التجربة بكل مكان
- سطر جديد يظهر **فوق** (جنب زر "إضافة")، مش بالأسفل.
- **تظليل أخضر مؤقت** (`newRowHighlight`, ٩٠٠ ميلي ثانية) على السطر الجديد فور ظهوره.
- **تركيز تلقائي** على حقل اختيار المادة.
- بارامتر `isNew` (true/false) بكل دالة بناء سطر — `true` عند الإضافة الفعلية (فوق+تظليل+تركيز)، `false` عند استرجاع أسطر موجودة بوضع التعديل (أسفل، بالترتيب الأصلي، بلا تأثيرات).
- الحذف بمرجع الكائن نفسه (`lineData`)، مش بالـ`index` — يمنع بق "انزياح index بعد حذف سطر وسطي".

### و) القوائم المنسدلة الديناميكية — لا قوائم ثابتة بالكود أبداً
أي تصنيف/وحدة/جهة (فئات، وحدات قياس، عبوات، جهات مستلمة، عملات) لازم يكون **جدول حقيقي بقاعدة البيانات**، مش `enum` أو مصفوفة PHP ثابتة. كل قائمة منسدلة معها **زر "+" يفتح مودال إضافة سريع** بنفس الصفحة، بلون مميز (بنفسجي للفئات، سماوي للوحدات...).

## ٣. نموذج البيانات (Data Model Pattern)

### أ) رأس + بنود (Header + Items)
كل مستند (فاتورة شراء، أمر صرف، مناقلة) = **جدولين**: `{document}_ret` (رأس: رقم، تاريخ، حالة، ملاحظات) + `{document}_items_ret` (بنود: مادة، كمية، سعر). أرقام المستندات مولّدة تلقائياً (`genXxxNo()`) بصيغة `PREFIX-YYYY-NNNN`.

### ب) الوحدات والعبوات (Unit/Packaging Conversion)
- عمود `quantity` بجدول البنود **دايماً بوحدة المخزون الأساسية** — بغض النظر شو الوحدة يلي المستخدم اختارها فعلياً.
- عمودين إضافيين `packaging_id` + `packaging_qty` (nullable) — **للعرض والتدقيق بس**: شو العبوة المُختارة، وشو الكمية الأصلية كما أُدخلت بوحدتها.
- معامل التحويل (`qty_per_package`) **يُقرأ من قاعدة البيانات مباشرة عند الحفظ**، مش من قيمة جاية من المتصفح — تفادياً للتلاعب.
- عند التعديل: الكمية المعروضة بالواجهة **تُعاد بناؤها بوحدة العبوة الأصلية** (`packaging_qty` لو موجودة، وإلا `quantity`)، مش تُعرض دايماً بوحدة المخزون.

### ج) العملة (Currency)
- **`currency_id` (FK رقمي لجدول `currencies`) دايماً — لا `currency` (نص) أبداً** بأي جدول قيود محاسبية جديد.
- **`original_amount`** (بعملة المستند الأصلية) + **`base_amount`**/`debit`/`credit` (بعملة الفرع/التقارير) — عمودين منفصلين دايماً، **مش تحويل لحظي واحد يُحسب من سعر صرف** (مبدأ IAS 21 — ثبات تاريخي، القيد المُرحّل ما بيتغيّر لو تصحّح سعر عملة لاحقاً).
- عملة الفرع تُقرأ عبر `branches.base_currency_id` (FK رقمي موثوق) **لا `branches.base_currency`** (نص قديم، لقيناه فيه بيانات غلط أكتر من مرة).

### د) شجرة الحسابات — مصدر واحد للحقيقة
حسابات الدفع/الصندوق/البنك تُجلب من **`invoice_account_settings`** (الربط المحاسبي المضبوط فعلياً)، **لا تخمين بنمط كود الحساب** (`code LIKE '111%'`) — التخمين هش وبينكسر أول ما حدا يستخدم ترقيم مختلف.

## ٤. دورة حياة المستند: مسودة → تأكيد → إلغاء/إرجاع

هاد **العمود الفقري** لكل قسم بالنظام، وأي قسم جديد لازم يتبعه بدون استثناء:

```
   إنشاء          تأكيد                    إلغاء                    إرجاع (اختياري)
  ┌──────┐      ┌──────────┐            ┌────────────┐          ┌──────────────┐
  │ Draft │ ───▶ │ Confirmed│ ─────────▶ │  Cancelled  │          │ (جزئي/كامل،   │
  │       │      │          │            │             │          │ مستند مستقل)  │
  └──────┘      └──────────┘            └────────────┘          └──────────────┘
  لا أثر فعلي    - رصيد فعلي يتغيّر        - قيد عكسي جديد          - قيد مستقل جديد
  على المخزون    - قيد GL يُنشأ            (الأصلي يضل موجود!)      - كمية جزئية مسموحة
  أو الحسابات    - رصيد شجرة الحسابات      - الرصيد يرجع
                   يتحدّث فوراً              (postAccountBalance)
```

### القاعدة الذهبية: **لا تحذف حدث مالي صار فعلياً أبداً**
- **الإلغاء = قيد عكسي جديد + تحديث حالة**، مش `DELETE FROM journal_entries`. القيد الأصلي يضل موجود للأبد (سجل تاريخي كامل).
- حتى الجداول البسيطة (زي `expenses_ret`) لازم يكون فيها عمود `status` (`active`/`cancelled`) — "الحذف" بالواجهة = تحديث حالة، مش `DELETE FROM` فعلي.
- استثناء وحيد مقبول: مسودة **قبل** التأكيد — ما أثّرت على شي فعلي بعد، فحذفها/إعادة بناء بنودها من الصفر آمن ١٠٠٪ (نفس منطق التعديل: امسح البنود القديمة وأعد إنشاءها).

### الإرجاع (Return) — مفهوم منفصل تماماً عن الإلغاء
- **الإلغاء** = "الأمر كله غلط من الأساس" — كمية كاملة، فوري، بيعكس القيد الأصلي بالكامل.
- **الإرجاع** = "الأمر كان صحيح فعلاً، بس لاحقاً رجعت كمية (جزئية أو كاملة)" — قيد **مستقل جديد** (مش عكس الأصلي)، بسعر التكلفة **الأصلي وقت العملية** (مش سعر اليوم)، مع تتبّع تراكمي (`returned_qty`) يمنع تجاوز الكمية الأصلية.

### الترحيل الفعلي لرصيد شجرة الحسابات (لو النظام يعتمد رصيد مخزّن)
لو `account_charts` عندها أعمدة `balance`/`base_balance` مخزّنة (بعكس بعض الأنظمة العالمية يلي بتحسبها لحظياً من دفتر اليومية)، **لازم دالة موحّدة واحدة** (`postAccountBalance()`) تُستدعى بعد **كل** إدراج بجدول `journal_entry_items` — بتفحص طبيعة الحساب (مدين/دائن) وتحدّث الرصيد فوراً. نسيان هالخطوة = قيود صحيحة بدفتر اليومية، بس شجرة الحسابات تضل صفر للأبد (بق حرج صار بالضبط بهالنظام).

### المناقلة/التحويل بين مستودعات — استثناء بلا قيد محاسبي
عملية **صفر تغيير على القيمة الإجمالية** (نقص من مستودع + زيادة بمستودع، نفس الشركة) — **بلا أي قيد GL** (بعكس الشراء/الصرف). بس **نفس آلية مسودة→تأكيد** تنطبق: الحفظ الأول مسودة بلا أثر فعلي، والتأكيد هو يلي بينفّذ الخصم/الإضافة الفعليين + الحركات + **إعادة فحص الرصيد من جديد وقت التأكيد** (ممكن يكون تغيّر منذ حفظ المسودة).

## ٥. الصلاحيات (Permissions)

- كل صفحة عندها مفتاح صلاحية خاص فيها بجدول `modules` (`can()`/`requirePermission()`) — **لا تعتمد على مفتاح صفحة تانية** حتى لو الوظيفة متشابهة (بق تكرر أكتر من مرة: صفحات جديدة كانت بتستخدم مفتاح صفحة الكتالوج بالغلط).
- الصفحات المشتركة (`warehouse.php`) لازم يكون **مفتاح الصلاحية ديناميكي حسب السياق** (`?type=consumables` → مفتاح مختلف عن `?type=products`) — **وحدد السياق قبل فحص الصلاحية**، مش بعده.
- أزرار مؤجّلة (ميزة لسا مش مبنية، زي "تسجيل دفعة") — تظهر لكل مستخدم، بس **تنعطّل** (`disabled`) لو ما عنده الصلاحية، بدل ما تختفي بالكامل — شفافية أكتر.

## ٦. تنظيم الملفات والمجلدات

- كل قسم منطقي = **مجلد مخصص واحد** (`modules/{section_name}/`) يجمع كل ملفاته المخصصة فيه فقط.
- **البنية التحتية المشتركة** (مخزون، مستودعات، حركات) **تبقى بمجلدها العام المحايد** (`inventory/`)، ولا تُنقل لمجلد قسم واحد — حتى لو قسمين بيستخدموها، لأنها مش "ملك" لقسم واحد.
- عند نقل ملف لمجلد جديد: **كل الروابط النسبية جواه لازم تُراجَع يدوياً** (مسافة `../` إضافية أو أقل حسب الفرق بالعمق) — **أكتر خطأ تكرر بهالمشروع** كان نسيان هالمراجعة بعد كل نقل.

## ٧. أخطاء متكرّرة يستاهل الانتباه لها مسبقاً (Checklist)

بناءً على كل الأخطاء الفعلية يلي انصلحت بهالقسم — راجعها **قبل** ما تبني قسم جديد، مش بعده:

- [ ] **عمود نصي مجمّد قديم** (`ci.unit`, `ci.category`) بدل `JOIN` حقيقي عبر `_id` — يصير أول ما تُبنى جداول ديناميكية لاحقاً وتُنسى الاستعلامات القديمة.
- [ ] **رمز عملة/كود ثابت بالكود** (`"$"`, `['USD'=>'$','SYP'=>...]`) بدل قراءة ديناميكية من `currencies`.
- [ ] **مفتاح صلاحية مكرر من صفحة تانية** بدل مفتاح خاص بالصفحة نفسها.
- [ ] **دالة JS ميتة بعد إعادة تصميم** (`onclick="oldFunction()"` بدون تعريفها — بترمي خطأ صامت بالكونسول وتعطّل التفاعل بصمت).
- [ ] **حذف مباشر لقيد محاسبي** بدل قيد عكسي + تحديث حالة.
- [ ] **`parseFloat()` مباشر على تاريخ** بمقارنات JS (بيتوقف عند أول شرطة).
- [ ] **رابط نسبي ما تحدّث بعد نقل ملف** لمجلد جديد.
- [ ] **تحقق صلاحية قبل تحديد السياق** بصفحة مشتركة (لازم العكس).
- [ ] **استعلام يفترض عمود غير موجود** (`SELECT currency FROM account_charts` بدل `currency_id`) — يطيح الصفحة بالكامل بخطأ SQL.
- [ ] **enum بقاعدة البيانات ما يشمل قيمة جديدة** (`reference_type`/`movement_type`) لما تُبنى ميزة جديدة (إرجاع، مناقلة) — لازم `ALTER TABLE ... MODIFY ... ENUM(...)` قبل الاستخدام.

## ٨. خلاصة: كيف تطبّق هالمخطط على قسم جديد (مثال: المبيعات)

1. حدّد جدولي رأس+بنود (`sales_invoices`, `sales_invoice_items`) — تأكد إنه `quantity` بوحدة المخزون الأساسية، مع `currency_id` (مش `currency`).
2. ابنِ دورة حياة **مسودة→تأكيد→إلغاء (عكسي)**، مع دالة `postAccountBalance()` مشتركة (أو أعد استخدام نفس الدالة لو بنفس الفرع).
3. لو فيه سيناريو "إرجاع بعد التأكيد" (مرتجع مبيعات) — ابنيه كمستند مستقل، مش تعديل على الإلغاء.
4. وحّد الألوان (أزرق=رقم الفاتورة، أخضر=العميل كمصدر الإيراد لو منطقي، أحمر=لو في وجهة مقابلة، أصفر=الكمية).
5. استخدم نفس مكوّنات الواجهة (breadcrumb مشترك، تبويبات موحّدة لو القسم متعدد الصفحات، جداول قابلة للفرز، مودالات واسعة).
6. راجع القائمة (القسم ٧) **قبل** التسليم، مش بعد ما يبلغ المستخدم عن بق.
