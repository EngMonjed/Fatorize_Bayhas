# مخطط بناء "صفحة تعديل فاتورة" — بالاستناد على `purchases/invoice_edit.php`

> ارفع هالملف بمحادثة "تعديل فاتورة البيع" (جنب `sales_invoice_blueprint.md` يلي
> جهزناه قبل لصفحة الإنشاء)، مع `master-construction-blueprint.md`. هاد الملف
> يوثّق **بالضبط** شو اتبنى وشو اتقرر وقت بناء `purchases/invoice_edit.php` —
> بما فيها باگ حقيقي واحد انصلح أثناء البناء يستاهل انتباه خاص وإحنا نبني
> النسخة التانية.

## ١. القرارات الجاهزة للنسخ الحرفي

هاي قرارات عامة لأي صفحة "تعديل مستند" بالنظام (مو خاصة بالمشتريات):

| القرار | التفصيل |
|---|---|
| **الأساس = نسخة مطابقة لصفحة الإنشاء** | صفحة التعديل مبنية بنسخ صفحة `_new.php` بالكامل (نفس التصميم/الهيكلية/دوال الحساب)، مو ملف مستقل من الصفر — يضمن اتساق تام بالسلوك والمظهر. |
| **حماية مزدوجة: تحميل + حفظ** | التحقق من `status === 'draft'` مرتين: مرة وقت GET (فتح الصفحة)، ومرة **تانية صريحة** وقت POST (الحفظ الفعلي) — لأنه ممكن تنأكد الفاتورة بتبويب تاني بالفترة بينهم. لا تكتفي بفحص واحد وقت التحميل بس. |
| **تحويل تلقائي بدل صفحة خطأ** | لو فاتورة مؤكدة وحدا فتح رابط التعديل مباشرة → `header('Location: index.php?view_id=' . $id); exit;` — يتطلب دعم إضافي بـ`index.php` (قسم ٦ تحت). |
| **رقم الفاتورة ثابت تماماً** | ما بيتقرأ من الواجهة ولا بيتولّد من جديد — يُقرأ من السجل الأصلي بس، معروض بحقل `readonly`. |
| **الحفظ = UPDATE + حذف/إعادة إدراج البنود** | مو محاولة مطابقة/تحديث بند-ببند (تعقيد غير مبرَّر لجدول متغيّر البنية). حذف كل بنود الفاتورة القديمة ثم إدراج الجديدة بالكامل — **آمن فقط لأنها مسودة** (صفر أثر مخزون/محاسبة بعد). |
| **حماية دفاعية وقت الحفظ** | `status` يُعاد فحصه داخل معالج الحفظ نفسه (مو بس GET) قبل تنفيذ `UPDATE`. |
| **بلا `sessionStorage`** | زر "تحديث" (تحديث قائمة المنتجات) يرجع دايماً للنسخة المحفوظة بقاعدة البيانات — قرار مبسَّط متعمَّد (راجع القسم ٤ للتفصيل الكامل ليش هالقرار مو بديهي كما يبدو). |
| **حقول "هوية المستند" مقفلة** | العميل/المورد، المستودع، تاريخ الفاتورة، تاريخ الاستحقاق — `disabled` بالواجهة (أيقونة قفل + تلميح)، **و** تجاهل صريح بجانب السيرفر لأي قيمة توصل لهالحقول بالـ`POST` (اعتماد القيم الأصلية المحفوظة حصراً، دفاعاً ضد تلاعب `devtools`). راجع القسم ٥ لسبب هالقرار ولوين ينطبق. |
| **مودال "إضافة سريعة" (مورد/عميل) = نفس حقول الصفحة الإدارية الكاملة** | لا نسخة مصغّرة بحقول ناقصة — نفس كل الحقول + **نفس منطق إنشاء الحسابات المحاسبية التلقائي** (راجع القسم ٧، فجوة حقيقية انصلحت). |

## ٢. جدول المطابقة: تعديل مشتريات ↔ تعديل مبيعات

| المشتريات | المبيعات | ملاحظة |
|---|---|---|
| `?id=` على `purchases_ret.id` | `?id=` على `sales_invoices_ret.id` | — |
| `requirePermission('purchases.invoices','edit')` | `requirePermission('sales.invoices','edit')` | تحقق مفتاح الصلاحية الفعلي بجدول `modules`. |
| `purchase_items_ret` (حذف/إعادة إدراج) | `sales_invoice_items_ret` | تحقق الأعمدة الفعلية (`DESCRIBE`) — **لا تفترض** نفس أسماء أعمدة المشتريات. |
| المورد (`supplier_id`) مقفل | العميل (`customer_id`) مقفل؟ | **قرار مفتوح — راجع القسم ٥.** |
| `add_supplier` (مودال سريع) | `add_customer` (مودال سريع)؟ | لو المبيعات عندها مودال مشابه، ينطبق نفس إصلاح القسم ٧ (حسابات محاسبية تلقائية) — تحقق أولاً هل `customers_ret` أصلاً عندها `account_id`/`prepaid_account_id` بنفس نمط `product_suppliers_ret`. |
| إعادة بناء `default_price` من `unit_price_base_currency`/`discount_percentage` | نفس المعادلة، لو نفس بنية الأعمدة موجودة بجدول المبيعات | `defaultPr = netPrice / (1 - discPct/100)` — تحقق العمود `discount_percentage` موجود فعلاً بـ`sales_invoice_items_ret` قبل الاعتماد عليه. |
| `packet_qty` من `product_sizes` | **مرتبط بالقرار المفتوح من `sales_invoice_blueprint.md` قسم ٤-١** | لو حسمتوا هناك إنه المبيعات بالقطعة المفردة (مو بالباكيت)، منطق إعادة بناء `packet_qty`/`piece_count` هون كله يختلف جوهرياً — راجع قبل البدء. |

## ٣. تسلسل البناء المقترح

1. **تأكيد القرارات المفتوحة أول شي** (قسم ٥ و٧ تحت) — مو بعد البناء.
2. انسخ `sales_invoice_new.php` (بعد ما يخلص) كأساس كامل لـ`sales_invoice_edit.php`.
3. هيدر PHP: تحميل الفاتورة بـ`?id=`، الحماية المزدوجة، التحويل التلقائي لمودال التفاصيل.
4. إعادة بناء نسب الخصم/الضريبة من القيم المحفوظة (نفس معادلة المشتريات، لو نفس بنية الأعمدة).
5. إعادة بناء `EXISTING_LINES` بجانب PHP من بنود الفاتورة الموجودة (تجميع بمفتاح: عميل/منتج + لون + سعر افتراضي مُعاد بناؤه).
6. قفل الحقول المقرَّرة بالقسم ٥ (واجهة + حماية سيرفر).
7. تحويل معالج الحفظ من `INSERT` لـ`UPDATE` + حذف/إعادة إدراج البنود.
8. توسيع مودال "عميل جديد" (لو موجود) بنفس منطق القسم ٧.
9. **اختبار حقيقي إلزامي قبل التسليم:** فتح فاتورة مسودة حقيقية، حذف سطر والتأكد إنه ينحذف فعلياً من الجدول (راجع القسم ٦ — باگ حقيقي وقع هون بالضبط).

## ٤. لماذا قرار حذف `sessionStorage` مو بديهي كما يبدو

بالوهلة الأولى بيبدو القرار بسيط ("ما في داعي حماية إضافية، البيانات محفوظة أصلاً"). بس اكتشفنا وقت البناء إنه فيه **غرضين مختلفين** بيستخدموا نفس الآلية:

1. **استرجاع بعد حادث** (تصفح انسكر بالغلط) — فعلاً مش لازم، البيانات المحفوظة كافية.
2. **زر "تحديث" (تحديث قائمة المنتجات)** — بيعمل `location.reload()` فعلي، وكان يعتمد على `sessionStorage` حتى **ما تضيع تعديلات غير محفوظة** وقت الضغط.

القرار النهائي كان: **شيلها بالكامل مع ذلك** — زر "تحديث" برجّع دايماً للنسخة المحفوظة بقاعدة البيانات، وأي تعديل غير محفوظ وقت الضغط يضيع عمداً (تبسيطاً). لو حابين إعادة نقاش هالقرار بالمبيعات، خدوا هالتفصيل بعين الاعتبار — القرار مو بديهي متل ما يبدو ظاهرياً.

## ٥. قرار مفتوح — قفل حقول "هوية المستند": ينطبق نفسه على المبيعات؟

بالمشتريات قررنا قفل: **المورد، المستودع، تاريخ الفاتورة، تاريخ الاستحقاق**. المنطق: هاي "بيانات هوية" المستند الأساسية، ما يفترض تتغيّر بعد الإنشاء (تغيير المورد بمنتصف تعديل فاتورة موجودة تعقيد/التباس غير مبرَّر).

**للمبيعات، اسألوا صراحة بمحادثة البناء:**
- هل نفس المنطق ينطبق (العميل/المستودع/التواريخ مقفلين بالتعديل)؟
- ولا فيه سيناريو مبيعات مشروع لتغيير العميل بمنتصف تعديل مسودة (مثلاً: كتب فاتورة لعميل غلط بالغلط، وبدو يصححها بدل ما يمسحها ويعمل وحدة جديدة)؟

**لا تفترضوا نفس القرار تلقائياً** — قرار عملي يعتمد سير عمل المبيعات الفعلي، مو نسخ آلي من المشتريات.

## ٦. باگ حقيقي وقع أثناء البناء — انتبهوا له من الأول بالمبيعات

### حذف سطر من الجدول: يشتغل حسابياً بس الصف البصري يضل عالق

**السبب:** `removeLine()` كانت تعيد بناء الـ`row_id` من نمط ثابت (`'lgrp_' + gk.replace(...)`) — صحيح **بس** للأسطر المضافة عبر `addLine()` وقت التصفح. أسطر الفاتورة **المحمّلة أصلاً من قاعدة البيانات** (عبر `loadExistingLines()`) عندها `row_id` بصيغة مختلفة تماماً (مولَّد من PHP، `uniqid()`-based). النتيجة: الحذف كان يشتغل صح على مستوى البيانات (`lines` array، والمجاميع تتحدّث صح)، بس `document.getElementById(rowId)` ما بيلاقي عنصر بهيك ID، فالصف البصري يضل عالق بالجدول.

**الإصلاح المطبَّق (طبّقوه من أول بناء بالمبيعات، لا تنتظروا نفس الباگ يتكرر):**
```js
function removeLine(gk) {
    const line = lines.find(l => l.grp_key === gk);   // ⚠ خذ row_id الحقيقي من كائن الخط نفسه قبل الحذف
    lines = lines.filter(l => l.grp_key !== gk);
    if (line) {
        const row = document.getElementById(line.row_id);  // مو إعادة بناء من نمط ثابت
        if (row) row.remove();
    }
    if (!lines.length) document.getElementById('emptyRow').style.display = '';
    calcTotals();
    updateLinesCount();
}
```
هاد النمط الآمن (الاعتماد على `row_id` المخزَّن، لا إعادة بنائه) يستاهل يتطبّق بأي مكان مشابه — بما فيه احتمالياً `sales_invoice_new.php` نفسها لو رح تستخدم نفس نمط `'lgrp_'+gk` بمكان واحد بس لكل مصادر الأسطر (مش باگ فعلي هناك حالياً بس هشاشة نظرية لو تغيّر شي لاحقاً).

## ٧. فجوة محاسبية حقيقية انصلحت — تحققوا من مكافئها بالمبيعات

مودال "مورد جديد" السريع (زر `+` جنب اختيار المورد بصفحتي الشراء) كان بس بيعمل `INSERT` بسيط (اسم، هاتف، جهة اتصال، نوع) — **بدون** إنشاء حسابي "ذمة المورد" و"الدفعة المقدمة" تلقائياً، عكس صفحة إدارة الموردين (`suppliers.php`) يلي عندها هالمنطق **إجباري** لكل مورد جديد (حساب فرعي مخصص تحت الحسابين الأب المضبوطين بإعدادات الربط المحاسبي).

**النتيجة قبل الإصلاح:** أي مورد مضاف من مودال الفاتورة السريع كان يطلع **بدون أي حساب محاسبي مرتبط إطلاقاً** — فجوة حقيقية، مو مجرد نقص حقول واجهة.

**تحققوا بالمبيعات:**
- هل فيه مودال "عميل جديد" سريع بصفحة فاتورة البيع (جديدة أو تعديل)؟
- لو موجود، راجعوا معالجه بجانب السيرفر — هل بيعمل نفس الإنشاء التلقائي لحساب "ذمة العميل" (وأي حساب مكافئ)، مطابق لمنطق صفحة إدارة العملاء (`customers.php`)؟
- لو الجواب لأ، هاد نفس نمط الفجوة بالضبط — يستاهل نفس الإصلاح (نسخ منطق إنشاء الحساب التلقائي من `customers.php` حرفياً، مو إعادة اختراعه).
