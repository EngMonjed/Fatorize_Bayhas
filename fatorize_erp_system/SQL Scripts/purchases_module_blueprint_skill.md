# سكلز بناء الأقسام المعاملاتية (Transactional Modules) — مُستخلص من قسم المشتريات

> ارفع هالملف بأول رسالة بأي محادثة بناء/مراجعة لقسم معاملاتي جديد (مبيعات،
> مرتجعات مبيعات، مستهلكات...). هو خلاصة كل قرار معماري وباگ حقيقي وقعنا
> فيه وصلحناه عبر بناء قسم المشتريات الكامل (٩ ملفات: `invoice_new.php`،
> `invoice_edit.php`، `index.php`، `returns.php`، `suppliers.php`،
> `reports.php`، `orders.php` [موقوف عمداً]، `confirm_purchase_invoice.php`،
> `confirm_purchase_return.php`). **مو نظري — كل قاعدة هون طلعت من باگ فعلي
> انصلح ووثّقناه.**

## ١. جرد الصفحات (القالب المتوقَّع لأي قسم معاملاتي كامل)

| الملف | الدور | يقابله بالمبيعات |
|---|---|---|
| `invoice_new.php` | إنشاء مستند جديد (مسودة فقط، صفر أثر مخزون/محاسبة) | `sales_invoice_new.php` |
| `invoice_edit.php` | تعديل مسودة موجودة (نفس تصميم `_new` + تحميل بيانات + قفل حقول هوية) | `sales_invoice_edit.php` |
| `index.php` | قائمة + مودال تفاصيل + مودال تأكيد + طباعة | نفسه بالمبيعات |
| `returns.php` | مرتجعات (مرتبطة إجبارياً بمستند مؤكد) | `sales_returns.php` |
| `suppliers.php` / `customers.php` | إدارة الطرف التجاري (CRUD + حسابات محاسبية تلقائية) | `customers.php` |
| `reports.php` | تقارير قراءة فقط، تبويب لكل تقرير | نفسه بالمبيعات |
| `orders.php` | أوامر شراء/بيع مؤجَّلة — **نمط "موقوف عمداً" موثَّق بالأسفل** | نفس النمط لو أوامر بيع مؤجَّلة |
| `api/confirm_*.php` | ملف API منفصل، خارج `modules/`، يعمل التأثير المحاسبي/المخزوني الفعلي الوحيد | `api/confirm_sale_invoice.php` |
| `api/confirm_*_return.php` | نفس الشي بس عكس الاتجاه | `api/confirm_sale_return.php` |

**قاعدة صفرية:** أي صفحة `_new.php`/`_edit.php` **لا تلمس** المخزون ولا القيود إطلاقاً — مسودة بس. التأثير الفعلي **حصراً** بملف `api/confirm_*.php` منفصل.

## ٢. الهيكل العام لكل صفحة (Header Skeleton)

```php
<?php
session_start();
require_once __DIR__ . '/../../../config/database.php';
require_once __DIR__ . '/../../../config/auth.php';
$pdo = getConnection();
checkLogin($pdo);
requirePermission('{module_key}', '{view|edit|create|confirm}');
$currentModule = '{module_key}';
$branchName = $_SESSION['branch_name'] ?? 'الفرع';
$TS = $_SESSION['table_suffix'];
$T{X} = "{table}_{$TS}";   // كل الجداول المستخدمة بالصفحة
```

**بعد الهيدر مباشرة، بالترتيب:**
1. معالج AJAX (`if ($_SERVER['REQUEST_METHOD']==='POST' && isset($_POST['_action']))`) — `header('Content-Type: application/json')`، `switch`/`if-elseif` على `$_POST['_action']`، `echo json_encode([...]); exit;`
2. تحميل بيانات الصفحة (GET فقط، بعد ما معالج AJAX يعمل `exit`)
3. HTML

**تضمينات ثابتة بكل صفحة:**
```php
require_once __DIR__ . '/../../../includes/sidebar.php';
require_once __DIR__ . '/../../../includes/breadcrumb.php';
```
مع `<div class="sb-overlay" id="sbOverlay" onclick="sbClose()"></div>` قبلهم مباشرة.

**شريط التبويبات الثابت** (نفس الخمسة، بنفس الترتيب، بكل صفحات القسم):
```html
<ul class="nav nav-tabs mb-3" style="border-bottom:2px solid #e2e8f0">
  <li><a href="index.php">فواتير الشراء</a></li>
  <li><a href="suppliers.php">إدارة الموردين</a></li>
  <li><a href="returns.php">مرتجعات المشتريات</a></li>
  <li><a href="orders.php">أوامر الشراء / طلبات عروض الأسعار</a></li>
  <li><a href="reports.php">التقارير</a></li>
</ul>
```
التبويب النشط: `class="nav-link fw-600 active"` + `border-bottom:2px solid var(--section-color)`.

## ٣. نمط "موقوف عمداً" (Deferred Page Pattern) — من `orders.php`

لما قرار معماري يتأجّل بس الصفحة لازم تكون موجودة وتظهر بالتنقّل:
- الشكل العام (Sidebar/Breadcrumb/تبويبات) **حقيقي ١٠٠٪**، مو placeholder.
- منطقة المحتوى بس بديلة برسالة واضحة: أيقونة `bi-cone-striped` برتقالية، عنوان، فقرة توضح **شو القرارات المتّفق عليها فعلاً** (حتى لو التنفيذ مؤجَّل)، وزر رجوع.
- تعليق بالكود يوثّق **بالضبط** وين يُستبدل لاحقاً بدون لمس باقي الصفحة.

## ٤. المعمارية المالية — أهم قسم بالملف، ومصدر أكتر الأخطاء تكراراً

### ٤-١. القاعدة الذهبية: عملة الفرع = مصدر الحقيقة الوحيد

**قرار مؤسِّس (اتخذ بمحادثة `invoice_new.php` الأولى):** جدول بنود أي مستند (`purchase_items`/`sales_invoice_items`) = **عملة الفرع فقط**. عملة المستند المختارة بالهيدر (`invoice_currency_id`/`exchange_rate`) **توثيقية بس** — ما بتدخل بأي حساب لمجاميع الشاشة أو الحفظ.

**النتيجة العملية:**
- `total_amount`, `discount_amount`, `tax_amount`, `final_amount`, `final_amount_base_currency` — **كلهم بعملة الفرع، ونفس القيمة بالضبط** (`final_amount == final_amount_base_currency` دايماً).
- ما في تخزين مكرَّر لقيمة بعملة المستند على مستوى الهيدر — **أي قيمة بعملة المستند تُشتق وقت الحاجة**، ما تُخزَّن كنسخة مستقلة:
  ```php
  $finalOrig = round($finalBase * $rate, 4);  // مُشتق، لا مقروء من عمود
  ```
- **الاستثناء الوحيد المدروس:** عمود `unit_price` (المفرد، بمستوى البند) فعلاً بعملة المستند (`= net_price × exchange_rate`)، بينما `unit_price_base_currency` بعملة الفرع — **زوج أعمدة حقيقي متعمَّد**، مو نفس نمط الهيدر. لا تفترض نفس القاعدة تنطبق بشكل أعمى على كل عمود.

### ٤-٢. الباگ يلي تكرر ٥+ مرات — احفظه عن ظهر قلب

**النمط:** قيمة مخزَّنة فعلياً بعملة الفرع، بس معروضة/محسوبة بجانب رمز عملة المستند (أو العكس: قسمة/ضرب مزدوج بسعر الصرف).

**كل الأماكن يلي وقع فيها هالباگ بالضبط بهالمشروع** (خارطة طريق لأي مكان جديد رح تبنيه):
1. `saveInvoice()` — `unit_price`/`unit_price_base_currency` كانوا نفس القيمة (defaultPr بدل netPrice)
2. مودال التفاصيل (`index.php`) — جدول البنود وملخص المبالغ
3. `confirm_purchase_invoice.php` — `$unitBase` (قسمة مزدوجة أفسدت `current_cost`)، و`original_amount` بالقيد الرئيسي، و`balance_amount`
4. مودال التأكيد (`index.php`) — نفس الشيئين بالضبط
5. "ملخص المبالغ حسب العملة" (`index.php`) — `_cTotal` مقروء خام بدل تحويله
6. قالب الطباعة — نفس النمط بجدول البنود

**القاعدة الوقائية:** أي مكان جديد بيعرض/يحسب مبلغ، اسأل صراحة: **"هالقيمة مصدرها عمود بعملة الفرع، وعم تُعرض جنب أي رمز؟"** قبل ما تكتب `${sym} ${amount}`.

### ٤-٣. تجميع "الكروب" — مفتاح التجميع الصحيح

**الباگ:** التجميع بمفتاح `net_price` (الصافي بعد الخصم) — كروبين مختلفين (سعر افتراضي وخصم مختلفين) ممكن يطلع صافيهم نفس الرقم بالصدفة، فينضموا غلط.

**الصح:** التجميع بمفتاح **السعر الافتراضي المُعاد بناؤه** (قبل الخصم):
```php
$defaultPr = $discPct > 0 ? round($netPrice / (1 - $discPct / 100), 4) : $netPrice;
$key = "{$productId}_{$defaultPr}";
```
مُطبَّق بـ: مودال التفاصيل، مودال التأكيد، قالب الطباعة، `returns.php` — **كل مكان فيه تجميع بنود لازم نفس المعادلة بالضبط.**

**كمان:** ترقيم/تلوين "كروب ١/٢/٣" لازم يكون **نسبي لكل منتج لحاله** (فلترة بـ`product_id` أول)، مو عالمي عبر كل بنود المستند — وإلا نفس المنتج بكروبين ياخدوا أرقام غير متسلسلة.

### ٤-٤. الكمية — قطعة وحدة، لا مضخّمة

**الباگ الأخطر (تأثير حقيقي على المخزون):** `quantity` المخزَّنة لكل صف مقاس = `qty × packetQty` (الكمية الكاملة) بدل `qty` وحدها — أي تأكيد كان رح يضخّم المخزون بمعامل `packetQty`.

**الصح:** `quantity` لكل صف مقاس بمفرده = `qty` (عدد الباكيتات/الكروبات) **فقط**. المجموع الكلي (`piece_count = qty × packetQty`) يُستخدم لعرض/حساب الإجمالي بس، **ما يُخزَّن كـ`quantity` لكل صف**.

### ٤-٥. `packet_qty` — غير مخزَّن على جدول البنود إطلاقاً

`purchase_items`/`sales_invoice_items` **ما فيهم عمود `packet_qty`**. أي مكان محتاجه بعد الحفظ (تفاصيل، تأكيد، طباعة) لازم يشتقّه:
```js
const packetQty = group.sizes.length || 1;  // عدد المقاسات المميّزة بالكروب
```

## ٥. دورة حياة المستند (Lifecycle)

```
مسودة (draft) ──[تعديل حر]──> مسودة
   │
   └──[تأكيد، api/confirm_*.php]──> مؤكَّد (confirmed)
                                        │
                                        └──[إلغاء]──> ملغى (cancelled)
```

### ٥-١. الحفظ (`_new.php`)
`INSERT` مباشر، `status='draft'`. رقم المستند يُولَّد (`{بادئة الفرع}-{نوع}-{سنة}-{٥ أرقام}`).

### ٥-٢. التعديل (`_edit.php`)
- **حماية مزدوجة**: فحص `status==='draft'` مرتين — وقت `GET` (فتح الصفحة)، **و**مرة تانية صريحة داخل معالج الحفظ نفسه وقت `POST` (دفاعاً ضد تأكيد بتبويب تاني بالفترة بينهم).
- لو الحالة مو مسودة → **تحويل تلقائي** لمودال التفاصيل بـ`index.php` (`header('Location: index.php?view_id=' . $id)`)، مو صفحة خطأ منفصلة. يتطلب دعم `?view_id=` بـ`index.php` (فتح `viewInvoice(id)` تلقائياً من `URLSearchParams`).
- الحفظ = `UPDATE` للهيدر + **حذف كل البنود القديمة وإعادة إدراجها بالكامل** (مو مطابقة سطر-بسطر) — آمن فقط لأنها مسودة (صفر أثر مخزون/محاسبة بعد).
- رقم المستند **ثابت**، ما بيتقرأ من الواجهة ولا بيتولَّد من جديد.
- حقول "هوية المستند" (المورد/العميل، المستودع، تاريخ المستند، تاريخ الاستحقاق) — **قرار عملي يعتمد سير العمل الفعلي، مو افتراض تلقائي.** بالمشتريات قررنا قفلها (`disabled` بالواجهة + تجاهل صريح لأي قيمة توصل بالـ`POST` بجانب السيرفر، اعتماد القيم الأصلية حصراً). اسأل صراحة قبل تطبيق نفس القرار بالمبيعات.
- إعادة بناء الأسطر من البيانات المحفوظة تُبنى بجانب PHP (`EXISTING_LINES` مصفوفة JSON)، مجمَّعة بنفس مفتاح "الكروب" (قسم ٤-٣)، وممرَّرة لدالة JS تبني الصفوف — **تعيد استخدام نفس دالة بناء الصف الموجودة أصلاً بـ`_new.php`**، ما تُكرَّر.
- **`sessionStorage` لاستعادة تعديلات غير محفوظة عند "تحديث" الصفحة:** قرار عملي منفصل عن الاسترجاع بعد حادث — يستاهل نقاش صريح لكل صفحة، مش نسخ آلي.

### ٥-٣. التأكيد (`api/confirm_*.php`)
- ملف **منفصل تماماً** خارج `modules/`، بمساره الخاص (`retail1/api/`).
- فحص `status==='draft'` **إجباري** قبل أي تعديل.
- **معاملة قاعدة بيانات واحدة** (`beginTransaction`/`commit`/`rollBack`) تغلّف: تحديث المخزون + حركة المخزون (`inventory_movements`/`inventory_movement_details`) + القيد المحاسبي + تحديث حالة المستند.
- **فحص سيادي لتوفر الكمية الفعلية وقت التأكيد نفسه** (مو بس وقت الحفظ) — المخزون ممكن يتغيّر بالفترة بين إنشاء المسودة والتأكيد. احترام `branches.allow_negative_stock`.
- `original_amount` بالقيد **مُشتق** (`base × rate`)، لا مقروء من عمود مكرَّر (قسم ٤-١).
- `current_cost` بـ`warehouse_items`: **يُحدَّث** وقت زيادة المخزون (شراء)، **لا يُلمَس** وقت نقصانه (بيع أو مرتجع شراء) — قرار محاسبي صريح: التقييم ما يتغيّر بخروج بضاعة، بس بدخولها.
- حسابات الربط (`invoice_account_settings`) عبر دالة `getAcc(string $key): ?array` موحَّدة — تبحث `setting_key` بجدول الإعدادات، ترجع الحساب أو `null`. رفض صريح وواضح لو الحساب الأب غير مضبوط.
- **حساب الطرف الفردي (مورد/عميل) يُفضَّل دايماً على الحساب الأب العام:**
  ```php
  $accEntity = /* حساب المورد/العميل الخاص، لو موجود */
      ?? $getAcc('supplier_payable'); // احتياطي عام
  ```
- **لا حساب وسيط جديد لأي سيناريو تسوية** — الحسابات الموجودة أصلاً لكل طرف (ذمة + دفعة مقدمة) كافية. أي "وجهة تسوية" (نقدي/ذمة/دفعة مقدمة) = **اختيار حساب مدين/دائن مختلف بنفس القيد**، مو حساب جديد بشجرة الحسابات.
- `cancel` (إلغاء مستند مؤكَّد) = **عكس كامل** بمعاملة واحدة: إرجاع الكمية للمخزون + عكس كل أسطر القيد (`base_balance -= net` لكل سطر) + `status='cancelled'` على القيد والمستند.

## ٦. نمط "الحساب المستهدف المرتبط بنوعية العملية" (Target Account Pattern)

لما عملية مالية (دفعة، تسوية، استرداد) ممكن توجَّه لأكتر من حساب حسب اختيار المستخدم:

1. **حقلين مرتبطين ببعض بجدول القاعدة:** `{operation}_type` (ENUM بسيط: `not_paid`/`partial`/`paid_full`) + `target_account_type` (ENUM: `cash`/`supplier`/`advance`، `NULL` لو `not_paid`).
2. **الواجهة:** حقل الحساب المستهدف **مخفي** لو `not_paid`، **ظاهر وإجباري** لو `partial`/`paid_full`.
3. **لو `cash`:** حقل إضافي لاختيار حساب صندوق/بنك حقيقي، مفلتَر بعملة المستند تلقائياً.
4. **لو `supplier`/`advance` (أو مكافئها `customer`):** الحساب مُحدَّد ضمنياً (حساب الطرف نفسه)، بلا اختيار حر.
5. **بالتأكيد:** قيد واحد بس، دائن/مدين ثابت بجهة (المخزون بالمشتريات)، والجهة المقابلة تتحدد من `target_account_type`.
6. **حماية سيادية مزدوجة:** الواجهة (`disabled`/`required`) + السيرفر (رفض الحفظ لو `partial`/`paid_full` بلا `target_account_type`، أو `cash` بلا حساب فعلي).

## ٧. حسابات الطرف التجاري التلقائية (Supplier/Customer Sub-Accounts)

كل مورد/عميل جديد ياخد **حسابين فرعيين تلقائياً** وقت الإنشاء (من أي مكان بالنظام — الصفحة الإدارية الكاملة **أو** مودال الإضافة السريعة من داخل فاتورة جديدة — **نفس المنطق بالضبط بالمكانين، بلا نسخة مبسَّطة بأي منهم**):
- **ذمة** (التزام) — تحت حساب أب مضبوط بـ`setting_key='supplier_payable'`
- **دفعة مقدمة** (أصل) — تحت حساب أب مضبوط بـ`setting_key='shipping_advance'` أو مكافئه

```php
$cnt = COUNT(*) WHERE parent_id = $parentPayable['id'];
$code = $parentPayable['code'] . '.' . str_pad($cnt+1, 3, '0', STR_PAD_LEFT);
INSERT INTO account_charts (code, name, parent_id, account_type, currency_id, level, is_locked)
    VALUES ($code, "ذمم {$name}", $parentPayable['id'], 'liability', $baseCurrencyId, ..., 0);
```

**فجوة حقيقية وقعنا فيها:** مودال الإضافة السريعة (من داخل الفاتورة) كان `INSERT` مبسَّط بلا إنشاء حسابات — مورد مضاف من هناك يطلع بلا أي ربط محاسبي. **افحص هالنقطة بالذات أول شي بأي مودال إضافة سريعة جديد.**

## ٨. نظام التصميم (Design System)

### الألوان الدلالية
| اللون | يمثّل | مثال |
|---|---|---|
| أحمر `#dc2626` | شراء منتجات | عنوان مستند الشراء، `var(--section-color)` بالمشتريات |
| أخضر `#16a34a` | بيع منتجات | عنوان مستند البيع (بالمبيعات) |
| برتقالي `#f59e0b` | صيانة/قيد الإعداد | صفحة `orders.php` الموقوفة |
| كحلي `#1e3a8a` | إجراءات أساسية | أزرار الحفظ الرئيسية |

### جدول البنود (كل صفحات القسم)
- شارة رقم دائرية (`.row-num`) بدل رقم عادي
- شريط لوني رفيع بحافة كل صف يطابق لون "الكروب" (`--grp-c` CSS variable)
- حقول مقفلة (محسوبة/من بيانات المنتج): نسيج `repeating-linear-gradient` خفيف بدل رمادي فاطس، `title` توضيحي
- أرقام بخط ثابت العرض (`font-variant-numeric: tabular-nums` أو كلاس `.n`)
- `table-layout:fixed` + `min-width:0` على عمود الشبكة الأب (`.page-grid > div:first-child`) لمنع جدول عريض من دفع عرض الصفحة/الشريط الجانبي

### "مبالغ الفاتورة" (سلسلة حسابية متصلة)
خط رأسي + نقاط ملوّنة (أحمر=خصم، أخضر=إضافة، كحلي=مجموع جزئي)، صندوق "توثيقي فقط" منقّط منفصل للعملة/سعر الصرف، بانر بارز متدرج للمبلغ النهائي.

### الجداول العامة (`.mtbl`)
رأس رمادي فاتح (`#f8fafc`) بلا حدود ثقيلة، `tr:hover{background:#f8faff}`، قابلة للفرز بالنقر (`makeSortable(table)` — دالة واحدة مشتركة، مُستنسخة بكل صفحة، ترتيب فحص: تاريخ ISO أولاً، رقم، أخيراً نص عربي؛ `data-no-sort` على عمود الإجراءات).

### قوالب الطباعة (`window.open('')` + `document.write`)
- مستند DOM منفصل بالكامل — **ما بيرث** `:root{--section-color}` من الصفحة الأصلية، لازم حقن القيمة صراحة أو استخدام لون ثابت بالقالب.
- حدود جدول واضحة (`border:1.5px solid #1e293b` إطار خارجي، `border:1px solid #94a3b8` داخلي) — لا الاعتماد على `border-bottom` خفيف فقط.
- هيدر ٣ أقسام: شعار المستأجر (يسار) + عنوان المستند الملوّن (وسط) + بيانات الفرع/السجل التجاري (يمين).
- تذييل: كشف حساب مختصر (المستحق قبل/آخر دفعة/الرصيد بعد) — **بعملة الفرع دايماً**، محسوب من رصيد حساب الطرف الفعلي بعكس أثر هالمستند تحديداً (`balance_after ± final_base ∓ paid_base`).

## ١٠. تحويل الفروقات مبيعات ↔ مشتريات (خارطة استبدال)

| المشتريات | المبيعات | ملاحظة |
|---|---|---|
| مورد (`product_suppliers`) | عميل (`customers`) | جدول مختلف بالكامل |
| مخزون **يزيد** بالتأكيد | مخزون **ينقص** بالتأكيد | + فحص توفر الكمية إجباري بالبيع |
| مدين مخزون / دائن ذمة مورد | مدين ذمة عميل (أو صندوق) / دائن إيراد + **قيد COGS منفصل** | البيع له قيدين، لا قيد واحد |
| `cost_price` (سعر التكلفة) | `selling_price` (سعر البيع) | **لا تخلط الاثنين** — كل قسم له عمود مرجعي مختلف بـ`product_sizes` |
| مرتجع شراء: مدين ذمة/دائن مخزون | مرتجع بيع: مدين مخزون / دائن ذمة عميل **+ عكس قيد COGS الأصلي** | مرتجع البيع أعقد — لازم يرجّع COGS كمان، لا بس الإيراد |
| `purchase_number` (`{بادئة}-PUR-...`) | `invoice_number` (`{بادئة}-SL-...` أو نمط موجود أصلاً بـ`sales_invoice_new.php`) | تحقق الصيغة الفعلية الموجودة قبل الافتراض |
| لا تحقق مخزون وقت الحفظ (الشراء دايماً يزيد) | **تحقق مخزون إجباري** وقت الحفظ/التأكيد (احترام `allow_negative_stock`) | فرق سلوكي حقيقي، مو تسمية بس |

## ١١. Checklist نهائي قبل تسليم أي ملف جديد بهالنمط

- [ ] هل أي مبلغ معروض/محسوب يقرأ من عمود بعملة الفرع بس يُعرض جنب رمز عملة المستند؟ (قسم ٤-٢)
- [ ] هل مفتاح تجميع "الكروب" يعتمد السعر الافتراضي المُعاد بناؤه، لا الصافي؟ (قسم ٤-٣)
- [ ] هل `quantity` المخزَّنة لكل صف = الكمية المفردة، لا المضخّمة؟ (قسم ٤-٤)
- [ ] هل `original_amount` بالقيود مُشتق (`base×rate`)، لا مقروء من عمود مكرَّر؟
- [ ] هل الحماية من `status≠draft` مطبَّقة GET **و**POST سوا (لصفحات التعديل)؟
- [ ] هل فحص توفر الكمية الفعلية يصير وقت **التأكيد** (مو بس وقت الحفظ)؟
- [ ] هل `removeLine()` (أو مكافئها) تستخدم `row_id` المخزَّن، لا نمط مُعاد بناؤه؟
- [ ] هل أي حقل "حساب مستهدف" جديد يستخدم حسابات الطرف الموجودة أصلاً، لا حساب وسيط جديد؟
- [ ] هل مودال الإضافة السريعة (مورد/عميل) بينشئ نفس الحسابات التلقائية متل الصفحة الإدارية الكاملة؟
- [ ] هل جرَّبت المستند بعملة **غير** عملة الفرع قبل التسليم؟ (كل الأمثلة أعلاه ما انكشفت إلا بعملة أجنبية — `rate=1` بيخفي كل هالفئة من الأخطاء تماماً)
