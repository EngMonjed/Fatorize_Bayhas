## ١. نظرة عامة

**FATORIZE** نظام تخطيط موارد مؤسسات (ERP) بالعربية بالكامل (واجهة RTL)،
مبني بـPHP خالص (بدون إطار عمل — procedural + دوال حرة)، MySQL/MariaDB،
موجّه لقطاع تصنيع/بيع الألبسة بالمنطقة العربية. المنتج بصيغة **SaaS
متعدد المستأجرين** — كل شركة عميلة (tenant) عندها قاعدة بيانات منفصلة
تماماً، بنفس نسخة الكود المشتركة.

كل tenant بيغطي: مبيعات، مشتريات، مخزون متعدد المستودعات، محاسبة كاملة
(دليل حسابات، قيود يومية، سندات قبض/دفع، تقارير مالية)، موارد بشرية
ورواتب (بمنطق استحقاق محاسبي حقيقي)، مستهلكات ومصاريف تشغيلية، طلبات
داخلية بين الفروع، وصلاحيات دقيقة لكل مستخدم/فرع/قسم.

## ٢. التقنيات المستخدمة

| الطبقة | التقنية |
|---|---|
| الخادم | PHP (procedural، بدون إطار عمل، PHP 7.4+/8.x) |
| قاعدة البيانات | MySQL/MariaDB عبر PDO (prepared statements حصراً) |
| الواجهة | HTML5 مُخرَج من PHP مباشرة (بدون محرك قوالب) |
| CSS | ملف مشترك `layout.css` + Bootstrap 5.3 RTL (CDN) |
| JavaScript | Vanilla JS، inline بكل صفحة + ملفات مشتركة محدودة (`assets/js/sidebar.js`) |
| الخطوط/الأيقونات | خط Cairo (Google Fonts)، Bootstrap Icons |
| كلمات المرور | `password_hash()`/`password_verify()` (bcrypt) |
| الجلسات | PHP Sessions أصيلة (`$_SESSION`) — آلية الحالة/الصلاحيات الوحيدة |
| تبادل البيانات | HTML مُخرَّج من الخادم + AJAX (`fetch`) بصيغة `_action` POST موحَّدة، JSON |

**مؤكَّد أنه غير مستخدم:** أي إطار MVC، React/Vue/Angular، Node.js، ORM،
محرك قوالب، Composer autoloading حقيقي.

## ٣. البنية متعددة المستأجرين (Multi-Tenant SaaS)

### ٣.١ النموذج

- **قاعدة بيانات منفصلة فعلياً لكل tenant** — عزل بيانات كامل، مو مجرد
  فلترة بعمود `tenant_id`.
- **نفس نسخة الكود بالضبط** تخدم كل الـtenants — لا مجلد منفصل لكل
  عميل.
- **التمييز بين الشركات عبر الساب-دومين** (`client1.fatorize.com`)،
  مو حقل تسجيل دخول بكود شركة.

### ٣.٢ قاعدة الماستر (`fatorize_master`)

جدول `tenants` — السجل المركزي: اسم الشركة، الساب-دومين، بيانات اتصال
قاعدة بياناتها (كلمة السر مشفَّرة AES-256-CBC عبر `encryptSecret()`/
`decryptSecret()`)، حالة الاشتراك (`active`/`suspended`/`cancelled`).

جدول `currencies` (بقاعدة الماستر، منفصل تماماً عن `currencies` بقاعدة
كل tenant) — قاموس عملات مصغَّر (كود/اسم/رمز، **بدون** أسعار صرف).

عمود `tenants.reporting_currency_id` (FK) — **عملة التقارير على مستوى
الشركة كاملة**، تُحدَّد مرة وحدة وقت تسجيل الشركة، **تتجمّد بعدها نهائياً**
(Trigger حقيقي بقاعدة البيانات `trg_tenants_freeze_reporting_currency`
بيرفض أي `UPDATE` يغيّرها). هاي **مختلفة تماماً** عن العملة الوظيفية لكل
فرع (راجع §٦).

### ٣.٣ تحليل الطلب (`config/tenant_resolver.php`)

كل طلب HTTP بيتحلّل الساب-دومين منه أول شي (`resolveCurrentTenant()`)،
بيتراجع لجدول `tenants` بقاعدة الماستر، بيفكّ تشفير بيانات اتصال قاعدة
الـtenant، وبعدين `config/database.php::getConnection()` بيتصل بقاعدة
الشركة الصحيحة **تلقائياً** — باقي كل ملفات النظام بتستدعي `getConnection()`
بنفس الطريقة العادية، بدون أي وعي بمنطق تعدد المستأجرين.

لو الساب-دومين مش موجود بجدول `tenants`، أو الحساب موقوف/ملغى — صفحة
خطأ عربية واضحة بدل أي محاولة اتصال.

**الدومين الرئيسي** (`fatorize.com` بدون ساب-دومين) بيخدم صفحات تسويقية
عامة (`index.php`, `about.php`, `find-my-company.php`) — **ما بتتصل
بأي قاعدة بيانات إطلاقاً**، لأنها سابقة لمعرفة أي شركة أصلاً.

### ٣.٤ نشر الإنتاج — قيد معماري حقيقي مكتشَف بالتطبيق

**Wildcard SSL الحقيقي (`*.domain.com`) غير مدعوم على خطط الاستضافة
المشتركة/Cloud العادية** (مؤكَّد رسمياً من دعم Hostinger) — متاح فقط
على VPS. **الحل البديل المعتمد**: كل tenant جديد ياخد ساب-دومين مُعرَّف
صراحة بلوحة الاستضافة (خيار "استخدام نفس مجلد الموقع الرئيسي"، مو مجلد
منفصل)، فيصدر SSL تلقائياً بدقائق. التكلفة العملية: ٢-٣ دقايق إعداد
يدوي لكل عميل جديد — كافي جداً لعدد قليل من الـtenants، وقابل للترقية
لـVPS + wildcard حقيقي لو زاد العدد.

## ٤. البنية متعددة الفروع (داخل كل Tenant)

### ٤.١ عزل البيانات: لاحقة اسم جدول، لا Schema منفصل

كل فروع نفس الشركة تتشارك **قاعدة بيانات واحدة**. العزل بين الفروع بلاحقة
اسم الجدول (`table_suffix`): `sales_invoices_ret`, `products_fac`،
إلخ. الجداول **العالمية** (بدون لاحقة — `branches`, `users`, `currencies`,
`modules`, `internal_orders`...) مشتركة بين كل فروع نفس الشركة.

### ٤.٢ نوع الفرع: `retail` أو `factory` بس

عمود `branches.branch_type` — `ENUM('retail','factory')` مقيَّد (لا أسماء
جغرافية، لا أنواع تانية زي "مستودع"/"مكتب"). النوع بيتحكّم بـ:
- ظهور/إخفاء قسم "الإنتاج" بالشريط الجانبي (منطق ديناميكي حسب
  `$_SESSION['branch_type']`، **مو** مقارنة نصية بـ`table_suffix` —
  آمن لأي عدد فروع من نفس النوع)
- الجداول الإضافية يلي بتتنشئ وقت إنشاء الفرع (جداول التصنيع الخمسة
  الحصرية لفروع `factory`)

### ٤.٣ الكود الفيزيائي — مجلد واحد مشترك، مش مجلد لكل فرع

**قرار معماري مؤسِّس:** كل الفروع (بيع أو تصنيع) بتشارك **نفس مجلد
الكود الفيزيائي** (`modules/`). الفرق بين الفروع بيصير بثلاث طبقات
بس، مش بمجلدات منفصلة:

1. **البيانات** — `$_SESSION['table_suffix']` ديناميكي بكل استعلام.
2. **ظهور القائمة** — فلترة الشريط الجانبي حسب `branch_type`.
3. **الصلاحيات** — `user_permissions` لكل مستخدم/فرع/قسم.

**الاستثناء الوحيد المبرَّر لمجلد جديد:** قسم فرعي **جديد بالكامل**
وخاص حصراً بنوع فرع واحد (`modules/production/` — منطقي لأنها صفحات
جديدة تماماً، ماإلها مقابل بفروع البيع أصلاً). أي قسم مشترك المنطق بين
الفروع (مبيعات، مخزون، محاسبة، موارد بشرية) **لا يُنسخ فيزيائياً أبداً**.

### ٤.٤ توفير فرع جديد (`createBranchTables()`)

آلية **ديناميكية بالكامل**: بتكتشف تلقائياً كل جداول الفرع المرجعي
(أول فرع بيع، لاحقة `_ret`) عبر `SHOW TABLES`، وتستنسخها لأي فرع جديد
بـ`CREATE TABLE ... LIKE` (بنية، فهارس، `AUTO_INCREMENT` كاملة). **لا
قائمة SQL ثابتة مكتوبة يدوياً** — أي عمود/جدول يُضاف لفرع البيع
مستقبلاً بينعكس تلقائياً بأي فرع جديد بدون أي صيانة يدوية لسكريبت
التوفير.

**الجداول الحصرية بفروع `factory`** (لا قالب بفرع بيع أصلاً — يدوية
بالضرورة): `raw_materials`, `raw_material_stock`, `production_operations`,
`production_entries`, `manufacturing_bom` (كلها بلاحقة الفرع الجديد).

**فرع جديد بيتوفّر جاهز للعمل المحاسبي فوراً** — بذرة دليل حسابات كاملة
(٤٤ حساب، ٤ مستويات، بعملة الفرع الوظيفية الحقيقية) + ٢٥ ربط محاسبي
(`invoice_account_settings`) محلولين تلقائياً لأكواد الحسابات المزروعة
بنفس الفرع + فئات/وحدات مستهلكات افتراضية + مستودعين (منتجات ومستهلكات).

### ٤.٥ إنشاء فرع جديد — واجهة إدارية

صفحة `admin/branch_add.php` (منفصلة تماماً عن `admin/branches.php`
يلي هي **تعديل فقط** لفروع موجودة): اختيار نوع الفرع (بيع/تصنيع)،
تحقق فوري من تفرّد `table_suffix`، **اختيار العملة الوظيفية للفرع —
هالصفحة المكان الوحيد بالنظام يلي هالحقل قابل للتعديل فيه**، وخيار
"إنشاء الجداول فوراً" بضغطة وحدة.

## ٦. نظام العملات — طبقتين منفصلتين تماماً

| المستوى | الاسم المحاسبي | أين يُختار | أين يُخزَّن | يُجمَّد؟ |
|---|---|---|---|---|
| **الشركة كاملة** | عملة التقارير (Reporting Currency) | تسجيل الشركة | `fatorize_master.tenants.reporting_currency_id` | ✅ نهائياً (Trigger بقاعدة البيانات) |
| **كل فرع لحاله** | العملة الوظيفية (Functional Currency، IAS 21) | إنشاء الفرع (`branch_add.php`) | `branches.base_currency`/`base_currency_id` (بقاعدة الـtenant) | ✅ نهائياً (`disabled` بالواجهة + رفض صريح بالسيرفر) |

**العملة المحلية** (`branches.local_currency`) — عملة المعاملات اليومية،
**قابلة للتعديل عادي** (غير مجمَّدة)، منفصلة تماماً عن العملة الوظيفية.

### القاعدة الذهبية المطبَّقة عبر كل المستندات المالية (فواتير، مرتجعات، سندات)

**كل مبلغ بمستوى رأس المستند (الإجمالي، الخصم، الضريبة) = عملة الفرع
الوظيفية دايماً، بدون استثناء.** عملة المستند المختارة (لعرضها للعميل/
المورد) توثيقية بس — أي قيمة بعملتها تُشتق وقت العرض (`base × rate`)،
ما تُخزَّن بعمود مستقل منفصل بمستوى الرأس.

**الاستثناء الوحيد المتعمَّد:** `unit_price` بمستوى بند السطر (فاتورة
بيع/شراء) فعلاً بعملة المستند، جنب `unit_price_base_currency`/`unit_price_base`
بعملة الفرع — زوج حقيقي مقصود، ما ينطبق على مستوى الرأس.

**بمستوى القيد المحاسبي (`journal_entry_items`):** `original_amount`
(بعملة المعاملة الأصلية، ثبات تاريخي دائم) منفصل عن `base_amount`
(بعملة الفرع) — مبدأ IAS 21 مطبَّق حرفياً.

**العملة دايماً `currency_id` (FK رقمي)** بجداول القيود، أبداً عمود
`currency` نصي حر.

## ٧. المصادقة والصلاحيات

### تدفق الدخول

`login.php` (اسم مستخدم + كلمة سر، bcrypt) → `select_account.php`
(اختيار فرع من الفروع المصرَّح بها للمستخدم عبر `user_branches`، بيخزّن
`branch_id`/`table_suffix`/`branch_type`/`dashboard_path` بالجلسة) →
داشبورد الفرع.

### الصلاحيات — نموذج دقيق مزدوج

- **دور عام** (`users.role`): `admin`/`accountant`/`sales`/`purchases`/
  `warehouse`/`user`. **`admin` بس بيتخطى كل فحوصات الصلاحية تلقائياً**
  (wildcard `['*']`).
- **صلاحيات دقيقة** (`user_permissions`): سبع أعلام منفصلة لكل
  (`user_id`, `branch_id`, `module_key`): `can_view/create/edit/delete/
  confirm/print/export`. مُخزَّنة بكاش الجلسة (`$_SESSION['permissions']`)
  — تغيير صلاحية لمستخدم داخل بالفعل يحتاج خروج/دخول من جديد ليُطبَّق.

### كل صفحة موديول — نمط بوابة موحَّد

```php
session_start();
require_once __DIR__ . '/../../../config/database.php';
require_once __DIR__ . '/../../../config/auth.php';
$pdo = getConnection();
checkLogin($pdo);
requirePermission('module.key', 'view');
$TS = $_SESSION['table_suffix'];
$currentModule = 'module.key';
```

## ٨. الشريط الجانبي والقوائم الديناميكية

القائمة كاملة **مبنية من قاعدة البيانات**، مش ثابتة بالكود — جدول
`modules` (عالمي، بدون لاحقة فرع): `key`/`parent_key` (تدرّج قسم←صفحة)،
`label`, `icon`, `sort_order`, `is_active`, `theme_color` (بس على
الصفوف الأب).

`buildSidebarMenu()` (بـ`config/auth.php`) بتجيب كل الصفوف الفعّالة،
تفلترها حسب صلاحية `view` للمستخدم الحالي (الأدمن يشوف الكل)، وتبني
شجرة قسم→أبناء. `includes/sidebar.php` بعدها:
- بترتّب المجموعات حسب أولوية ثابتة (مبيعات، مخزون، مشتريات، مالية،
  مصاريف، موارد بشرية، إدارة — الإنتاج مخفي تلقائياً لفروع البيع)
- بتحدّد القسم "النشط" حسب `$currentModule` الفعلي (مو تخمين نصي)
- بتحقن متغيّر CSS للون القسم الحالي (راجع §٩)

**خريطة `moduleUrl()`** (بنفس الملف) — تحويل `module.key` → مسار ملف
فيزيائي حقيقي. **أي صفحة جديدة تحتاج ثلاث تسجيلات منفصلة، مش وحدة**:
(١) صف بجدول `modules`، (٢) مدخل بـ`moduleUrl()`، (٣) `$currentModule`
داخل الصفحة نفسها — نسيان أي وحدة بيعطي عطل صامت مختلف (رابط فاضي،
صفحة تشتغل بس ما تتفعّل بالقائمة، أو ما تظهر إطلاقاً).

### الشريط الجانبي — منطق JS مشترك وحيد

`assets/js/sidebar.js` — ملف واحد (فتح/إغلاق موبايل + طي/فرد الأقسام)،
كل صفحة تستدعيه بسطر وحيد قبل `</body>`:
```php
<script src="<?= BASE_PATH ?>/assets/js/sidebar.js"></script>
```
**لا نسخ محلي مكرَّر بأي صفحة** — القسم "النشط" المحدَّد من الـPHP هو
المرجع الوحيد الموثوق (بيصفّر أي قيمة `localStorage` قديمة متعارضة).

## ٩. نظام الألوان الموضوعية لكل قسم (Section Theming)

كل قسم رئيسي (`modules.theme_color`، عمود hex) عنده لون مميّز، مُدار
من صفحة إعدادات مخصصة (`admin/section_colors.php` — Color Picker لكل
قسم، حفظ فوري). `includes/sidebar.php` بيحقن اللون كمتغيّر CSS وحيد
بأول كل صفحة:
```php
<style>:root { --section-color: <?= $sectionColor ?>; }</style>
```
أي صفحة بتستخدم `var(--section-color)` بدل ألوان hex ثابتة (أزرار
أساسية، تبويب نشط، حدود مميّزة) — **لا** الألوان الدلالية (نجاح/خطر/
تحذير تضل ثابتة بغض النظر عن لون القسم). تغيير اللون من صفحة الإعدادات
بينعكس فوراً على كل صفحات القسم بدون رفع أي ملف جديد.

**استثناء مقصود:** الصفحات مزدوجة الغرض (`warehouse.php`, `movements.php`
— بتخدم قسمين حسب `?type=`/`?tab=`) عندها لون محسوب يدوياً حسب السياق
النشط فعلياً، مش `var(--section-color)` المباشر.

## ١١. القواعد المعمارية الذهبية (تنطبق عبر كل الأقسام التجارية)

هاي المبادئ المعتمدة موحَّدة بكل مستند مالي بالنظام (فواتير بيع/شراء،
مرتجعاتهم، فواتير/صرف المستهلكات، سندات القبض/الدفع، المصاريف):

1. **عملة الفرع بمستوى الرأس دايماً** (راجع §٦) — `final_amount ==
   final_amount_base_currency` حرفياً.
2. **دورة حياة موحَّدة**: مسودة → تأكيد (ملف `api/confirm_*.php` منفصل،
   معاملة واحدة تغلّف المخزون + القيد المحاسبي + تحديث الحالة، فحص
   كمية/رصيد سيادي وقت التأكيد نفسه) → مؤكَّد/ملغى.
3. **الإلغاء ≠ الحذف**: أي "حذف" لمستند مؤكَّد = قيد عكسي حقيقي + تغيير
   حالة (`status='cancelled'`)، **أبداً `DELETE` فعلي** يمحي القيد
   المحاسبي.
4. **المرتجع مستقل عن الإلغاء**: مستند جديد قائم بذاته (`*_returns`
   جداول منفصلة)، بسعر التكلفة الأصلي للبند المُرجَع، مو تعديل على
   المستند الأصلي.
5. **نمط "الحساب المستهدف"** (`target_account_type`) لكل عملية تسوية
   مالية (مرتجع، دفعة): قيمة من (`cash`/`receivable أو supplier`/
  `prepaid أو advance`) بتحدد الوجهة المحاسبية الفعلية — بلا حساب وسيط
  جديد بشجرة الحسابات، الوجهة دايماً حساب موجود أصلاً.
6. **حساب مخصص تلقائياً لكل كيان تجاري جديد** (عميل، مورد، شركة شحن،
   موظف) — حساب فرعي (أو حسابين: ذمة + دفعة مقدمة/سلف) بشجرة الحسابات،
   من أي مكان بالنظام ينشئ الكيان (صفحة إدارية كاملة أو مودال إضافة
   سريعة من داخل فاتورة). **لا حساب أب مشترك واحد بدون تفصيل**.
7. **حسابات الدفع/القبض تُسحَب من `invoice_account_settings` الفعلي**
   (مفاتيح `cash_%`/`bank_%`/`setting_key` محدَّد)، **أبداً تخمين بادئة
   كود** (`code LIKE '111%'`).
8. **`postAccountBalance()` مشتركة** — أي قيد محاسبي بيرحّل فعلياً
   `balance` (بعملة الحساب) و`base_balance` (بعملة الفرع) على
   `account_charts` بمكانه الصحيح (مدين/دائن حسب طبيعة الحساب) — **مو
   بس كتابة سطر بدفتر اليومية**.

### التسعير — نظام ثلاثي المستويات

- **سعر البيع الافتراضي** (قراءة فقط، من `product_sizes.selling_price`)
- **قيمة الخصم الإفرادي** (محسوبة تلقائياً، مبلغ لا نسبة)
- **سعر البيع بعد الخصم** (الحقل التحريري الوحيد)

`packet_qty` جزء أساسي من معادلة الإجمالي الفعلي: **عدد المنتجات =
عدد الكروبات × packet_qty**. `quantity` المخزَّنة بمستوى الصنف = عدد
الكروبات بس.

**مسح الباركود** = إضافة فورية تلقائية (نمط سوبرماركت) — موجود بالفاتورة
→ +١ للكمية، مو موجود → سطر جديد بكمية ١. البحث بالاسم/الموديل (نتائج
متعددة محتملة) يفتح مودال اختيار.

### المرتجعات — مسارات `target_account_type` الثلاثة

| القيمة | السلوك |
|---|---|
| `receivable` (افتراضي) | خصم من ذمة العميل، بلا قيد إضافي |
| `cash` | استرداد نقدي فعلي — قيد إضافي (عكس الذمة + دائن صندوق) |
| `prepaid` | تحويل لرصيد دائن بحساب `customers.prepaid_account_id` الخاص بالعميل — يرفض بوضوح لو الحساب مش مضبوط |

### إدارة العملاء

كل عميل عنده `account_id`/`prepaid_account_id` (حساب مخصص تلقائي).
حقول `credit_limit`/`discount_percentage`/`notes` معلوماتية حالياً
(للتناظر مع الموردين، غير مفعَّلة بمنطق تلقائي بعد). صف الفاتورة بقائمة
المبيعات ملوَّن حسب حالة الفاتورة+الدفع مجتمعتين.

### الرواتب كالتزام محاسبي حقيقي (Accrual)

**Subledger حقيقي لكل موظف** — حساب فرعي مخصص (مستحقات + سلف)، نفس
نمط العملاء/الموردين، لا حساب مركزي واحد بدون تفصيل.

**قيد الاستحقاق منفصل عن قيد الدفع** (خطوتين، IAS 21/GAAP):
- `accrue` — قيد استحقاق (مدين مصروف رواتب / دائن رواتب مستحقة الدفع)
- `pay` — قيد دفع لاحق (مدين رواتب مستحقة / دائن صندوق)، بديل مباشر
  لو الفترة مو معتمدة أصلاً

**السلف**: قيد فوري عند الصرف (مدين سلفة الموظف / دائن الصندوق). القسط
يُخصم محاسبياً لحظة الاستحقاق، مو لحظة الدفع النقدي. إلغاء سلفة مسموح
بس لو صفر أقساط مدفوعة، وبمستند إلغاء بقيد عكسي منفصل — القيد الأصلي
لا يُلمَس.

**المكافآت**: "حذف" = `status='cancelled'`، لا `DELETE` فعلي.

**سعر الصرف**: مصدر وحيد معتمد — جدول `currencies` بقاعدة الـtenant
(دالة مركزية `payrollSafeRate()`). **الباك-إند لا يثق بأي رقم قادم من
الواجهة** للحساب الفعلي، حتى لو المستخدم عدَّله يدوياً بالحقل (عرض بس).

## ٢٠. الأرصدة الافتتاحية (Opening Balances)

آلية إدخال أول-مدة لأي فرع جديد أو نقل من نظام قديم — صفحة
`admin/opening_balances.php`، ٤ تبويبات:

| التبويب | الآلية |
|---|---|
| مخزون المنتجات | صنف + مستودع + كمية (+ تكلفة تلقائية من `product_sizes.cost_price`، قابلة للتعديل) |
| مخزون المستهلكات | نفس المنطق، جداول المستهلكات |
| أرصدة العملاء | مبلغ لكل عميل (مدين) |
| أرصدة الموردين | مبلغ لكل مورد (دائن) |

**المبدأ المحاسبي:** كل إدخال بيترحّل قيد حقيقي مقابل حساب مخصص
**"رصيد افتتاحي"** (equity، كود `3900`، متفرّع تحت "حقوق الملكية") —
**مو** فاتورة شراء/بيع وهمية. `reference_type='opening_balance'` لكل
قيد، قابل للفلترة بأي تقرير مستقبلي.

**آلية القفل:** مرحلة واحدة (إدخال حر، بدون قيود)، وقفل يدوي نهائي من
المدير (`branches.opening_balance_locked_at`/`_by`) — بعده كل الحقول
تتعطّل تلقائياً بالواجهة **و**السيرفر يرفض أي محاولة تعديل صراحة.

## ٢٢. قيود وفجوات معروفة حالياً (Known Limitations)

- **لا CSRF tokens** على أي نموذج/AJAX بكل التطبيق.
- **لا سجل تدقيق شامل** — `user_activities` يسجّل دخول/خروج بس، لا
  تسجيل لإنشاء/تعديل/حذف مستخدم أو تغيير صلاحيات، ولا لأي عملية تجارية
  تانية.
- **لا إقفال فترة محاسبية فعلي** — الميزانية العمومية عندها تعويض مؤقت
  بسطر اصطناعي (راجع §١٦).
- **الضرائب غير مربوطة بفواتير البيع/الشراء** — بس بسندات الدفع
  للموردين (راجع §١٦).
- **أوامر البيع/الشراء بوضع صيانة** — شكل كامل، بلا منطق فعلي (`sales/orders.php`,
  `purchases/orders.php`).
- **قسم الإنتاج غير مكتمل** — بنية تحتية جاهزة، صفحات فعلية جزئية (راجع §١٩).
- **جداول HR الفرعية بدون FOREIGN KEY حقيقي** (`hr_attendance`,
  `public_holidays`, `hr_payroll`, `hr_loans`, `hr_bonuses`) — خطر
  سجلات يتيمة لو انحذف موظف.
- **`confirm_purchase_invoice.php`'s `cancel` ما بتكتب سجل حركة مخزون
  للإلغاء** — فجوة تدقيق (بعكس `confirm_sale_invoice.php` يلي بتكتب صح).
- **ميزة ترتيب التبويبات بالسحب/الإفلات معطَّلة مؤقتاً** — الجدول
  (`user_tab_order`) والمنطق جاهزين، التفعيل بقرار صريح مؤجَّل.
- **لا صفحة "إضافة تينانت جديد" مؤتمتة بالكامل** — `super_admin/add_tenant.php`
  موجودة بس ما بتنشئ قاعدة البيانات تلقائياً (قيد استضافة مشتركة).
