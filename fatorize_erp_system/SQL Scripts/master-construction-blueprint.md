> **الغرض:** هذا الملف الوحيد يكفي عند بناء أي قسم مستندات جديد (المبيعات تحديداً) —
> يجمع كل الأنماط والقرارات والأخطاء المُصلَّحة من قسمي "المصاريف والمستهلكات"
> و"المشتريات" (فواتير + مرتجعات + تقارير) بمكان واحد. **لا تبني أي جدول أو
> شاشة دفع/عملة جديدة قبل ما تراجع البنود ذات الصلة هون.**
> يحلّ محل الرجوع لملفي `blueprint-pattern.md` و`purchase-invoice-blueprint.md`
> منفصلين — بس هنّي محفوظين كمرجع تاريخي لو احتجت التفاصيل الأصلية.

## ١. الهيكلية العامة لأي قسم مستندات

### أ) ملفات منفصلة حسب الدور — مو ملف واحد يعمل كلشي
```
{section}_new.php    → إنشاء مسودة فقط (بدون أي أثر مخزون/محاسبة)
{section}_edit.php   → تعديل مسودة موجودة (نفس قيود new.php + رفض التعديل لو الحالة ≠ draft)
api/confirm_{section}.php → الوحيد المخوَّل يحوّل مسودة لمستند فعلي (مخزون + قيود، معاملة واحدة beginTransaction/commit)
{section}.php (أو index.php) → القائمة/العرض
returns.php (لو منطبق)     → مستند مستقل تماماً للإرجاع بعد التأكيد
reports.php                → تقارير القسم (قراءة فقط)
orders.php (لو منطبق)      → أوامر/طلبات (ممكن تُبنى بوضع صيانة مؤقت إذا الأولوية أقل)
```
**لماذا:** أي خطأ بواجهة الإدخال ما بيقدر يفتح قيد محاسبي أو يحرّك مخزون بالغلط — الفصل حماية أساسية، مش شكليات.

### ب) تسجيل أي صفحة جديدة — ٣ خطوات ثابتة، بالترتيب
1. أنشئ الملف نفسه (`requirePermission('{section}.{page}', 'view')` بأول سطر).
2. سكريبت migration رقمي جديد (`NN_add_{section}_{page}_module.sql`) يسجّل الصف بجدول `modules` (`INSERT ... WHERE NOT EXISTS` — آمن لإعادة التشغيل).
3. أضف مدخل بخريطة `moduleUrl()` بـ`includes/sidebar.php` — بدون هالخطوة، الرابط بيرجع `#` وما يشتغل الشريط الجانبي ولا الـ`breadcrumb`.

### ج) صفحة مؤجَّلة عن قصد — وضع الصيانة الموحَّد
لو قرّرت تأجيل ميزة فرعية (زي أوامر الشراء)، ابنِ الصفحة بهالنمط الثابت بدل ما تسيبها بلا رابط:
```php
if (true) {
    // HTML بسيط: أيقونة bi-cone-striped + عنوان + سبب التأجيل بجملتين + زر رجوع
    exit;
}
// ── نهاية وضع الصيانة ── (كل المنطق الحقيقي تحت هالسطر، جاهز يتفعّل بحذف الشرط بس)
```
سجّل الصفحة بجدول `modules` **رغم كونها بوضع صيانة** — عشان الرابط ما يطلع مكسور بالشريط الجانبي.

## ٢. الواجهة — نظام موحَّد بكل صفحة

### أ) نظام الألوان (ثابت بكل جدول بالنظام)
| اللون | الكود | المعنى | مثال بالمبيعات |
|---|---|---|---|
| 🔵 أزرق | `#1e3a8a` | المعرّف/الرقم | رقم فاتورة البيع |
| 🟢 أخضر | `#16a34a` | المصدر | اسم العميل (هون العميل = "مصدر" الإيراد، نفس منطق المورد بالمشتريات) |
| 🔴 أحمر | `#dc2626` | الهدف/الوجهة | لو في وجهة مقابلة (نادر بالمبيعات) |
| 🟡 أصفر | `#ca8a04` | الكمية | عدد القطع/البنود |
| افتراضي (بدون لون) | — | القيمة المالية | الإجمالي، الصافي |

### ب) هيكل الصفحة الثابت (كل صفحة قسم)
```
Sidebar + Header (breadcrumb) → شريط تبويبات القسم (كل الصفحات، روابط نسبية) 
→ ٤ بطاقات إحصائيات (محسوبة من بيانات فعلية، بعملة الفرع لو فيها مبالغ — لا تجمع عملات مختلفة خام)
→ جدول (tbl-wrap > tbl-hdr [عنوان + فلاتر + بحث + زر إجراء] > table.mtbl قابل للفرز)
```

### ج) الجداول
- كلاس `mtbl` فقط (لا `table table-hover` العام).
- `makeSortable()`/`sortTableByColumn()` — نفس الدالة تُنسخ بكل صفحة (ليست ملف مشترك بهالنظام)، بترتيب فحص: **تاريخ ISO أولاً** (مقارنة زمنية حقيقية، لا `parseFloat` مباشر عليه)، رقم كامل المطابقة، وأخيراً نص عربي.
- `data-no-sort` على عمود "إجراءات".
- **جدول التقارير تحديداً:** لو الصفوف قليلة/الأرقام قصيرة، الجدول بيتقلّص لعرض محتواه بصمت (يبان "مضغوط بزاوية") — أضف `width:100% !important` و`table-layout:auto` صراحة لأي جدول تقارير من أول بناء، لا تنتظر الشكوى.

### د) المودالات
- `modal-xl`/`modal-lg` دايماً لنماذج المستندات الحقيقية.
- بنود المستند: سطر جديد **فوق**، تظليل أخضر مؤقت، تركيز تلقائي، بارامتر `isNew`، حذف بمرجع الكائن لا بالـ`index`.

### هـ) القوائم المنسدلة — دايماً من جدول حقيقي
لا `enum` ولا مصفوفة PHP ثابتة لأي تصنيف/جهة — زر "+" لإضافة سريعة بجانب أي قائمة كهيك.

## ٣. بناء بنود المستند (Line Items) — أخطر جزء تقني، وقع فيه خطأين منفصلين

### أ) "الكروب" بالواجهة ≠ "المتغيّر الفعلي" بقاعدة البيانات
سطر واحد بالواجهة (منتج+سعر+لون) ممكن يمثّل **عدة متغيّرات فعلية** (مقاسات مختلفة). لازم فصل واضح:
- `line.qty` (الواجهة) = عدد المتغيّرات المدموجة بالسطر — **لازم يزيد مع كل دمج** (`mergeVariant()`)، مو يضل ثابت.
- عند **الحفظ الفعلي**: كل متغيّر داخل سطر متعدد المتغيّرات = **قطعة وحدة (`quantity=1`)** — لا نطبّق `line.qty` الكامل على كل متغيّر بذاته (هيك ضاعفنا الكمية مرتين فعلياً: مرة عالسطر، ومرة تانية لكل متغيّر). `line.qty` الكامل يُطبَّق بس لو السطر أصلاً متغيّر وحيد (تعديل يدوي حقيقي لكمية واحدة).

### ب) تجميع العرض (لا التحرير) — بالكروب لا باللون
مودال العرض/التأكيد/قالب الطباعة: صف واحد لكل (منتج+سعر)، عمود "اللون" يجمع كل الألوان المشاركة (` · `)، الكمية = **مجموع فعلي** من كل الأسطر (لا كمية أول عنصر بس). جدول **التحرير/الإنشاء** نفسه يبقى صف لكل لون (تحكّم دقيق بالسعر وقت الإدخال) — التوحيد للعرض بس.

### ج) السعر المستخدم بالمرتجع = الصافي، لا الخام
لو الفاتورة فيها **خصم على السطر نفسه** (مو بس خصم إجمالي على الفاتورة)، أي إرجاع لاحق لازم يستخدم `total_price ÷ quantity` (السعر الصافي الفعلي المدفوع)، **لا** `unit_price` الخام (قبل خصم السطر) — وإلا المرتجع بيحسب قيمة أعلى من الصحيح. خصم الفاتورة الإجمالي (كنسبة متناسبة) ينطبق **فوق** هيك، بلا ازدواجية.

## ٤. العملات — أخطر ملف بالنظام كله (٥+ أخطاء متتالية هون، بالترتيب التاريخي يلي صارت فيه)

### أ) الثلاث عملات، ولازم عدم خلطهم أبداً
| العملة | مين بيحددها | وين تُستخدم |
|---|---|---|
| **عملة المستند** | تُختار وقت الإنشاء، ثابتة | كل أعمدة المستند (`total_amount`, `final_amount`...) |
| **عملة الفرع الأساسية** | FK ثابت (`branches.base_currency_id`) | كل أعمدة `journal_entries`/`journal_entry_items` (`total_debit`, `base_amount`) |
| **عملة الدفع الفعلية** | تُختار وقت التأكيد | `original_amount` بسطر القيد + حساب الصندوق/البنك المُقيَّد |

### ب) القرار النهائي المعتمد لـ"عملة الدفع" (بعد تجربة وتراجع) — طبّقه من أول يوم بالمبيعات
**لا تعرض قائمة عملات كاملة لحقل "عملة الدفع" بمودال التأكيد.** احصرها بخيارين بس: **عملة المستند، أو عملة الفرع** — تُملأ ديناميكياً فور تحميل بيانات المستند. أي دفع بعملة ثالثة (نادر) يصير من صفحة "المدفوعات" العامة بقسم المحاسبة، مش من مودال التأكيد. هيك بتقضي مسبقاً على كل تعقيد سعر الصرف اليدوي بهالحقل تحديداً.

**عملة الشحن (أو أي تكلفة فرعية مشابهة) تبقى بلا قيد** — أي عملة من الجدول العام، مع حقل سعر صرف يدوي شرطي (يظهر بس لو "عملة ثالثة" فعلاً — مو عملة المستند ولا الفرع)، لأنها غالباً محدَّدة من طرف خارجي (شركة الشحن) خارج تحكّمك.

### ج) معادلة التحويل — خطوتين، مش خطوة وحدة
```
عملة الدفع → عملة المستند:  المبلغ ÷ سعر_الصرف_المُدخَل   (سعر_الصرف = "1 عملة المستند = س عملة الدفع")
عملة المستند → عملة الفرع:   ÷ exchange_rate المسجَّل على المستند نفسه
```
**تسمية الحقل مهمة:** "عملة الفرع" هي المرجع الثابت (الـ"١") دايماً بالليبل المعروض — نفس رقم `exchange_rate` المخزَّن مباشرة، بدون أي عكس. (وقعنا بهالعكس أكتر من مرة — راجع لو حسّيت رقم غريب زي "٠.٠٢" بدل "٤٥.٩").

### د) 🔴 القرار الأهم للأمان: الحساب المحاسبي الفعلي مستقل تماماً عن أي رقم قادم من الواجهة
بما إنه عملة الدفع محصورة بخيارين معروفين (مستند/فرع)، **لا تعتمد الباك-إند على `paidRate` المُرسَل من الواجهة لحساب `base_amount` إطلاقاً**:
```php
if ($paidCur === $branchBaseCurrency) { $paidAmt = $paidOrigAmt; }          // بديهي، بدون أي تحويل
elseif ($paidCur === $docCurrency)    { $paidAmt = $paidOrigAmt / $rate; }  // $rate = exchange_rate المستند نفسه (ثابت وموثوق)
else { throw new Exception('عملة دفع غير مدعومة'); }                        // احتياط دفاعي — الواجهة المقيَّدة ما توصل هون أصلاً
```
حقل السعر بالواجهة صار **للعرض/المعاينة بس** ("المبلغ بعملة المستند")، مش مصدر الحقيقة المحاسبية — حتى لو صار خطأ مستقبلي بعرض الواجهة، الرقم المحاسبي الحقيقي ما بيتأثر.

### هـ) تسمية `currency_id`/`exchange_rate` بجداول القيود
- **رأس القيد** (`journal_entries.total_debit/credit`): `currency_id` = عملة الفرع الأساسية دايماً (لأنها فعلياً بهاي العملة).
- **سطور القيد** (`journal_entry_items`): `currency_id` = عملة "الطرف الأصلي" لهاد السطر تحديداً (مطابق لـ`original_amount`) — قيد الشحن مثلاً بعملته الخاصة، قيد الاسترداد بعملة المستند.
- **`exchange_rate` المخزَّن بأي سطر قيد = `original_amount ÷ base_amount` فعلياً محسوب، لا متغيّر وسيط جانبي منسوخ كما هو** — أكتر باگ متكرر بهالمشروع كان نسخ رقم وسيط بمعنى مختلف عن المطلوب تخزينه.

### و) لا عمود عملة نصي مباشر أبداً، حتى لو موجود
أي عمود `currency` (نص) بأي جدول — **لا يُقرأ مباشرة**، دايماً عبر `_id` (FK) بجوين حي على `currencies`. لو موجود عمود نصي قديم جنب FK صحيح، هو على الأغلب **متروك وغير محدَّث** (نفس فئة `branches.base_currency`/`purchases.currency` القديمين — لقيناهم أكتر من مرة يحملوا قيمة غلط بالصدفة).

## ٥. اتجاه القيد (مدين/دائن) — 🔴 أخطر باگ صار بكل المشروع، تكرر ٣ مرات منفصلة

**القاعدة الأساسية (من أول قيد استلام/بيع بالنظام):**
- حساب **التزام** (ذمم موردين/عملاء): **دائن = طرح** (زيادة المديونية)، **مدين = جمع** (تخفيض المديونية).
- حساب **أصل** (مخزون، صندوق): **مدين = جمع** (زيادة)، **دائن = طرح** (نقصان).

**الخطأ يلي تكرر:** بناء قيد "مدين" جديد (دفعة، خصم، مرتجع) بنسخ نفس عامل الطرح من القيد "الدائن" الأصلي **بدون عكسه**. النتيجة: الدفع كان يزيد المديونية بدل ما ينقصها — رقم صحيح بالمظهر (نفس المبلغ)، بس اتجاه الأثر معكوس بالكامل، وما بينكشف إلا برصيد نهائي غريب.

**إلزامي بأي قيد جديد على حساب موجود:** اسأل نفسك صراحة "هاد بيقلل الالتزام/يزيد الأصل، ولا العكس؟" — لا تنسخ عامل حسابي من قيد تاني بدون هالسؤال. **اختبار إلزامي فوري:** أنشئ التزام (فاتورة) ثم صفّره بالكامل (دفعة/خصم/مرتجع)، وتأكد الرصيد النهائي = **صفر بالضبط**. لو طلع "ضعف المتوقع"، هاد بالضبط توقيع الباگ.

## ٦. حسابات مخصصة لكل كيان — لا حساب مشترك أبداً

أي كيان (مورد/عميل/شركة شحن) له تتبّع مالي مستقل لازم **حساب فرعي مخصص خاص فيه** تحت الحساب الأب العام من أول يوم — مش حساب "ذمم العملاء" العام مباشرة لكل العملاء مع بعض (لو صار هيك بالغلط، رصيد كل عميل بمفرده **غير قابل للمعرفة** من شجرة الحسابات، بس المجموع الكلي). كود الحساب الفرعي يُبنى تلقائياً (`MAX(SUBSTRING_INDEX(code,'.',-1))+1` تحت نفس الأب) عبر migration بسيط، بس **برصيد صفر** (إعادة توزيع رصيد تاريخي متراكم قرار منفصل يحتاج مراجعة يدوية، مش أتمتة).

## ٧. ميزات مالية إضافية — أنماط جاهزة للنسخ

### أ) الشحن/تكلفة فرعية — كيان محاسبي مستقل تماماً
قيد GL منفصل بالكامل عن قيد استلام/بيع المستند. **مافي "رصيد معلّق" يُحسب مع رصيد المستند بنفس الصندوق** — بطاقتين منفصلتين بالواجهة، بدون أي دمج بصري أو حسابي.

### ب) حساب الدفع يتصفّى ديناميكياً حسب العملة
قائمة اختيار حساب الدفع (صندوق/بنك/دفعة مقدمة) **تتصفّى تلقائياً** حسب عملة الدفع المختارة (`data-cur` على كل `<option>`). حساب الدفعة المقدمة تحديداً: يُعرض بس لصاحب المستند المفتوح (لا كل الكيانات)، مع رصيده ظاهر وملوّن (أخضر موجب/أحمر سالب/أصفر صفر)، ومنع فعلي بالسيرفر لو الرصيد أقل من المطلوب. **تحكّم يدوي كامل** — بدون أي تطبيق تلقائي بالخلفية (خطر خصم مزدوج).

### ج) خصم تعجيل الدفع (Settlement Discount)
نسبة + شرط "قبل الاستحقاق" يُدخلا وقت الإنشاء. **الأهلية الفعلية تُتحقّق بالسيرفر حصراً** وقت التأكيد: تاريخ اليوم ≤ الاستحقاق **و** الدفعة كاملة (تغطي كامل المبلغ المخصوم — دفعة جزئية لا تفعّله إطلاقاً). قيد منفصل، بحساب "إيراد/خصم" مستقل عن أي خصم تجاري آخر (نوعان مختلفان محاسبياً: تفاوض سعر مقابل سرعة سداد).

### د) تسوية فروقات التقريب
تشيك بوكس اختياري بالواجهة (**مو تلقائي بصمت**)، بحد أقصى ثابت صغير (`≤0.01$`) — أي فرق أكبر ما ينسوّى حتى لو الخيار مفعّل، حماية من إخفاء خطأ حقيقي.

### هـ) مودال "تفاصيل التأكيد" — من القيود الفعلية، لا من تخمين
أي عرض "شو صار وقت التأكيد" (تاريخ، مبلغ، حالة) **يُبنى من استعلام حقيقي على `journal_entries` المرتبطة فعلياً** (`reference_id`) — مش من أعمدة المستند المفترضة. **تحذير صريح** (مو صامت) لو مجموع البنود المعروضة ما يطابق `total_amount` (**قبل** الخصم/الضريبة، لا `final_amount` بعدهم — هاي كانت غلطة مقارنة بحد ذاتها).

## ٨. التقارير — قراءة فقط، بعملة الفرع دايماً

- كل مبلغ مجمَّع عبر أكتر من مستند/عملة → حوّله لعملة الفرع الأساسية **أول ما تجمعه** (`SUM(final_amount_base_currency)`)، لا تجمع مبالغ خام بعملات مختلفة مع بعض أبداً (حتى لو التقرير بسيط).
- بطاقات إحصائيات فوق كل تقرير (نفس نمط باقي الصفحات)، وفلتر فترة زمنية موحَّد (افتراضي: آخر ٣٠ يوم).
- ترويسة طباعة مخصصة (`@media print`) بلوغو النظام + اسم الفرع + التاريخ، مخفية بالعرض العادي وتظهر بس عند `window.print()`.
- **تذكير الجدول المضغوط** (قسم ٢-ج فوق) — طبّقه على أي تقرير من أول بناء.

## ٩. الصلاحيات

- مفتاح صلاحية خاص بكل صفحة بجدول `modules` — لا تعتمد مفتاح صفحة تانية حتى لو الوظيفة مشابهة.
- الصفحات المشتركة بين قسمين: حدّد السياق **قبل** فحص الصلاحية، مش بعده.

---

## ١٠. القاعدة الذهبية العامة لأي قسم مالي جديد

**لا تحذف حدث مالي صار فعلياً أبداً.** الإلغاء = قيد عكسي جديد + تحديث حالة (الأصلي يضل موجود). المرتجع = مستند مستقل جديد (مش تعديل على مستند الإلغاء ولا الأصلي). حتى الجداول البسيطة لازم عمود `status` بدل `DELETE` فعلي — الاستثناء الوحيد: مسودة قبل التأكيد (ما أثّرت على شي فعلي بعد).

---

## ١١. Checklist نهائي — راجعها قبل التسليم، مش بعد ما يبلّغ المستخدم عن باگ

- [ ] عمود عملة/نص مجمَّد قديم بدل جوين حي عبر `_id`
- [ ] رمز عملة ثابت بالكود بدل قراءة ديناميكية
- [ ] `exchange_rate` مخزَّن من متغيّر وسيط بدل `original_amount ÷ base_amount` الفعلي
- [ ] اتجاه مدين/دائن منسوخ من قيد معاكس بدون عكسه — **اختبر بتصفير التزام كامل لصفر بالضبط**
- [ ] حساب مشترك لكل الكيانات بدل حساب فرعي مخصص لكل واحد
- [ ] الكمية بسطر متعدد المتغيّرات مطبَّقة على كل متغيّر بذاته بدل `quantity=1` لكل واحد
- [ ] سعر المرتجع من `unit_price` الخام بدل `total_price ÷ quantity` الصافي
- [ ] `parseFloat()` مباشر على تاريخ بمقارنات JS
- [ ] رابط نسبي (`require_once`/`fetch()`) ما تحدّث بعد نقل ملف أو حساب عدد `../` غلط
- [ ] enum بقاعدة البيانات ما يشمل قيمة جديدة (`reference_type` جديد) — تحقّق `SHOW CREATE TABLE` قبل الاستخدام لا بعده
- [ ] جدول تقارير بعدد صفوف قليل يبان مضغوطاً بدون `width:100%` صريح
- [ ] صفحة جديدة غير مسجَّلة بجدول `modules` — رابط الشريط الجانبي بيرجع `#`

---

*هذا الملف يجمع كل قرار فعلي اتُّخذ وكل باگ فعلي انصلح من قسمي المصاريف/المستهلكات والمشتريات الكاملين (فواتير، مرتجعات، تقارير) — ما فيه نظري. يُحدَّث كل ما يصير درس جديد يستاهل التعميم، ويُقرأ بالكامل قبل أول سطر كود بأي قسم مالي جديد.*
