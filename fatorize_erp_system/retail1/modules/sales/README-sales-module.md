# README — قسم المبيعات (Sales & CRM)

> يوثّق هالملف **الحالة النهائية الحالية** لقسم المبيعات بالكامل —
> بلا أي إشارة لمراحل التطوير أو التعديلات التاريخية. الهدف: مرجع
> تقني كامل لآلية عمل كل صفحة (باك-إند وفرونت-إند)، جاهز لأي محادثة
> جديدة تكمل الشغل على هالقسم.

**المسار الجذري:** `retail1/modules/sales/`
**واجهة الـAPI:** `retail1/api/confirm_sale_invoice.php`, `retail1/api/confirm_sale_return.php`

## ١. البنية المعمارية العامة

### ١.١ الجداول الأساسية (بلاحقة الفرع، مثلاً `_ret`)

| الجدول | الوظيفة |
|---|---|
| `sales_invoices_{suffix}` | رأس فاتورة البيع |
| `sales_invoice_items_{suffix}` | بنود الفاتورة (متغيّر واحد لكل صف) |
| `sales_returns_{suffix}` | رأس مرتجع البيع |
| `sales_return_items_{suffix}` | بنود المرتجع |
| `customers_{suffix}` | العملاء |
| `pricing_patterns_{suffix}` | أنماط تسعير العملاء (تصنيف بس حالياً) |
| `transport_carriers_{suffix}` | شركات النقلية |
| `shipping_carriers_{suffix}` | شركات الشحن |

### ١.٢ قرار العملة — "عملة الفرع مصدر الحقيقة الوحيد"

كل أعمدة المبالغ بمستوى **هيدر** الفاتورة/المرتجع (`total_amount`,
`discount_amount`, `tax_amount`, `final_amount`, `return_amount`...)
مخزَّنة **بعملة الفرع الأساسية مباشرة** —
`final_amount == final_amount_base_currency` دايماً بالضبط (نفس
القيمة، بلا أي اشتقاق). عملة المستند (`invoice_currency_id`) توثيقية
بس؛ أي قيمة بعملة المستند تُشتق وقت العرض فقط (`base × exchange_rate`).

**الاستثناء الوحيد** بمستوى **البند**: `unit_price`
(`sales_invoice_items`) مخزَّن فعلياً بعملة المستند، جنب
`unit_price_base_currency` بعملة الفرع. `total_price`/
`discount_amount` بمستوى البند بعملة الفرع، مطابقين للهيدر.

### ١.٣ نظام التسعير — "سعر تكلفة ثابت + سعر بيع حر + فارق ربح/خسارة"

- **سعر التكلفة** (`default_price`) — للقراءة فقط، من
  `product_sizes.cost_price` الحقيقي بالكتالوج. لا يتعدَّل عبر أي
  مسار (لا مودال اختيار، لا حقل مباشر).
- **سعر البيع** (`net_price`) — الحقل التحريري الوحيد، بعملة الفرع
  دايماً داخلياً. يقبل أي قيمة موجبة (حتى أقل من التكلفة — بيع
  بخسارة قرار تجاري صريح).
- **نسبة الفارق** = `(سعر البيع − سعر التكلفة) ÷ سعر التكلفة × 100`
  — موجبة = ربح، سالبة = خسارة. تُخزَّن بعمود `discount_percentage`
  (٤ خانات عشرية، `decimal(8,4)`).
- **قيمة الفارق** = `سعر التكلفة − سعر البيع` — عكس إشارة النسبة
  بالتصميم (سالبة = ربح). تُخزَّن بعمود `discount_amount`
  (`decimal(10,2)`، يقبل سالب).
- **عدد المنتجات** = `عدد الكروبات × عدد القطع بالباكيت`
  (`product_sizes.packet_qty`) — هي الكمية المستخدمة بحساب الإجمالي.
- **الإجمالي** = `عدد المنتجات × سعر البيع`.
- `quantity` المخزَّنة لكل متغيّر (مقاس) بمفرده بجدول البنود = عدد
  الكروبات فقط (بلا ضرب بـ`packet_qty`) — كل كروب = قطعة وحدة من كل
  مقاس بالكروب.

### ١.٤ التجميع البصري — `group_key`

أي مكان بالنظام بيجمّع مقاسات بنفس الكروب (جدول بحث، جدول بنود
الفاتورة، مودالات العرض) بيعتمد **حصراً** على `product_sizes.group_key`
(عمود مخزَّن فعلياً وقت إنشاء/تعديل المنتج) — **مو** مطابقة السعر أو
نوع العمر. القياسات تُعرض كمدى/قائمة (`٢ · ٣ · ٤ · ٥`)، واللون **نص
فقط بلا دائرة لونية** بكل مكان (جدول البنود، مودالات البحث، مودالات
التفاصيل/التأكيد).

**قرار عرض الألوان بالمودالات:** كل لون بصف مستقل (بلا دمج) بمودالي
تفاصيل الفاتورة وتأكيدها — المقاسات المختلفة بنفس اللون تندمج بنفس
الصف، بس الألوان المختلفة **ما تندمج**.

## ٢. فاتورة بيع جديدة — `invoice_new.php`

### ٢.١ بيانات الفاتورة

- **العميل**: حقل بحث مخصَّص (بديل عن `<select>` عادي) — يبحث بالاسم
  **أو برقم حساب الذمة/الدفعة المقدمة** (`customers.account_id`/
  `prepaid_account_id` عبر JOIN مع `account_charts`). قائمة نتائج
  منسدلة تفلتر حي وقت الكتابة.
- زر "+" جنب حقل العميل يفتح مودال إضافة عميل سريع (ينشئ حسابي ذمة
  ودفعة مقدمة تلقائياً).
- **نسبة الخصم العام** تتعبّى تلقائياً من `customers.discount_percentage`
  عند اختيار العميل، وتضل قابلة للتعديل يدوياً بهالفاتورة تحديداً.
- **عملة الفاتورة وسعر الصرف**: قائمة عملات + حقل سعر صرف يدوي
  (`1 عملة الفرع = س عملة الفاتورة`).

### ٢.٢ إضافة المنتجات

- **مسح الباركود**: إضافة فورية تلقائية (نمط سوبرماركت) — بلا مودال.
  موجود أصلاً بالفاتورة → +١ لعدد الكروبات. غير موجود → سطر جديد
  بكمية "١". باركود مشترك بين عدة مقاسات بنفس الكروب → يندمجوا
  تلقائياً.
- **البحث بالاسم/الموديل**: يفتح مودال اختيار متعدد؛ السعر المعروض
  بالمودال قابل للمراجعة/التعديل قبل الإضافة — القيمة المُعدَّلة
  تُطبَّق كـ**سعر بيع** (`sell_price_direct`)، **مش** سعر تكلفة (ثابت
  دايماً من الكتالوج).

### ٢.٣ جدول بنود الفاتورة — ترتيب الأعمدة النهائي

```
# | بيان المنتج | الموديل | القياس | [عدد القطع بالباكيت — مخفي] |
اللون | المتوفر بالمخزون | عدد الكروبات | [سعر التكلفة — مخفي] |
[سعر البيع بعملة الفرع — مخفي] | سعر البيع بعملة الفاتورة |
نسبة الفارق | عدد المنتجات | الإجمالي | إجراءات
```

- الأعمدة المخفية (`.hidden-col`) موجودة بالـDOM فعلياً (آلية الحفظ
  ما تغيّرت) — مخفية بصرياً بـCSS فقط.
- **"المتوفر بالمخزون"**: رقم واحد بس لكل صف = **أقل كمية متوفرة بين
  كل مقاسات الكروب بهالّون** (الباكيت الكامل محتاج قطعة من كل مقاس،
  فالمقاس الأقل مخزوناً هو الحاجز). مجلوب حياً من `warehouse_items`
  بمستودع الفاتورة المختار حالياً بالفورم.
- **"سعر البيع بعملة الفاتورة"**: الحقل التحريري الظاهر الوحيد للسعر
  — يعرض `net_price × exchange_rate`، ويتحدَّث فوري عند تغيير العملة
  أو سعر الصرف. الكتابة فيه تتحوَّل تلقائياً لعملة الفرع
  (`net_price = القيمة المكتوبة ÷ exchange_rate`) للحفظ الداخلي —
  آلية الحفظ بالباك-إند ما تغيّرت (لسا `net_price` بعملة الفرع).

### ٢.٤ التسلسل الحسابي (الملخص الجانبي)

```
المبلغ الصافي (بدون خصومات أو زيادات) = Σ(سعر التكلفة × عدد المنتجات)
مجموع قيمة الفوارق (سالب أو موجب)     = Σ(قيمة الفارق × عدد المنتجات)
المبلغ بعد الفوارق                    = الصافي − مجموع الفوارق
نسبة الخصم العام للعميل               [حقل %]
قيمة خصم تعجيل الدفع (معلوماتي بس)     = المبلغ بعد الفوارق × نسبة الخصم
المبلغ الصافي بعد الخصوم والفوارق      = بعد الفوارق × (1 − نسبة الخصم العام/100)
نسبة ضريبة المبيعات العامة            [من tax_rate_default بجدول الفروع]
قيمة الضريبة                          = الصافي بعد الخصوم × نسبة الضريبة/100
المبلغ الإجمالي                       = الصافي بعد الخصوم + قيمة الضريبة
```

### ٢.٥ الحفظ — `save_invoice`

1. **فحص كفاية المخزون إلزامي قبل أي إدراج** — لكل متغيّر بكل بند،
   الكمية المطلوبة تُقارَن بـ`warehouse_items.quantity` بمستودع
   الفاتورة المختار. أي نقص → رفض الحفظ بالكامل (بلا أي إدراج جزئي)
   برسالة توضح المنتج/المقاس/اللون والمتاح مقابل المطلوب.
2. الفاتورة تُحفظ **دايماً كمسودة** (`status='draft'`) — التأكيد من
   صفحة `sales_index.php` حصراً.
3. `quantity` لكل بند = عدد الكروبات (بلا ضرب بـ`packet_qty`).
   `unit_price` (عملة المستند) = `net_price × exchange_rate`.
   `unit_price_base_currency` = `net_price` مباشرة.
   `discount_amount`/`discount_percentage` = قيمة/نسبة الفارق (تقبل
   سالب).

## ٣. تعديل فاتورة بيع — `invoice_edit.php`

نفس بنية `invoice_new.php` حرفياً (جدول البنود، التسلسل الحسابي،
بحث العميل، فحص المخزون)، بفرق جوهري واحد:

**إعادة بناء البنود المحفوظة سابقاً** (`renderExistingLine`) — السعر
الافتراضي (`default_price`) لكل بند تاريخي **مُعاد بناؤه من القيم
المحفوظة فعلاً وقت الإنشاء الأصلي** (`unit_price_base_currency` +
`discount_percentage`)، **مو** من كتالوج المنتج الحي اليوم:

```
net_price = unit_price_base_currency (محفوظ)
default_price = net_price ÷ (1 + discount_percentage/100)
```

هيك، حتى لو تغيّرت تكلفة المنتج بالكتالوج منذ إنشاء الفاتورة، البند
المعروض بالتعديل بيعكس أرقام الفاتورة الأصلية بالضبط.

**قيد إضافي على التعديل**: مسموح بس للفواتير بحالة `draft` — أي محاولة
فتح فاتورة `confirmed`/`cancelled` للتعديل تُرفض (تحقق مكرَّر بمستوى
الصفحة ومعالج AJAX).

## ٤. سجل المبيعات — `sales_index.php`

### ٤.١ الجدول الرئيسي

- تلوين الصف الكامل حسب حالة الفاتورة/الدفع مجتمعتين
  (`invoiceRowStyle()`): مسودة=رمادي، مؤكدة+غير مدفوعة=أزرق،
  مؤكدة+جزئي=أصفر، مؤكدة+مدفوعة بالكامل=أخضر، ملغاة=أحمر.
- رقم الفاتورة قابل للنقر — يفتح مودال التفاصيل مباشرة.
- فلاتر: تاريخ، حالة، عميل، بحث نصي (رقم فاتورة/اسم عميل).

### ٤.٢ مودال تفاصيل الفاتورة (`viewInvoice`)

جدول بنود مُجمَّع حسب `group_key` **مع فصل الألوان** (كل لون صف
مستقل). أعمدة: المنتج، الموديل، الكروب/القياسات، اللون، المتوفر
بالمخزون (رقم واحد، أقل كمية بين المقاسات المدموجة)، عدد الكروبات،
سعر الوحدة (عملة الفاتورة)، الإجمالي (عملة الفاتورة)، التكلفة (عملة
الفرع، عمودين رمز عملة منفصلين — عملة المستند للسعر/الإجمالي، عملة
الفرع للتكلفة).

### ٤.٣ مودال تأكيد الفاتورة (`openConfirmModal` / `doConfirm`)

**جدول البنود**: نفس منطق مودال التفاصيل (فصل ألوان، مخزون، موديل).

**بيانات لوجستية (ربط توثيقي بحت — بلا أي مبلغ، بلا أي قيد محاسبي):**
- قائمة "شركة النقلية" (من `transport_carriers_{suffix}`، اختياري).
- قائمة "شركة الشحن" (من `shipping_carriers_{suffix}`، اختياري).
- تكلفة النقل/الشحن الفعلية **لا تُسجَّل هون إطلاقاً** — تُسجَّل
  كمصروف منفصل بصفحة المصاريف والمستهلكات.

**الجمارك (استثناء — بيانات فقط، بمبلغ):**
- تشيك بوكس "يوجد جمارك؟" → يفتح حقل "أجور الجمارك" (رقم، اختياري).
- **لا يُضاف لإجمالي الفاتورة إطلاقاً، ولا يُرحَّل أي قيد تلقائي** —
  يُحفظ بس كبيانات على صف الفاتورة (`has_customs`, `customs_cost`)،
  وتُسوَّى لاحقاً يدوياً من صفحات المقبوضات/المدفوعات العامة عبر
  حساب `customs_suspense` ("أمانات الجمارك") بجدول ربط الحسابات.

**لا يوجد أي تحصيل بهالمودال** (لا مبلغ مدفوع، لا حساب تحصيل، لا
تسوية فروقات تقريب) — كل فاتورة تتأكَّد بحالة `payment_status='pending'`
دايماً، والتحصيل (جزئي أو كامل) يصير حصراً لاحقاً من صفحة المقبوضات
العامة.

**بانر خصم تعجيل الدفع**: إعلامي بس (يعرض النسبة والموعد النهائي
والمبلغ بعد الخصم)، بلا أي زر تطبيق — بما إنه التحصيل خارج المودال
كلياً.

**حالة التسليم (`delivery_status`)**: عمود موجود بقاعدة البيانات
(افتراضي `draft`، ٨ حالات ممكنة)، بلا أي واجهة تغيير حالة مبنية بعد،
وبلا أي قيد محاسبي مرتبط فيه حالياً.

## ٥. تأكيد فاتورة البيع — `confirm_sale_invoice.php`

### ٥.١ عملية `confirm`

1. **فحص المخزون** لكل بند (نفس فحص الحفظ، مُكرَّر دفاعياً).
2. **خصم المخزون الفعلي** من `warehouse_items` + سجل
   `inventory_movements`/`inventory_movement_details`.
3. **حسابات الربط المحاسبي** — تفضيل حساب العميل الخاص
   (`customers.account_id`) لو موجود ونشط، وإلا الحساب العام
   (`customer_receivable` بإعدادات الربط).
4. **القيد الرئيسي** (`reference_type='sale'`): مدين ذمة العميل،
   دائن إيراد المبيعات — بعملة الفرع، `balance == base_balance`
   بالضبط للحسابين (غير نقديين).
5. **قيد COGS منفصل** (`reference_type='sale_cogs'`): مدين تكلفة
   البضاعة المباعة، دائن المخزون.
6. **حفظ البيانات اللوجستية**: `transport_carrier_id`,
   `shipping_carrier_id`, `has_customs`, `customs_cost` — تحديث
   مباشر على صف الفاتورة، **بلا أي قيد محاسبي**.
7. **تحديث حالة الفاتورة**: `status='confirmed'`, `paid_amount=0`,
   `balance_amount=final_amount`, `payment_status='pending'` دايماً.

### ٥.٢ عملية `cancel`

عكس القيد الرئيسي فقط (`journal_entry_id` المخزَّن على الفاتورة) —
إعادة المخزون لـ`warehouse_items`. القيود المنفصلة (لو وُجدت مستقبلاً
لشحن/نقلية) ما بتنعكس تلقائياً بهالمسار.

### ٥.٣ قاعدة عملة الهيدر بالقيود

أي عمود هيدر (`final_amount`, `tax_amount`, `discount_amount`) يُقرأ
**مباشرة** كعملة فرع؛ المكافئ بعملة المستند يُشتق **بالضرب**
(`× exchange_rate`)، أبداً بالقسمة.

## ٦. إدارة العملاء — `customers.php`

### ٦.١ نوع العميل

`ENUM('wholesale','retail','super_wholesale')` — جملة / مفرق / جملة
الجملة. شارات/أفاتار بألوان مختلفة لكل نوع بجدول القائمة.

### ٦.٢ نمط التسعير

حقل `pricing_pattern_id` (FK اختياري لـ`pricing_patterns_{suffix}`)
— **تصنيف/وسم بس حالياً**، بلا أي تأثير تلقائي على الأسعار. زر "+"
جنب الحقل يفتح مودال إضافة نمط جديد فوري (نفس نمط "إضافة فئة"
بالمنتجات) — الجدول فارغ افتراضياً، يُعبَّى من الواجهة تدريجياً.

### ٦.٣ حقول إضافية

`credit_limit` (حد الذمة)، `discount_percentage` (نسبة الخصم
الافتراضية — تتعبّى تلقائياً بفاتورة البيع الجديدة عند اختيار
العميل)، `notes`.

### ٦.٤ "المستحق" — مصدر الحقيقة

عمود "المستحق" (بمودال العرض وبجدول القائمة) = **رصيد حساب الذمة
الحي مباشرة** (`account_charts.base_balance` عبر `customers.account_id`)
— **مو** حساب منفصل من مجموع الفواتير غير المسدَّدة. هيك بيعكس
الرصيد الافتتاحي وأي قيد يدوي مباشر، مو الفواتير بس.

### ٦.٥ الحسابات المحاسبية

كل عميل جديد يُنشئ تلقائياً حسابي ذمة (`account_id`، أصل) ودفعة
مقدمة (`prepaid_account_id`، التزام) تحت الحسابات الأب المناسبة
بشجرة الحسابات.

## ٧. مرتجعات المبيعات — `returns.php` + `confirm_sale_return.php`

### ٧.١ نمط "الحساب المستهدف" (`target_account_type`)

`payment_handling` (`not_paid|partial|paid_full`) + `target_account_type`
(`cash|receivable|prepaid`) — الأخير إجباري لو `partial`/`paid_full`.

| `target_account_type` | السلوك | القيد الإضافي |
|---|---|---|
| `receivable` (افتراضي) | خصم من ذمة العميل | ولا واحد — القيد الرئيسي كافٍ |
| `cash` | استرداد نقدي فعلي | `sale_return_refund`: عكس تخفيض الذمة + دائن صندوق/بنك محدَّد |
| `prepaid` | تحويل لرصيد دائن | `sale_return_prepaid`: عكس تخفيض الذمة + دائن `customers.prepaid_account_id` |

### ٧.٢ جدول بنود المرتجع

نفس منطق `group_key` — دمج المقاسات (مدى)، اللون نص بلا دائرة.
السعر الصافي لكل بند = `total_price ÷ quantity` (يحترم أي خصم إفرادي
مطبَّق أصلاً بالفاتورة الأصلية).

### ٧.٣ القيود بالتأكيد (`confirm_sale_return.php`)

- **قيد رئيسي** (`sale_return`): مدين إيراد (تخفيض)، دائن ذمة العميل
  (تخفيض).
- **قيد COGS معكوس** (`sale_return_cogs`): مدين مخزون، دائن COGS.
- **قيد الحساب المستهدف** (لو `cash`/`prepaid`) — راجع الجدول أعلاه.
- المخزون يرجع لـ`warehouse_items` تلقائياً.

## ٨. تقارير المبيعات — `reports.php`

٦ تقارير: سجل المبيعات، الأكثر شراءً (عملاء)، الأكثر مبيعاً
(منتجات)، هامش الربح التقديري (COGS حي من `product_sizes.cost_price`)،
تقرير المرتجعات، حالة الدفع. كل المبالغ تُقرأ من أعمدة عملة الفرع
مباشرة (`final_amount_base_currency`, `return_amount`,
`balance_amount`) — بلا أي قسمة على `exchange_rate`.

## ٩. أوامر البيع — `orders.php`

**لسا ما تُبنى منطقياً** — صفحة كاملة التصميم (شريط جانبي + تبويبات
القسم)، بوضع صيانة (`maintenance mode`) بلا أي منطق عمل فعلي. بانتظار
قرار صريح حول الآلية المطلوبة (أوامر بيع مبدئية؟ عروض أسعار؟).

## ١٠. نقاط معلَّقة معروفة (لحظة كتابة هالملف)

1. **باگ مُبلَّغ عنه، غير محلول بعد**: مستخدم أبلغ إنه عمود "سعر
   البيع بعملة الفاتورة" ممكن يُحفظ بقيمة عملة الفرع كأنها عملة
   الفاتورة بحالات معيّنة — راجع منطق `exchange_rate`/`net_price_doc`
   بـ`invoice_new.php`/`invoice_edit.php` عند المتابعة؛ يحتاج مثال
   رقمي محدَّد أو لقطة شاشة لإعادة الإنتاج والتشخيص الدقيق.
2. **واجهة "حالة التسليم" غير مبنية**: عمود `delivery_status` (٨
   حالات) موجود بقاعدة البيانات، بلا أي واجهة تغيير حالة أو منطق
   قيود آلي مرتبط فيه. حسب التصميم المعتمَد (`READMElogistics.md`):
   قيد إلزامي واحد عند الانتقال لـ"شُحنت من المعمل" (لو فيه نقلية)،
   وقيد شرطي واحد عند "سُلّمت" (لو `shipping_cost > 0`) — باقي
   الحالات الوسيطة تسميات/تتبّع بصري بس، بلا قيد. القفز بين الحالات
   (تخطي حالات وسيطة) **مسموح ومقصود**، بلا أي أثر محاسبي إضافي.
3. **عمودا `transport_cost`/`shipping_cost`** موجودين بقاعدة
   البيانات (`sales_invoices`) لتوافق مستقبلي، بلا أي كود يكتب فيهم
   حالياً (أُلغيا من واجهة التأكيد بقرار صريح — التكلفة تُسجَّل
   كمصروف منفصل بصفحة المصاريف والمستهلكات).
