## ١. نظرة عامة

**FATORIZE** نظام ERP بالعربية بالكامل (RTL)، PHP خالص بدون إطار عمل،
MySQL/MariaDB، SaaS متعدد المستأجرين. كل شركة عميلة (tenant) عندها
قاعدة بيانات منفصلة تماماً، بنفس نسخة الكود المشتركة.

## ٢. التقنيات المستخدمة

| الطبقة | التقنية |
|---|---|
| الخادم | PHP (procedural، بدون إطار عمل) |
| قاعدة البيانات | MySQL/MariaDB عبر PDO (prepared statements حصراً) |
| الواجهة | HTML مُخرَج من PHP مباشرة، Bootstrap 5.3 RTL (CDN) |
| JavaScript | Vanilla JS، ملف مشترك واحد للشريط الجانبي (`assets/js/sidebar.js`) |
| الجلسات | PHP Sessions أصيلة — آلية الحالة/الصلاحيات الوحيدة |

## ٣. البنية متعددة المستأجرين (Multi-Tenant SaaS)

### ٣.١ النموذج
قاعدة بيانات منفصلة فعلياً لكل tenant، نفس نسخة الكود بالضبط لكل
العملاء، التمييز بين الشركات عبر الساب-دومين (`client1.fatorize.com`).

### ٣.٢ قاعدة الماستر (`fatorize_master`)
- جدول `tenants` — السجل المركزي (اسم الشركة، الساب-دومين، بيانات
  اتصال قاعدة بياناتها مشفَّرة AES-256-CBC)
- جدول `currencies` (بقاعدة الماستر) — قاموس عملات على **مستوى الشركة
  ككل**، منفصل تماماً عن جدول `currencies` بقاعدة كل tenant (راجع §٨
  للتمييز الكامل)
- `tenants.reporting_currency_id` — عملة التقارير الموحَّدة للشركة
  كاملة، تُحدَّد مرة وحدة وقت التسجيل وتتجمَّد نهائياً (Trigger حقيقي
  بقاعدة البيانات يرفض أي `UPDATE`)

### ٣.٣ تحليل الطلب (`config/tenant_resolver.php`)
كل طلب HTTP بيتحلّل الساب-دومين منه، بيتراجع لجدول `tenants`، بيفكّ
تشفير بيانات الاتصال، و`config/database.php::getConnection()` بيتصل
بقاعدة الشركة الصحيحة تلقائياً. باقي كل ملفات النظام بتستدعي
`getConnection()` بشكل عادي، بدون أي وعي بمنطق تعدد المستأجرين.

**⚠ قيد تقني حاسم:** `branches.base_currency_id` (بقاعدة الـtenant)
**مستحيل** يشاور مباشرة عبر `FOREIGN KEY` على `fatorize_master.currencies`
— MySQL ما بتسمح بـFK بين قاعدتي بيانات منفصلتين فيزيائياً. لهيك، جدول
`currencies` بقاعدة كل tenant **مستقل فعلياً**، وبيتزامن (Sync) من قائمة
عملات الماستر بإجراء صريح (زر "مزامنة العملات من الماستر"، أدمن فقط) —
مش مربوط مباشرة.

### ٣.٤ نشر الإنتاج
Wildcard SSL الحقيقي غير مدعوم على استضافة مشتركة (متاح VPS بس).
الحل المعتمد: كل tenant جديد ياخد ساب-دومين مُعرَّف صراحة بلوحة
الاستضافة (خيار "استخدام نفس مجلد الموقع الرئيسي")، فيصدر SSL تلقائياً.

## ٤. البنية متعددة الفروع (داخل كل Tenant)

### ٤.١ عزل البيانات
كل فروع نفس الشركة تتشارك قاعدة بيانات واحدة. العزل بلاحقة اسم الجدول
(`table_suffix`): `sales_invoices_ret`, `products_fac1`، إلخ. الجداول
العالمية (`branches`, `users`, `currencies`, `modules`, `internal_orders`...)
مشتركة بين كل فروع نفس الشركة، بدون لاحقة.

### ٤.٢ نوع الفرع
`branches.branch_type` — `ENUM('retail','factory')` مقيَّد. النوع
بيتحكّم بظهور/إخفاء قسم "الإنتاج" بالشريط الجانبي (حسب
`$_SESSION['branch_type']`)، وبالجداول الإضافية الحصرية وقت التوفير.

**⚠ قاعدة أساسية بأي فحص كود على نوع/هوية الفرع:** استخدم `branch_type`
أو `branch_id` من الجلسة **دايماً** — **أبداً** مقارنة نصية ثابتة على
`table_suffix` (زي `!== 'ret'`). هالخطأ بالذات صار **مرتين** بملفات
مختلفة (`sidebar.php`, `dashboard.php`) — أي فرع جديد بلاحقة مختلفة عن
القيمة المفترضة كان يترفض بالكامل.

### ٤.٣ الكود الفيزيائي — مجلد واحد مشترك
كل الفروع (بيع أو تصنيع) بتشارك **نفس مجلد الكود الفيزيائي**
(`modules/`) — اسم المجلد (`retail1/`) تسمية تاريخية بس، مو وصف دقيق.
الفرق بين الفروع بيصير بثلاث طبقات: البيانات (`$_SESSION['table_suffix']`
ديناميكي بكل استعلام)، ظهور القائمة (فلترة حسب `branch_type`)،
والصلاحيات (`user_permissions`). **مجلد جديد فيزيائي مبرَّر بس لقسم
جديد بالكامل وخاص حصراً بنوع فرع واحد** (`modules/production/`).

### ٤.٤ توفير فرع جديد — ديناميكي بالكامل

`config/create_branch_tables.php::createBranchTables($pdo, $suffix, $branchType)`
بتنفّذ الخطوات التالية تلقائياً:

1. **اكتشاف واستنساخ الجداول** — `SHOW TABLES LIKE '%\_ret'` (فرع البيع
   الأول = القالب المرجعي **الحي**)، `CREATE TABLE new LIKE old` لكل
   جدول (بنية، فهارس، `AUTO_INCREMENT` كاملة). **لا قائمة SQL ثابتة
   مكتوبة يدوياً** — أي عمود/جدول يُضاف لفرع البيع مستقبلاً بينعكس
   تلقائياً بأي فرع جديد.
2. **جداول حصرية بفروع `factory`** (لا قالب بفرع بيع، مكتوبة يدوياً
   بالضرورة): `raw_materials`, `raw_material_stock`,
   `production_operations`, `production_entries`, `manufacturing_bom`.
3. **بذرة دليل حسابات كاملة** (٤٤ حساب، ٤ مستويات) — بعملة الفرع
   الوظيفية الحقيقية المُختارة وقت الإنشاء (مو رقم ثابت). التسلسل
   الهرمي بيتحل ديناميكياً (parent-first resolution).
4. **بذرة الربط المحاسبي** (`invoice_account_settings`) — ٢٥ مفتاح
   (`sales_revenue`, `customer_receivable`, `cash_usd`... إلخ) محلولين
   تلقائياً لأكواد الحسابات المزروعة **بنفس الفرع الجديد**.
5. **فئات ووحدات مستهلكات افتراضية** + **مستودعين** (منتجات ومستهلكات).

**⚠ قيد معروف حالياً:** بذرة الحسابات (الخطوة ٣) بتزرع حسابات صندوق/بنك
**بعملة واحدة بس** (مطابقة لبيانات القالب المرجعي الأصلية وقت البناء) —
**مش ديناميكية حسب العملة المحلية الفعلية المُختارة** لكل فرع جديد.
لو الفرع الجديد عملته المحلية مختلفة، حساباتها ما بتتزرع تلقائياً —
تحتاج إضافة يدوية لاحقاً من `accounting/account_settings.php`.

### ٤.٥ إنشاء فرع جديد — واجهة إدارية

`admin/branch_add.php` (منفصلة عن `admin/branches.php` يلي هي **تعديل
فقط**): اختيار نوع الفرع، تحقق فوري من تفرّد `table_suffix`، **العملة
الوظيفية قابلة للاختيار هون فقط** (تتجمّد بعدها)، خيار "إنشاء الجداول
فوراً".

**عند إنشاء أي فرع جديد، تلقائياً:** المستخدم رقم `1` (مدير النظام)
بيتربط بالفرع الجديد (`user_branches`) وياخد **كل الصلاحيات السبعة على
كل الأقسام الموجودة فعلياً** بجدول `modules` وقت الإنشاء
(`user_permissions`) — بدون أي خطوة يدوية إضافية.

## ٦. قاعدة البيانات — مرجع كامل

### الجداول العالمية (بدون لاحقة فرع)

| الجدول | الغرض | أعمدة مهمة |
|---|---|---|
| `branches` | الفروع | `branch_type`، `base_currency`/`base_currency_id` (تتجمّد)، `local_currency`/`local_currency_id`، `table_suffix`، `costing_method`، `opening_balance_locked_at`/`_by` |
| `currencies` | عملات الـtenant (مستقلة عن عملات الماستر — راجع §٨) | `code`، `is_base`، `cash_account_id`/`bank_account_id` (رابط عرض بس) |
| `modules` | أقسام الشريط الجانبي وتدرجها | `key`/`parent_key`، `theme_color` (بس على الصفوف الأب) |
| `users`, `user_branches`, `user_permissions`, `user_activities`, `user_tab_order` | نظام المصادقة والصلاحيات (راجع §٩) | — |
| `shipping_carriers` | شركات الشحن | `account_id`/`payable_account_id` |
| `internal_orders`, `internal_order_items` | الطلبات الداخلية بين الفروع | `from_branch_id`/`to_branch_id`، `status` (٨ حالات) |

### المنتجات والمخزون (`_ret`)

| الجدول | الغرض | أعمدة مهمة |
|---|---|---|
| `products_ret` | الموديلات الأب | `model_number`، `category_id`، `fabric_type` — **`supplier_id` غير مُستخدَم من الواجهة العادية** (منتج واحد ما بينحصر بمورد واحد، قرار معماري صريح؛ العمود يبقى بالجدول لميزة مؤجَّلة) |
| `product_categories_ret`, `product_colors_ret` | فئات/ألوان (قواميس) | `product_colors` عام، مش لكل منتج |
| `product_sizes_ret` | مقاسات كل موديل — **مصدر السعر الحقيقي** | `selling_price`، `cost_price`، `packet_qty`، `sort_order`، **`group_key`** (مفتاح الكروب الحقيقي المخزَّن — راجع §١٢) |
| `product_variants_ret` | مقاس×لون = سطر (وحدة الباركود) | `size_id`/`color_id` (FK)، `barcode` (باركود رقمي ٩ خانات، **مشترك لكل كروب×لون**، مو فريد لكل صف) |
| `product_suppliers_ret` | الموردون | `account_id`/`prepaid_account_id` (حساب مخصص تلقائي)، `supplier_type` |
| `warehouses_ret` | المستودعات | `warehouse_type` (`products`/`consumables`/`raw_materials`) — **عمود لازم يكون موجود بأي جدول مستودعات، تحقق منه لو صار خطأ "Unknown column"** |
| `warehouse_items_ret` | رصيد كل Variant بكل مستودع | `current_cost` |
| `inventory_movements_ret`, `inventory_movement_details_ret` | حركات المخزون | `movement_type` (بما فيها `opening`) |

### المبيعات والمشتريات (`_ret`)

| الجدول | الغرض | أعمدة مهمة |
|---|---|---|
| `customers_ret` | العملاء | `account_id`/`prepaid_account_id` تلقائي |
| `sales_invoices_ret`, `purchases_ret` | فواتير | `final_amount`/`final_amount_base_currency` متطابقان دايماً |
| `sales_invoice_items_ret`, `purchase_items_ret` | بنود | `unit_price` (عملة المستند) مقابل `unit_price_base_currency` (عملة الفرع) — الاستثناء الوحيد لقاعدة "عملة الفرع بس" |
| `sales_returns_ret`, `purchase_returns_ret` + بنودهم | مرتجعات | ⚠️ `purchase_returns.status='posted'` (مش `'confirmed'`) — تصادم تسمية مع `purchases.status` |
| `purchase_payments_ret`, `purchase_payment_invoices_ret`, `receipt_invoices_ret` | سندات ودفعات | — |

### المحاسبة (`_ret`)

| الجدول | الغرض | أعمدة مهمة |
|---|---|---|
| `account_charts_ret` | شجرة الحسابات | `balance` (عملة الحساب) مقابل `base_balance` (عملة الفرع) — لازم يتحدّثوا سوا؛ `cash_flow_category`؛ **اتفاقية الإشارة: `debit` = دلتا موجبة، `credit` = دلتا سالبة على كلا العمودين، بشكل موحَّد بغض النظر عن نوع الحساب** (أصل/التزام/حقوق ملكية) — حسابات الالتزامات بتظهر بأرقام سالبة لما يكون فيها مبلغ مستحق |
| `invoice_account_settings_ret` | إعدادات الربط المحاسبي — **المصدر الحقيقي الوحيد** | `setting_key` فريد (`sales_revenue`, `cash_usd`, `bank_try`... نمط `cash_{code}`/`bank_{code}` لكل عملة) |
| `journal_entries_ret`, `journal_entry_items_ret` | القيود | `currency_id` (FK رقمي، **أبداً** نص `currency`) — تصادم اسم شائع لازم الانتباه له دايماً؛ `original_amount` منفصل عن `base_amount` (IAS 21) |
| `receipts_ret`, `expenses_ret`, `exchange_rates_ret`, `tax_types_ret` | — | — |

### المستهلكات، الموارد البشرية، النظام (`_ret`)

راجع الجداول الكاملة بقسم "Database Overview — retail1" بملف
`README-claude.md` (سجل تاريخي — البنية نفسها موصوفة هون بالمختصر
أعلاه شاملة كل الفئات).

### ⚠️ ملاحظات عابرة لكل الجداول

- **`_base`/`_base_currency` = عملة الفرع دايماً** — تسميتين تاريخيتين
  لنفس المفهوم، حسب متى اتضاف العمود (`_base_currency` أقدم،
  `_base` بعد جلسة رينيم `_usd`→`_base`).
- **جداول المرتجعات مستقلة عن "الإلغاء"** — الإلغاء بيعكس مستند
  موجود بقيد عكسي، المرتجع مستند جديد قائم بذاته.
- **حساب مخصص تلقائياً لكل كيان تجاري جديد** (عميل، مورد، موظف، شركة
  شحن) — لا حساب أب مشترك.

## ٨. نظام العملات — ثلاث طبقات منفصلة تماماً

| المستوى | الاسم | أين يُخزَّن | يُجمَّد؟ |
|---|---|---|---|
| **الشركة كاملة** | عملة التقارير | `fatorize_master.tenants.reporting_currency_id` | ✅ نهائياً (Trigger بقاعدة الماستر) |
| **كل فرع لحاله** | العملة الوظيفية (IAS 21) | `branches.base_currency`/`base_currency_id` (بقاعدة الـtenant) | ✅ نهائياً بعد الإنشاء |
| **كل فرع لحاله** | العملة المحلية (معاملات يومية) | `branches.local_currency`/`local_currency_id` | ❌ قابلة للتعديل عادي |

**جدولا `currencies` — مو نفس الشي بالاسم:**
- `fatorize_master.currencies` — قاموس عام على مستوى الشركة، **بدون
  أسعار صرف**، يُستخدم بس لعملة التقارير.
- `bayhas.currencies` (بقاعدة كل tenant) — القاموس **الحقيقي المُستخدَم
  فعلياً** بكل شاشات النظام (اختيار عملة فرع، فواتير، حسابات صندوق/بنك)
  — فيه أسعار صرف، `is_base`، روابط حسابات. **مستقل تماماً عن جدول
  الماستر** (قيد تقني: FK بين قاعدتين منفصلتين مستحيل)، ويتزامن منه
  بإجراء صريح بس (مش تلقائي، مش مباشر).

### القاعدة الذهبية على كل مستند مالي

كل مبلغ بمستوى رأس المستند = **عملة الفرع الوظيفية دايماً**. عملة
المستند المختارة (للعرض) توثيقية بس، تُشتق وقت العرض (`base × rate`).
الاستثناء الوحيد: `unit_price` بمستوى بند السطر (فاتورة بيع/شراء) —
زوج حقيقي (`unit_price` بعملة المستند + `unit_price_base_currency`).

**العملة دايماً `currency_id` (FK رقمي)** بجداول القيود والبنود، أبداً
عمود `currency` نصي حر — هالغلط بالذات (استخدام `currency` بدل
`currency_id`) صار **أكتر من مرة** بملفات مختلفة، تأكد بـ`SHOW COLUMNS`
مباشرة قبل أي كود جديد يلمس قيد محاسبي.

## ١٠. الشريط الجانبي والقوائم الديناميكية

القائمة كاملة مبنية من جدول `modules` (`key`/`parent_key`/`label`/
`icon`/`sort_order`/`is_active`/`theme_color`). `buildSidebarMenu()`
بتفلتر حسب صلاحية `view`. `includes/sidebar.php` بترتّب المجموعات،
تحدّد القسم النشط حسب `$currentModule`، وتحقن متغيّر CSS للون القسم.

**خريطة `moduleUrl()`** (بنفس الملف) — تحويل `module.key` → مسار ملف
فيزيائي.

### ⚠️ القاعدة الأهم: أي صفحة جديدة تحتاج ثلاث تسجيلات منفصلة

نسيان أي وحدة بيعطي عطل صامت مختلف — **هالنمط بالذات صار سبب أكتر بق
تكرر بالمشروع**:

| # | المكان | لو اننسي شو بيصير |
|---|---|---|
| ١ | صف بجدول `modules` | الصفحة ما بتظهر بالشريط إطلاقاً |
| ٢ | مدخل بخريطة `moduleUrl()` | الرابط بيطلع فاضي → "Index of /modules" أو رابط ميت |
| ٣ | `$currentModule = 'key';` جوا الصفحة | تشتغل، بس عنصرها بالشريط ما بيتفعّل |

**نمط الفحص السريع لأي صفحة جديدة ما بتفتح من الشريط:** تأكد أولاً من
الصف بـ`modules`، وبعدين **بالتحديد** من `moduleUrl()` — هاي أكتر
نقطة بينسى تحديثها لأنها مو بنفس ملف الصفحة الجديدة نفسها.

### الشريط الجانبي — منطق JS مشترك وحيد
`assets/js/sidebar.js` — ملف واحد، كل صفحة تستدعيه بسطر وحيد قبل
`</body>`. **لا نسخ محلي مكرَّر بأي صفحة.**

## ١٣. الأرصدة الافتتاحية (Opening Balances)

`admin/opening_balances.php` — آلية إدخال أول-مدة لأي فرع جديد، **٥
تبويبات**:

| التبويب | الآلية |
|---|---|
| مخزون المنتجات | صنف + مستودع + كمية (تكلفة تلقائية من `product_sizes.cost_price`، قابلة للتعديل) |
| مخزون المستهلكات | نفس المنطق |
| أرصدة العملاء | مبلغ لكل عميل (مدين → دلتا موجبة) |
| أرصدة الموردين | مبلغ لكل مورد (دائن → **دلتا سالبة**، مطابق لاتفاقية §٦) |
| **الصندوق والبنوك** | حسابات مسحوبة من `invoice_account_settings` (مفاتيح `cash_%`/`bank_%`) — المبلغ بعملة الحساب، يتحوّل تلقائياً بسعر الصرف المسجَّل لو مختلف عن عملة الفرع |

**المبدأ المحاسبي:** كل إدخال بيترحّل قيد حقيقي مقابل حساب مخصص
**"رصيد افتتاحي"** (equity، كود `3900`) — مو فاتورة وهمية.
`reference_type='opening_balance'` لكل قيد.

**آلية القفل:** مرحلة واحدة (إدخال حر)، وقفل يدوي نهائي من المدير
(`branches.opening_balance_locked_at`/`_by`) — بعده كل الحقول تتعطّل
بالواجهة **و**السيرفر يرفض أي تعديل صراحة.

## ١٤. استيراد المنتجات (Bulk Import)

`inventory/import_products.php` — رفع CSV → معاينة/تحقق (بدون كتابة
لقاعدة البيانات) → تأكيد الاستيراد الفعلي.

### أعمدة الملف
```
model_number,product_name,category,supplier,size,age_type,selling_price,cost_price,packet_qty,group_no,color,barcode,warehouse_code,quantity
```
**أسماء بديلة مقبولة تلقائياً:** `category_id`→`category`,
`supplier_id`/`supplie_id`→`supplier`, `warehouse`→`warehouse_code`,
`qty`→`quantity`.

### قواعد الحقول
- `model_number`, `product_name`, `size`, `selling_price` — إجبارية
- `category` — يقبل ID رقمي (خطأ لو غير موجود) أو اسم نصي (تحذير + إنشاء تلقائي لو جديد)
- `supplier` — يقبل ID أو اسم، **لا إنشاء تلقائي أبداً** (خطأ دايماً لو غير موجود — يُضاف يدوياً من `suppliers.php` أول) — استثناء واعٍ يخالف قرار `product_add.php` العادية (منتج واحد بمورد واحد بالاستيراد بس، بطلب صريح)
- `warehouse_code`/`quantity` — اختياريين مع بعض؛ الكمية بتمر بنفس منطق الأرصدة الافتتاحية بالضبط (قيد محاسبي حقيقي، تحترم حالة القفل)
- `group_no` — اختياري (راجع §١٥ لتفاصيل "الكروب")

### التحقق قبل الاستيراد
- تعارض سعر لنفس (موديل+مقاس) بأسطر مختلفة → خطأ صريح يمنع السطر (بدل فقدان صامت بسبب القيد الفريد `UNIQUE(product_id,size,age_type)`)
- ألوان بتهجئتين مختلفتين لنفس اللون (همزة/بدون همزة، ة/ه) → تتوحّد تلقائياً بمطابقة مُطبَّعة، وتظهر بالمعاينة كإشعار شفافية
- باركود مستخدَم لأكتر من كروب/لون مختلف بالغلط → خطأ (تكراره **ضمن** نفس الكروب واللون طبيعي ومقصود)
- **إزالة BOM تلقائية** — ملفات Excel أحياناً بتضيف BOM بأول الملف، بيكسر قراءة أول عمود بصمت لو ما انزال

## ١٥. "الكروب" — حقيقة مخزَّنة، مش مُستنتَجة (`group_key`)

مجموعة مقاسات لنفس المنتج بنفس السعر وعدد قطع الباكيت = "كروب واحد".
`product_sizes.group_key` (عمود مخزَّن فعلياً) هو **مصدر الحقيقة الوحيد**
لأي تجميع كروب بأي مكان بالنظام — مش إعادة استنتاج من تطابق
(`selling_price`+`age_type`) بكل ملف لحاله (طريقة قديمة هشة، بتفشل لو
نفس السعر تكرر لكروبين مختلفين، أو نفس اللون تكرر بكروبات مختلفة).

**الاستخدام الفعلي:**
- **إنشاء/تعديل منتج** (`product_add.php` → `includes/product_save_helper.php`):
  `saveProductSizes()` بتخزّن `group_key` مباشرة، `syncProductVariants()`
  بتقرأه (مش تعيد استنتاجه) لتوليد **باركود مشترك واحد لكل (كروب × لون)**.
- **الاستيراد** (`import_products.php`): `group_key` بيُشتق تلقائياً من
  (`selling_price`+`packet_qty`) إلا لو الملف زوّد عمود `group_no` صريح
  (لازم لو صادف كروبين بنفس المنتج عندهم نفس السعر بالضبط).
- **أي صفحة بيع/شراء بتعرض/تجمّع منتجات بكروبات** (بحث منتج، مودال
  اختيار) — لازم تضيف `s.group_key` لأي `SELECT` من `product_sizes`
  وتستخدمه كمفتاح تجميع مباشر، بدل إعادة الاستنتاج.

**باركود:** رقمي عشوائي **٩ خانات**، متحقَّق من تفرّده فعلياً بقاعدة
البيانات (مش صيغة نصية `{MODEL}-V{ID}`). **لا يُلمَس إطلاقاً** عند
تحديث متغيّر موجود مسبقاً — حفاظاً على أي ملصق مطبوع فعلياً.

## ١٦. القواعد الذهبية العابرة لكل الأقسام التجارية

1. **عملة الفرع بمستوى الرأس دايماً** (راجع §٨).
2. **دورة حياة موحَّدة:** مسودة → تأكيد (ملف `api/confirm_*.php`
   منفصل، معاملة واحدة تغلّف المخزون + القيد + الحالة) → مؤكَّد/ملغى.
3. **الإلغاء ≠ الحذف:** قيد عكسي حقيقي + تغيير حالة، أبداً `DELETE`
   فعلي يمحي قيد محاسبي.
4. **المرتجع مستقل عن الإلغاء:** مستند جديد قائم بذاته، بسعر التكلفة
   الأصلي، مو تعديل على المستند الأصلي.
5. **نمط "الحساب المستهدف"** (`target_account_type`): `cash`/
   `receivable أو supplier`/`prepaid أو advance` — الوجهة دايماً حساب
   موجود أصلاً، بلا حساب وسيط جديد.
6. **حساب مخصص تلقائياً لكل كيان تجاري جديد** — لا حساب أب مشترك.
7. **حسابات الدفع/القبض من `invoice_account_settings`**، أبداً تخمين
   بادئة كود.
8. **`postAccountBalance()`/`bumpAccountBalance()` مشتركة** — أي قيد
   بيرحّل فعلياً `balance`+`base_balance` بمكانه الصحيح (مدين=دلتا
   موجبة، دائن=دلتا سالبة، موحَّد بغض النظر عن نوع الحساب).

## ١٧. دروس تقنية متكررة — تستاهل فحص استباقي بأي كود جديد

هالأنماط صارت **أكتر من مرة** بملفات مختلفة عبر جلسات متعددة — أي كود
جديد يلمس نفس المناطق، افحصها استباقياً:

| النمط | التفصيل |
|---|---|
| `currency` نص بدل `currency_id` رقمي | بجداول القيود المحاسبية — تأكد بـ`SHOW COLUMNS` قبل أي `INSERT` جديد لقيد |
| مقارنة `table_suffix` حرفية بدل `branch_type` | (`!== 'ret'`) — أي فرع جديد بلاحقة مختلفة بينكسر |
| `moduleUrl()` ناسي مدخل جديد | صفحة جديدة بتظهر بالشريط بس ما بتفتح (رابط ميت) — **افحص هالخريطة بالتحديد**، مو بس صف `modules` |
| BOM بملفات CSV مُصدَّرة من Excel | بيكسر قراءة أول عمود بالهيدر بصمت — إزالته تلقائياً بأي أداة رفع ملف جديدة |
| أسماء أعمدة CSV متعددة لنفس الحقل | (`category`/`category_id`, `supplier`/`supplier_id`/`supplie_id`) — دعم أسماء بديلة بدل افتراض تسمية وحيدة |
| عمود جديد بجدول قالب (`_ret`) ما بينعكس على فروع قديمة | فروع اتنشأت **قبل** إضافة عمود جديد للقالب ما بتاخده تلقائياً (`createBranchTables()` بس بتنسخ البنية **وقت الإنشاء**) — أي عمود جديد مهم، فكّر بسكريبت تصحيح رجعي لفروع موجودة أصلاً |
| `opcache.validate_timestamps=0` (Laragon) | بيخدّم نسخة قديمة مُجمّعة من ملف حتى بعد تعديله فعلياً — أول شي يُفحص عند "الإصلاح ما بينعكس رغم الرفع" |
| نسخ فيزيائية مكرَّرة من نفس الملف على القرص | (Laragon بيقرأ من مسار مختلف عن يلي بتعدّل عليه) — نفس السبب أعلاه بالضبط أحياناً |

## ١٨. قيود وفجوات معروفة حالياً (Known Limitations — هيكلية/قاعدة بيانات)

- بذرة حسابات فرع جديد **ثابتة بعملة واحدة**، مش ديناميكية حسب العملة
  المحلية الفعلية المُختارة (راجع §٤.٤).
- لا تزامن تلقائي/مباشر بين `fatorize_master.currencies` وعملات كل
  tenant — بس زر مزامنة يدوي صريح (أدمن فقط).
- لا CSRF tokens على أي نموذج/AJAX بكل التطبيق.
- لا سجل تدقيق شامل — `user_activities` يسجّل دخول/خروج بس.
- لا إقفال فترة محاسبية فعلي.
- `branches.factory_branch_id`/`internal_orders.from_branch_id`/
  `to_branch_id` بلا `FOREIGN KEY` حقيقي — حذف فرع بيسيب مراجع يتيمة
  صامتة (يحتاج تصفير/فحص يدوي قبل أي حذف فرع).
- جداول HR الفرعية (`hr_attendance`, `hr_loans`, `hr_bonuses`...) بلا
  FK حقيقي على `hr_employees`.
