## ٠.٠ ✅ محسوم — قسم الإنتاج ينتمي لفرع تصنيع مستقل، مو retail1

كل الجداول والصفحات المبنية بهالمستند تنتمي لفرع تصنيع جديد **منفصل تماماً**
عن `retail1` (فرع بيع تجريبي، لاحقة `_ret`) يلي كنا نختبر عليه. الفرع الجديد:

|                                                                                                                  |                                                                                                                       |
| ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **الاسم**                                                                                                        | `factory1`                                                                                                            |
| **لاحقة الجداول**                                                                                                | `_fac` (اقتراح متوافق مع نمط `retail1`→`_ret` بمشروعك — قابل للتعديل لو تحدد غيره)                                    |
| **توفير الفرع فعلياً** (صف `branches` + توليد جداوله الأساسية عبر `create_branch_tables.php` + نسخ مجلد الوحدات) | **محادثة تانية مسؤولة عنه — خارج نطاق هالمحادثة**                                                                     |
| **نطاق هالمحادثة**                                                                                               | تجهيز ملفات قسم الإنتاج (والمواد الأولية) جاهزة بلاحقة `_fac` الصحيحة، لتُرفع بمجلد `factory1/` بمجرد ما الفرع يتوفّر |

**مواد أولية بُنيت مسبقاً بهالمحادثة (`raw_materials.php` وملحقاتها):** كود
PHP ما بيحتاج أي تعديل (ديناميكي بالكامل عبر `$_SESSION['table_suffix']`)؛
سكريبت الـSQL تحدَّث ليستخدم `_fac` بدل `_ret`.

**قسم المشتريات (شراء مواد أولية):** ⚠ خارج نطاق هالمحادثة أيضاً — محادثة
المشتريات مالكة `purchases/*.php`. تعليمات التسليم بملف منفصل
(`handoff_to_purchases_conversation.md`).

## ٠. المبادئ الحاكمة (مستنتجة من النقاش + قواعد المشروع العامة)

1. **فصل المخطط عن التنفيذ الفعلي** — "المسار" (Routing) قالب حي يتغيّر مع الوقت،
   لكن أي أمر إنتاج بياخد **لقطة (Snapshot)** منه وقت الإنشاء ويشتغل عليها
   باستقلالية تامة. تعديل القالب لاحقاً **لا يمس** أوامر شغالة.
2. **لا مرجع حي لأي قيمة تاريخية** — تسعيرة العامل/المقاول تُنسخ (snapshot) بلحظة
   التنفيذ الفعلي داخل سجل التنفيذ نفسه، مو تُقرأ حية من جدول العامل وقت
   التقرير — وإلا تغيير سعر مقاول اليوم بيغيّر تكلفة أوامر قديمة مكتملة بالغلط
   (نفس المبدأ المطبّق أصلاً على `exchange_rate` بالفواتير).
3. **أي تعديل مسار على أمر قيد التنفيذ = حدث موثّق، مو تعديل مباشر صامت**
   (`Production Change` بمصطلحك) — سبب + مستخدم + تاريخ + قبل/بعد.
4. **الكمية "الخارجة عن المسار الطبيعي"** — تصميم نهائي (بعد تكرار النقاش):
   - **Good** — تتقدّم عادي
   - **Rework** — ترجع تدور بالمسار (لمرحلة/محطة تُحدَّد وقت التسجيل). علامة
     اختيارية `بدون تكلفة إضافية` (لحالة "المقاول رجّعها مجاناً لأنه غلطه") —
     نفس آلية Rework بالضبط، بس بدون توليد قيد تكلفة جديد لما ترجع.
   - **Scrap** — تخرج نهائياً، قيد خسارة محاسبي فوري
   - **Accept (استخدام كما هو)** — القطعة فيها ملاحظة جودة بسيطة بس بتُحتسب
     Good عادي (تتقدّم بالمسار)، الملاحظة تُحفظ للتقارير بس
   - ⚠ **حُذفت فئة "Reject" المستقلة** — كانت بتحتاج سلسلة مرجعية (تتبّع
     "هاي الكمية شو صار فيها لاحقاً") لتفادي ازدواجية العد؛ استبدلناها
     بـ"سبب عيب + ديسبوزيشن مباشر" بمكان واحد (بند ١ تحت) — أبسط وبنفس القوة
5. **لا حذف لحدث صار فعلياً** — نفس القاعدة الذهبية العامة بالمشروع.
6. **تكلفة العمالة الداخلية ≠ دين حقيقي** — الموظف ماخد راتبه من `payroll.php` بغض النظر عن الإنتاج. أي "تكلفة قطعة" تُحمَّل على WIP من عمل داخلي بتقيد بحساب وسيط (Clearing) مو بحساب دفع فعلي، لتفادي تضخيم المصروف (راتب حقيقي + تكلفة وهمية مكررة).
7. **تكلفة القطعة الكاملة = مواد + عمالة خارجية (دين حقيقي) + عمالة داخلية (محمَّلة/وسيطة) + تكلفة غير مباشرة موزَّعة** — الأربعة كلهم يدخلوا WIP بنفس آلية القيد، بس الطرف الدائن يختلف حسب النوع.

## ٠.١ محطة العمل (Work Center) — توضيح العلاقة

```
المرحلة (خياطة)
   └── محطة عمل داخلية "خط خياطة ١"  → موظفين + تسعيرة معيارية للتكلفة
   └── محطة عمل داخلية "خط خياطة ٢"  → موظفين + تسعيرة معيارية للتكلفة
   └── محطة عمل خارجية "شركة ABC"    → مقاول + تسعيرته الفعلية
```

بدون تخطيط طاقة استيعابية (لا جدولة، لا حدود ساعات/يوم) بهالنسخة — بس تصنيف/تجميع، يسمح لاحقاً بإضافة الجدولة بدون كسر أي شي موجود.

**توضيح مهم:** "الكمية عند المقاول الخارجي بانتظار الرد" **ما بتحتاج جدول
منفصل** — هي فعلياً بس كمية قاعدة بدفتر الكمية الحي (بند ٢) عند محطة عمل
نوعها `خارجية`. إرسال الكمية للمقاول = حركة عادية (نقل مرحلة/محطة لمحطة
المقاول، بدون نتيجة بعد). استلامها منه = التنفيذ يلي بيسجّل النتيجة
(سليم/Rework/Scrap + التكلفة). نفس آلية النقل اليدوي العادية، بدون كيان
جديد.

## ٢. طبقة التشغيل (Transactional — يومي)

| الكيان                                                      | الوصف                                                                                                                                                                                                                                         |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **أمر الإنتاج (Production Order)**                          | موديل + كمية إجمالية + **نسخة المسار المستخدمة وقت الإنشاء** + حالة (تحت)                                                                                                                                                                     |
| **لقطة مسار الأمر (Order Routing Snapshot)**                | نسخة مستقلة تماماً من مراحل القالب، مملوكة للأمر نفسه فقط                                                                                                                                                                                     |
| **تعديل مسار أمر قائم (Change Routing)**                    | حدث موثّق منفصل: أي مرحلة اتضافت/اتشالت/اترتبت، السبب، المستخدم، التاريخ — **ممنوع** لو الأمر `مكتمل`/`ملغى`                                                                                                                                  |
| **دفتر الكمية الحي لكل مرحلة**                              | "شو قاعد هلق بكل مرحلة" — بيسمح بالتقسيم الجزئي (جزء بمرحلة ٣، جزء بمرحلة ١)                                                                                                                                                                  |
| **سجل تنفيذ المراحل (Stage Execution)**                     | كل تنفيذ فعلي: من مرحلة/محطة عمل لمرحلة/محطة عمل، **كمية داخلة + كمية Good + كمية Rework**، مين نفّذ، تسعيرته **المنسوخة وقتها**، التكلفة المحسوبة                                                                                            |
| **نتائج الجودة (Quality Results / أسباب العيوب)** ✅ محدَّث | جدول حقيقي (مو enum)، مربوط بكل تنفيذ: سبب العيب (تمزق، مقاس خاطئ...) + كمية + شدة + **ديسبوزيشن مباشر واحد**: `Rework` (بتكلفة أو بعلامة `بدون تكلفة إضافية`) / `Scrap` / `Accept`. لا حالة "بانتظار قرار" وسيطة — القرار يُتخذ لحظة التسجيل |
| **المواد الفعلية المستهلكة بالتنفيذ**                       | ما استُهلك **فعلياً** بهاي المرحلة (يختلف عن "المخطَّط" بالقالب) — بيولّد حركة `raw_material_movements` (`production_out`) **+ قيد محاسبي مرافق: مدين WIP / دائن مخزون المواد الأولية** ✅ فجوة كانت ناقصة، انضافت                            |
| **قيد الخسارة (Scrap)**                                     | تلقائي لحظة تسجيل ديسبوزيشن Scrap: مدين "خسارة إنتاج"، دائن "منتج تحت التصنيع" — بقيمة نصيبها من التكلفة المتراكمة لحد هاي المرحلة                                                                                                            |
| **قيد WIP لكل تنفيذ مقاول خارجي**                           | مدين "منتج تحت التصنيع" (أصل)، دائن حساب المقاول المخصص (دين حقيقي)                                                                                                                                                                           |
| **قيد WIP لكل تنفيذ داخلي (موظف)** ✅ جديد                  | مدين "منتج تحت التصنيع"، دائن **"عمالة داخلية مُحمَّلة"** (حساب وسيط Clearing — مو دين حقيقي، الموظف ماخد راتبه من الرواتب أصلاً). المطابقة بين هالحساب ومصروف الرواتب الفعلي = مرحلة لاحقة منفصلة، غير مبنية الآن.                           |
| **قيد التكلفة غير المباشرة المخصَّصة (Overhead)** ✅ جديد   | لكل تنفيذ: مدين WIP / دائن حساب مجمّع التكلفة، بقيمة محسوبة حسب طريقة توزيعه (تسعيرة ثابتة أو % من العمالة المباشرة لهاي المرحلة)                                                                                                             |
| **إغلاق الأمر (Completion)**                                | لما الكمية الصافية (الإجمالي - كل الـScrap المتراكم) توصل آخر مرحلة بالكامل: مدين "مخزون منتج جاهز"، دائن "منتج تحت التصنيع" بكامل التكلفة، + زيادة فعلية برصيد المنتج                                                                        |
| **مصير الإغلاق/الإلغاء (Order Disposition)** ✅ جديد        | سجل قرارات إغلاق أمر متوقف: إرجاع مواد / نقل WIP لأمر تاني / Scrap / خسارة إنتاج مستقلة — تفصيل كامل ببند ٥.١                                                                                                                                 |

## ٣. آلة حالات أمر الإنتاج

```
مسودة (Draft) ──► مُعتمَد (Released) ──► تحت التنفيذ (In Production) ──► مكتمل (Completed)
     │                    │                        │
     └────────────────────┴────────────────────────┴──► ملغى (Cancelled)
                                                          عبر معالج "إغلاق/إلغاء" (بند ٥.١) — ليس زر مباشر
```

| الحالة          | تعديل المسار                                                                            | تسجيل تنفيذ جديد                                        |
| --------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **مسودة**       | حر ومباشر (لسا ما بدأ فعلياً، ما في حدث "Change" موثّق لأنه ما في شي يتغيّر عليه أصلاً) | ممنوع                                                   |
| **مُعتمَد**     | يُفضَّل التثبيت (تحذير لا منع صارم — نقطة مفتوحة ٥.٤)                                   | ممنوع لحد أول تنفيذ (عندها تلقائياً تصير `تحت التنفيذ`) |
| **تحت التنفيذ** | **ممنوع مباشرة** — فقط عبر `Change Routing` موثّق                                       | مسموح، هو صلب الصفحة اليومية                            |
| **مكتمل**       | ممنوع نهائياً                                                                           | ممنوع نهائياً                                           |
| **ملغى**        | ممنوع                                                                                   | ممنوع                                                   |

## ٥. نقاط لسا مفتوحة (لازم نحسمها قبل البناء)

### ٥.١ ✅ محسوم — إغلاق/إلغاء أمر الإنتاج (Cancel ≠ Scrap تلقائي)

**قرار نهائي:** "الإلغاء" مو زر بسيط ولا مرادف لـ"خسارة تلقائية". هو **إجراء
معالج (wizard)** مستقل اسمه "إغلاق/إلغاء أمر الإنتاج" — لما يُفعَّل، النظام
يفحص أول شي الوضع الفعلي للأمر:

- في تكاليف مسجَّلة فعلياً؟ (تسعيرة موردي الخدمةاتقيّدت بحسابهم)
- في مواد مصروفة فعلياً؟
- في كمية WIP عالقة (بأي مرحلة)؟
- في كمية سليمة (Good) خلصت فعلاً؟
- في كمية Scrap مسجَّلة مسبقاً؟

وبعدين **يطلب من المستخدم يحدد مصير كل رصيد متبقي**، مو يقرر تلقائياً:

| الخيار                                  | الأثر                                                                                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **إرجاع مواد**                          | مواد اتصرفت بالتنفيذ بس فعلياً رجعت سليمة → حركة عكسية بجدول حركات المواد الأولية (رصيدها يرجع)                                                        |
| **نقل WIP لأمر تاني**                   | الكمية العالقة (وتكلفتها المتراكمة) تنتقل لأمر إنتاج قائم تاني، مو تضيع                                                                                |
| **تسجيل Scrap**                         | خسارة فعلية حقيقية → نفس قيد الـScrap العادي (بند ٢)                                                                                                   |
| **إثبات خسارة إنتاج (Production Loss)** | تكلفة اتصرفت فعلياً (مثلاً فصالة اتدفعلها) بس ما في قطعة مادية مقابلها تتسجل كـScrap — قيد خسارة مستقل، مختلف عن Scrap لأنه مو مرتبط بكمية مادية محددة |

**القاعدة الذهبية المطبَّقة هون تحديداً:** الإلغاء يوقف الأمر عن قبول تسجيلات
جديدة، **بس ما بيمحي ولا يعدّل أي قيد قديم** — كل قرار من الأربعة فوق
بيولّد **قيد/حركة جديدة مستقلة**، مو تعديل على شي موجود. المبلغ المستحق
لأي مقاول اشتغل فعلاً **يضل مستحق** بغض النظر عن مصير الأمر — الإلغاء ما
بيلغي دين حقيقي.

**كيان جديد لازم ينضاف للطبقة التشغيلية:** `production_order_dispositions`
(أو تسمية مشابهة) — سجل كل قرار مصير اتخذ وقت الإغلاق: النوع (إرجاع
مواد/نقل WIP/Scrap/خسارة)، الكمية، الوجهة (لو نقل WIP، أي أمر استلمها)،
السبب، مين نفّذ، تاريخه، ومرجع القيد المحاسبي المرتبط.

### ٥.٢ ✅ محسوم — صلاحية Scrap منفصلة

تسجيل Scrap (خسارة فعلية بقيد محاسبي) يحتاج **صلاحية اعتماد مستقلة**
(زي `can_confirm` المستخدمة بتأكيد الفواتير)، منفصلة عن صلاحية تسجيل
التنفيذ العادي (`production.board:execute` مثلاً مقابل
`production.board:confirm_scrap`). نفس المنطق ينطبق على "إثبات خسارة
إنتاج" بمعالج الإغلاق (بند ٥.١) — كلاهما قيد خسارة حقيقي.

### ٥.٣ ✅ محسوم — Reject حُذفت، استُبدلت بـ"سبب عيب + ديسبوزيشن مباشر"

راجع بند ٠.٤ و١ فوق — Rework (بعلامة اختيارية "بدون تكلفة إضافية" لحالة
المقاول اللي يرجّعها مجاناً) / Scrap / Accept، بديسبوزيشن واحد مباشر
لحظة الاكتشاف، بدون سلسلة مرجعية معقّدة ولا حالة "بانتظار قرار" وسيطة.

### ٥.٥ ✅ محسوم — لا BOM مستقل

مواد كل مرحلة + تكلفتها المعيارية تعيش جوا تعريف مرحلة المسار نفسها،
وتُنسخ مع لقطة المسار وقت إنشاء الأمر. كافي لتغطية الهدف (ثبات تاريخي)
بدون بنية إضافية.

### ٥.٦ ✅ محسوم (افتراض مبسَّط) — الفرق بين `مُعتمَد` و`مسودة`

**القرار الافتراضي:** `مُعتمَد` = قفل المسار بس، بدون خطوة موافقة/فحص
إضافية بهالنسخة (نفس مستوى البساطة المعتمد بباقي فواتير النظام: مسودة→
تأكيد بدون طبقة موافقة وسيطة). لو ظهرت حاجة فعلية لخطوة فحص/استلام
رسمية قبل البدء لاحقاً، بتنضاف كحالة جديدة بالآلة بدون ما تكسر الموجود.

## الملحق ب — تصميم المواد الأولية لمعامل الخياطة (توثيق، لسا مو SQL)

> نتيجة جلسة نقاش مخصصة لطبيعة مواد الخياطة (قماش، خيوط، سحابات، أزرار،
> تغليف). كل ما يلي **تعديلات على جداول المواد الأولية المبنية أصلاً**
> (`raw_*_alpfac`) — لسا ما نُفّذ شي منها.

### ب.١ القرارات المحسومة

| القرار                        | التفاصيل                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **القماش بالرول**             | تتبّع لكل رول/دفعة (متراجه + دفعة صباغته + تكلفته الفعلية). خاصية "أسلوب التتبّع" بالفئة (`none`/`lot`) — فئة الأقمشة `lot`، الأزرار `none`  |
| **الألوان: عائلة مادة**       | مواد بألوان مختلفة بتنتمي لـ"عائلة" (مثال: دنيم ١٢ أونص). المخزون والتكلفة والرولات تبقى **لكل مادة ملوّنة على حدة**؛ العائلة بس لربط المسار |
| **سطر المسار يتبع لون الأمر** | سطر مواد المسار إما `ثابت` (مادة محددة، مثل إتيكيت أبيض) أو `يتبع لون الأمر` (يشاور على عائلة)                                               |
| **استهلاك القماش**            | من **مخطط القص** (طول المخطط × الطبقات)، مو رقم قياسي للقطعة                                                                                 |
| **استهلاك غير القماش**        | رقم واحد قياسي لكل موديل (لكل قطعة) + نسبة هدر                                                                                               |
| **الوحدات**                   | وحدة شراء (رول/كون/جروس) ← وحدة مخزون (متر/كغ/قطعة) بمعامل تحويل. التكلفة دايماً لوحدة المخزون                                               |
| **تكلفة المواد**              | `lot` = تكلفة الرول الفعلية (specific identification). غير `lot` = `current_cost` حسب `branches.costing_method`                              |

### ب.٢ تعديلات جداول المواد الأولية (مقترحة)

**جداول جديدة:**

```
raw_material_families_fac   (id, name, is_active)
raw_material_lots_fac       (id, raw_material_id FK, lot_no VARCHAR(50), dye_lot VARCHAR(50) NULL,
                             warehouse_id FK, received_qty DECIMAL(14,3), remaining_qty DECIMAL(14,3),
                             unit_cost DECIMAL(14,4), supplier_id NULL, purchase_item_id NULL,
                             received_at, is_active)   UNIQUE(raw_material_id, lot_no)
```

**جدول الألوان:** ⚠ لا ننشئ `raw_material_colors` قبل ما نتحقق كيف ألوان المنتجات مخزّنة بالنظام (جدول موجود؟). الأفضل نعيد استخدام نفس جدول الألوان، عشان "لون أمر الإنتاج" و"لون المادة" يتطابقوا مباشرة.

**أعمدة جديدة:**

```
raw_material_categories_fac  + tracking_mode ENUM('none','lot') DEFAULT 'none'
raw_materials_fac            + family_id INT NULL FK, color_id INT NULL FK,
                               purchase_unit_id INT NULL FK→raw_material_units,
                               purchase_to_stock_factor DECIMAL(14,4) DEFAULT 1,
                               width_cm DECIMAL(8,2) NULL,        (للأقمشة)
```

**قاعدة توازن:** لمواد `lot`، مجموع `remaining_qty` للرولات = `raw_material_stock.quantity` (يصلح لتقرير مطابقة لاحقاً، نفس فكرة `warehouse_items` مقابل `inventory_movements`).

### ب.٣ أسطر مواد المسار (تعديل على أ.١)

```
production_route_version_stage_materials_fac
  + raw_material_id  INT NULL   (مادة محددة = سطر ثابت)
  + family_id        INT NULL   (عائلة = يتبع لون الأمر)      -- واحد بس من الاثنين
  + consumption_basis ENUM('per_piece','cutting_marker') DEFAULT 'per_piece'
  + waste_pct_override DECIMAL(6,2) NULL
```

**عند إنشاء أمر الإنتاج (لونه معروف):** لقطة المسار (`production_order_stage_materials_fac`) **بتخزّن المادة الفعلية المحلولة** — سطر العائلة بيتحوّل لمادة اللون المطلوب. لو ما في مادة بهاللون ضمن العائلة، الأمر ما بيتعتمد (Released) وبتظهر رسالة صريحة.

### ب.٤ مرحلة القص (`stage_type = 'cutting'`)

القص مرحلة إلها نموذج خاص، بياخد مكان "التنفيذ العادي":

```
production_cutting_markers_fac       (id, execution_id FK, marker_no, marker_length_m DECIMAL(8,3),
                                      fabric_width_cm DECIMAL(8,2), layers INT,
                                      end_allowance_cm DECIMAL(6,2) DEFAULT 0, notes)
production_cutting_marker_sizes_fac  (id, marker_id FK, size_ref, ratio INT)
      -- القطع لكل مقاس = layers × ratio
production_stage_execution_materials_fac  + lot_id INT NULL FK, + returned_qty DECIMAL(14,3) DEFAULT 0
      -- الصافي المستهلك = actual_quantity − returned_qty ، والتكلفة = الصافي × تكلفة الرول
```

- **الاستهلاك المخطَّط للقماش** = طول المخطط × الطبقات (+ سماح نهاية لكل طبقة).
- **الاستهلاك الفعلي** = أمتار الرولات المصروفة − باقي الرول المرتجع.
- **تحقق عرض القماش:** عرض الرول لازم يطابق عرض المخطط (تحذير).
- **تحذير دفعات الصباغة:** خلط دفعات مختلفة بأمر قص واحد.
- **الباقي الصالح** بيرجع لنفس الرول (`remaining_qty`)، وغير الصالح بمسار Scrap (قيد خسارة إنتاج بصلاحية اعتماد منفصلة).

### ب.٥ تأثيرات على شغل تاني

| المكان                               | التأثير                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `raw_materials.php` (الصفحة المبنية) | إضافة: عائلة، لون، وحدة شراء + معامل، عرض، هدر، عرض الرولات لمواد `lot`                                       |
| محادثة المشتريات                     | فاتورة استلام قماش لازم تدخّل **سطر لكل رول** (تفصيل بملف التسليم المحدَّث) + تحويل وحدة الشراء لوحدة المخزون |
| مخزون المواد (`raw_material_stock`)  | يبقى رصيد مخزَّن لكل مستودع (Cached)؛ الرولات هي التفصيل                                                      |

### ب.٦ نقاط لسا مفتوحة

1. **جدول ألوان المنتجات:** هل موجود؟ (استعلام تحقق: `SHOW TABLES LIKE '%color%'`) — يحدد إعادة الاستخدام.
2. ✅ **محسوم (ب.٧):** أمر لكل (موديل × لون)، والكمية تُتبَّع لكل مقاس على حدة.
3. **تقدير القماش قبل ما يتعمل مخطط القص** (لتخطيط الشراء/الصرف): رقم قياسي تقديري اختياري مقابل الانتظار للمخطط.
4. **إدخال الرولات جماعياً** بفاتورة الشراء (لصق/استيراد) بدل سطر بسطر.
5. **قرارين لسا معلّقين من قبل:** إعادة تسمية `last_cost` → `current_cost`، وفصل `movement_type` لـ`in/out` + `reference_type`.

### ب.٧ ✅ محسوم — بُعد المقاس: أمر لكل (موديل × لون)، وتتبّع الكمية لكل مقاس

**الوحدة الأساسية للكمية = المتغيّر (`variant`: مقاس × لون)**، مو الرقم الإجمالي. هيك بتتطابق كمية الإنتاج مباشرة مع `warehouse_items`/`inventory_movements` لما الأمر يكتمل (نفس الوحدة اللي بيتخزّن فيها المنتج الجاهز).
⚠ التسمية الفعلية للجدول والأعمدة (`product_variants_...`) لسا لازم تتأكد من قاعدة البيانات قبل التنفيذ — راجع ب.٩.

**التعديلات على الملحق أ** (كلها لسا توثيق):

| الجدول (الملحق أ)                                   | التعديل                                                                                                                                                                    |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `production_orders_fac` (أ.٢)                       | `total_quantity` تصير **مجموع محسوب** من أسطر الأمر (مو مصدر حقيقة). يُضاف جدول `production_order_lines_fac`                                                               |
| **جديد** `production_order_lines_fac`               | `id · order_id FK · variant_id FK · planned_qty DECIMAL(14,3)` — الكمية المخطَّطة لكل مقاس. عند إنشاء الأمر بتختار الموديل واللون، فالنظام بيعرض مقاسات ذاك اللون تلقائياً |
| `production_order_stage_qty_fac` (دفتر الكمية الحي) | يُضاف `variant_id`، والمفتاح الفريد صار `(order_id, stage_id, work_center_id, variant_id)`                                                                                 |
| `production_stage_executions_fac` (أ.٣)             | الأعمدة `input_qty/good_qty/rework_qty` تنتقل لجدول أسطر جديد (تحت). الرأس بيحتفظ بمجاميع مخزَّنة للعرض السريع فقط                                                         |
| **جديد** `production_stage_execution_lines_fac`     | `id · execution_id FK · variant_id FK · input_qty · good_qty · rework_qty` — التحقق الرياضي (`input = good + rework + scrap + accept`) بيصير **لكل مقاس**                  |
| `production_quality_results_fac`                    | يُضاف `variant_id` (العيب مرتبط بمقاس معيّن)                                                                                                                               |
| `production_order_dispositions_fac` (أ.٤)           | يُضاف `variant_id NULL` (قرار الإغلاق ممكن يكون لمقاس بعينه)                                                                                                               |
| `production_cutting_marker_sizes_fac` (ب.٤)         | `size_ref` تصير `variant_id` (لون الأمر ثابت، فالمقاس بيحدد المتغيّر)                                                                                                      |

**أثر على الإتمام:** لما الأمر يكتمل، بيزيد `warehouse_items` بالكمية الجاهزة **لكل متغيّر**، وبيكتب سجل حركة `inventory_movements` (نوع `in`، `reference_type = production`) لكل متغيّر.

**أثر على واجهة اللوحة اليومية:** تسجيل أي نقلة/تنفيذ بيصير عبر **شبكة مقاسات** (مقاس ← كمية) بدل رقم واحد، مع خيار "نفس الكمية لكل المقاسات" للنقلات الكاملة.

### ب.٨ ⚠ قرار مقترح (لسا ما انحسم): التكلفة لكل مقاس

الأمر بيراكم التكلفة كتلة وحدة (مواد + عمالة + تكلفة غير مباشرة)، لكن المقاسات بتختلف باستهلاك القماش. **اقتراحي للنسخة الأولى:** تكلفة القطعة = تكلفة الأمر الإجمالية ÷ عدد القطع الجاهزة (متوسط لكل الأمر)، مع ترك مجال لتوزيع مرجَّح بعامل استهلاك كل مقاس لاحقاً (مخطط القص أصلاً بيعطينا نسب المقاسات). التوزيع المرجَّح أدق بس بيحتاج عامل استهلاك لكل مقاس مخزَّن — نأجّله.

### ب.٩ ✅ محسوم — أسماء الحقول الحقيقية (تحقّق من قاعدة البيانات الفعلية)

```
product_variants_{TS}   (id, product_id FK, size_id FK, color_id FK NULL, barcode, is_active, ...)
product_colors_{TS}     (id, name, hex_code, is_active, ...)   -- id INT UNSIGNED
```

**قرارات نهائية:**

- كل مكان بالملحقين أ وب مكتوب فيه `variant_id` ⇐ FK حقيقي على `product_variants_{TS}(id)`.
- **لا جدول ألوان جديد** — `raw_materials_fac.color_id` (ب.٢) FK مباشر على `product_colors_{TS}(id)` **نفسه**، إعادة استخدام كاملة. نفس الشي لأي مكان ذكرنا فيه "لون" بمواد أولية.
- ⚠ **ملاحظة نوع بيانات:** `product_colors.id` هو `INT UNSIGNED`، بينما بقية مفاتيحنا (`raw_materials.id` وغيرها) `INT` عادي (بدون UNSIGNED). أي عمود `color_id` بجداولنا لازم يكون `INT UNSIGNED` بالضبط ليطابق النوع المرجعي، وإلا الـFOREIGN KEY بيرفض بخطأ نوع.
- تأكّد `product_variants.id` نوعه (`INT` بدون UNSIGNED حسب الظاهر) قبل كتابة أي FK عليه بالسكيما النهائية.

### ب.١٠ ✅ محسوم — مواد الخطوط (أزرار، مطاط، إكسسوارات): صرف للخط ثم استهلاك

**القرار:** الإكسسوارات بتُصرف أولاً من المستودع المركزي لمخزون مؤقت عند الخط، وبعدين بتُستهلك بتسجيل التنفيذ.

**التصميم المقترح (لسا توثيق):**

- **مخزون الخط = مستودع من نوع خاص (`production_line`)** مربوط بمحطة العمل. بما إن `raw_material_stock` أصلاً لكل مستودع، ما بنحتاج بنية جديدة للأرصدة: الصرف للخط هو **نقل بين مستودعين** (`transfer_out` من المركزي + `transfer_in` للخط) بسجل `raw_material_movements` (النوعين موجودين بالـenum الحالي).
- الفرق عن قطع الإنتاج: **القطع** (WIP) تبقى دفتر افتراضي بلا مستودعات (ب.٧)؛ **المواد** مخزون حقيقي بكميات وتكلفة، فمنطقي يكون إلها مكان مخزني.
- عمود جديد `production_work_centers_fac.material_warehouse_id INT NULL FK→warehouses`.
- **مستند جديد "صرف مواد للخط":**
  ```
  production_material_issues_fac       (id, issue_no, from_warehouse_id FK, work_center_id FK,
                                        direction ENUM('issue','return'), status ENUM('draft','confirmed','cancelled'),
                                        issued_by FK, issued_at, notes)
  production_material_issue_items_fac  (id, issue_id FK, raw_material_id FK, lot_id NULL FK, quantity DECIMAL(14,3))
  ```
  التأكيد بيكتب حركات النقل وبيحدّث الأرصدة. الإلغاء بيولّد حركة عكسية (لا حذف) — نفس القاعدة الذهبية. `return` لإرجاع الفائض من الخط للمركزي.
- **الاستهلاك بالتنفيذ:** بيُخصم من مستودع محطة العمل المنفّذة (مو المركزي). لو الرصيد غير كافي: يتبع `branches.allow_negative_stock`.
- **المحاسبة:** الصرف للخط بحد ذاته **بلا قيد** (المادة لسا مخزون مواد أولية). القيد `مدين WIP / دائن مخزون المواد الأولية` بيصير **لحظة الاستهلاك** فقط، مثل ما اتفقنا (أ.٥).
- **التكلفة:** بتنتقل مع المادة بنفس `current_cost` للمادة (مو لكل مستودع)، والرولات بتكلفتها الفعلية.

### ب.١١ ✅ محسوم — مرونة المراحل لكل "قصة" (موديل)

"القصة" مصدرها قسم التصميم، ومراحلها بتختلف حسب الموديل. **مغطّى بالتصميم الحالي بدون تعديل بنيوي**، على ٣ مستويات:

1. **مسارات مسمّاة لكل موديل** بنسخ ثابتة (أ.١) — تضيف/تشيل/ترتّب مراحل بنسخة جديدة.
2. **لقطة المسار لكل أمر** قابلة للتعديل الحر بالمسودة (٣).
3. **`Change Routing` موثّق** لأمر قيد التنفيذ (٥.١/٢).
   المراحل نفسها كتالوج مفتوح (ما في مرحلة محفوظة بالكود)، فأي مرحلة جديدة (مكحتة، تطريز، غيرهم) بتنضاف بسطر.

### ب.١٢ ⚠ نقاط مفتوحة جديدة

1. **قسم التصميم:** مين بيعرّف مسار القصة بالنظام؟ التصميم أو الإنتاج؟ (بيحدد الصلاحيات). وهل في مرحلة **عينة (sample)** لازم تُتبَّع قبل اعتماد القصة للإنتاج؟
2. **صرف الخط مجمّع أو لكل أمر؟** اقتراحي مجمّع (مخزون الخط بيخدم كل الأوامر عليه)؛ التخصيص لأمر معيّن يزيد الإدخال.
3. ✅ محسوم (ب.١٩): خطوتين — إرسال ثم استلام بتأكيد الكمية.
4. **صفحة إضافية جديدة:** `material_issues.php` (صرف/إرجاع مواد للخط) — تنضاف لقائمة الصفحات (٤).
5. **القماش والخط:** هل الرولات كمان بتنصرف لمكان القص قبل التنفيذ؟ افتراضياً لا: الرول بيتصرف مباشرة بتنفيذ القص (ب.٤).

## ب.١٣ مسار القصة من التصميم حتى المنتج الجاهز (وصف المستخدم — خطوط عريضة محسومة)

> "المسطرة" = وحدة التصميم/الباترون. "القصة" = الستايل (الموديل) بكل مساطره وتعديلاته.

### التسلسل

1. **التصميم والمساطر:** القسم بيعمل مساطر متنوعة (موديلات بلون أو لونين ومقاس أساسي واحد)، وبيقدر يعدّل على المسطرة أكتر من مرة (تعديلات نهائية ممكن تشمل لون، حركة، جزء جديد، كحت...). كل قصة لها **رقم تتبّع من أول لحظة تصميم**، وبيرافقها لآخر المنتج الجاهز.
2. **الاعتماد:** بعد الموافقة على التعديلات النهائية، المسطرة/التعديل بياخد علامة **"جاهزة للإنتاج"**.
3. **تعريف الإنتاج:** مسؤول بيحدد بناءً على المسطرة المعتمدة: **المراحل** (مع تاريخ/وقت ومدة مخططة لكل مرحلة) + **المواد والإكسسوارات لقطعة واحدة لكل (كروب × مقاس × لون)**.
4. **التنفيذ:** المراحل كحاويات — بأي لحظة بنعرف القصة وأي كروب فيها بأي مرحلة. عند كل مرحلة: مقارنة الداخل بالخارج، التكلفة، المواد/الإكسسوارات الفعلية مقابل المخطَّطة (من التعريف)، والهدر والإصلاح.
5. **الاستلام النهائي:** لما القصة (بكل كروباتها) توصل آخر مرحلة، المسؤول **بيوافق ويؤكّد** النقل النهائي لمستودع المنتجات الجاهزة، وحالتها بتتحول من "قيد التصنيع" لـ"جاهزة للبيع". الكمية بتنضاف لمنتج موجود، أو بتنضاف القصة بكروباتها ومقاساتها وألوانها كمنتج جديد.

### كيانات جديدة (توثيق، لسا مو SQL)

```
production_styles_fac          (id, style_code UNIQUE  -- رقم التتبّع, name, product_id NULL FK,
                                status ENUM('design','approved','in_production','archived'),
                                created_by, created_at)
production_style_revisions_fac (id, style_id FK, revision_no, notes,
                                ready_for_production TINYINT, approved_by NULL, approved_at NULL,
                                created_by, created_at)
production_style_files_fac     (id, revision_id FK, file_path, file_type, uploaded_by)   -- مرفقات (لسا للنقاش)
```

- المسار (`production_routes`) بيرتبط بـ`style_revision_id` بدل الاعتماد على الموديل بس.
- مراحل المسار ولقطة الأمر: عمود `planned_duration_minutes` (للمقارنة مع الوقت الفعلي بتقرير التأخير — معلومة، مو جدولة طاقة).

### تعديلات على قرارات سابقة (⚠ تحتاج تأكيدك)

| القرار السابق                          | الجديد                                                                                            |
| -------------------------------------- | ------------------------------------------------------------------------------------------------- |
| استهلاك غير القماش: رقم واحد لكل موديل | تعريف لكل (كروب × مقاس × لون)، مقترح: **قيمة افتراضية بالموديل + تخصيص فقط عند الاختلاف** (وراثة) |
| القماش: من مخطط القص بس                | + **تقدير للقطعة لكل متغيّر** بتعريف الإنتاج (بيحل بند ب.٦.٣)، والفعلي من المخطط                  |
| إتمام الأمر تلقائي                     | **مستند "استلام منتج جاهز"** مسودة ← تأكيد المسؤول (صلاحية اعتماد)                                |
| المراحل بدون وقت                       | مدة مخططة لكل مرحلة (معلومة/تنبيه تأخير)                                                          |

### ب.١٤ نقاط لسا مفتوحة

1. ✅ محسوم (ب.١٥): القصة بتنربط بمنتج الكتالوج **وقت اعتماد المسطرة للإنتاج**.
2. ✅ محسوم (ب.١٥): الاستلام النهائي **جزئي ممكن** (كروب/مقاس جاهز ينتقل والباقي لسا).
3. ✅ محسوم (ب.١٦): التكلفة تراكمية بعد كل مرحلة.
4. ✅ محسوم (ب.١٧): تجميد المسطرة عند الاعتماد.
5. ✅ محسوم (ب.١٨): نعم، مرفقات (باترون + حتى ٥ صور مضغوطة).

### ب.١٥ ✅ قرارات مثبّتة (جلسة تعريف المسار من التصميم)

| القرار                    | التفاصيل                                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **مواد القطعة الواحدة**   | قيمة افتراضية بالموديل (لكل قطعة)، **وتخصيص فقط لكل مقاس/لون مختلف** (وراثة). سطر بلا `variant_id` = افتراضي لكل المتغيّرات، وسطر بـ`variant_id` = تخصيص بيتغلّب عليه                |
| **الاستلام النهائي جزئي** | كل مقاس/كروب جاهز بآخر مرحلة ممكن ينتقل لمستودع الجاهز، والباقي لسا قيد التصنيع. الأمر يكتمل لما كل الكميات المخطَّطة تُستلم أو تُغلق بقرار مصير (بند ٥.١)                           |
| **القصة ومنتج الكتالوج**  | لحظة اعتماد المسطرة للإنتاج القصة بتنربط بمنتج بالكتالوج (موجود أو يُنشأ عبر شاشات المنتجات الحالية). بهيك متغيّراته (مقاس × لون) بتكون موجودة قبل أي أمر إنتاج، و`variant_id` مضمون |

### مستند جديد: استلام منتج جاهز (Finished Goods Receipt)

```
production_fg_receipts_fac        (id, receipt_no, order_id FK, warehouse_id FK  -- مستودع المنتجات الجاهزة,
                                   status ENUM('draft','confirmed','cancelled'),
                                   received_by FK, received_at, confirmed_by NULL, confirmed_at NULL, notes)
production_fg_receipt_lines_fac   (id, receipt_id FK, variant_id FK, quantity DECIMAL(14,3),
                                   unit_cost DECIMAL(14,4)  -- لقطة وقت التأكيد)
```

**التأكيد بيعمل:** (١) مدين "مخزون المنتج الجاهز" / دائن WIP بقيمة القطع المستلمة، (٢) زيادة `warehouse_items` لكل متغيّر (`current_cost` حسب `branches.costing_method`)، (٣) حركة `inventory_movements` (`in`, `reference_type='production'`) لكل متغيّر، (٤) تنقيص دفتر الكمية الحي من آخر مرحلة. الإلغاء بحركة عكسية. تحتاج **صلاحية اعتماد**.

### ⚠ مقترح جديد (يحتاج موافقتك): تتبّع قيمة WIP داخل الدفتر

الاستلام الجزئي بيفرض سؤال: **شو تكلفة القطع يلي انستلمت هلق؟** الدفتر الحالي (كمية فقط) ما بيجاوب، لأنه كروبات مختلفة بمراحل مختلفة بتكون تكلفتها متراكمة بأرقام مختلفة.

- إضافة عمود `wip_value DECIMAL(14,4)` لدفتر الكمية الحي (✅ الاسم الصريح النهائي — راجع ب.٢٣.١، كان مؤقتاً `value`) `production_order_stage_qty_fac` (قيمة التكلفة المتراكمة بهاي الخانة: أمر × مرحلة × محطة × متغيّر).
- **النقلة** بتحرّك قيمة بنسبة الكمية (متوسط الخانة)، وتنضاف عليها تكلفة التنفيذ الجديدة (مواد + عمالة + تكلفة غير مباشرة). **الـScrap** بيشيل حصته من القيمة.
- **الاستلام** بيقرأ تكلفة القطعة = `wip_value ÷ quantity` للخانة الأخيرة، لكل متغيّر.
- **يحل بند ب.٨ (التكلفة لكل مقاس):** كلفة قماش القص بتتوزّع على المتغيّرات بحسب `الاستهلاك المقدَّر للقطعة لكل متغيّر × عدد القطع المقصوصة` (استهلاك مخطَّط عندنا هلق بتعريف الإنتاج)، وباقي المراحل بالتساوي لكل قطعة.

## ب.١٦ ✅ محسوم — التكلفة تراكمية بعد كل مرحلة (مو نهائية فقط)

**ليست مسألة تفضيل — هي نتيجة حتمية لقرار الاستلام الجزئي (ب.١٥).** لو التكلفة
تُحسب نهائياً بس بعد كل التعديل وإعادة التصليح، ما رح نقدر نعرف قيمة كروب
يوصل آخر مرحلة ويُستلم بينما باقي الكروبات لسا بالمنتصف. عمود `value`
المقترح بدفتر الكمية الحي (ب.١٥) هو بالضبط هالآلية: كل مرحلة (وكل جولة
Rework) بتزيد القيمة، والاستلام بياخد القيمة المتراكمة لحظتها. **لا تصميم
إضافي مطلوب هون** — القرار بس يثبّت الآلية الموجودة أصلاً.

## ب.١٩ ⚠ مُستبدَلة بـب.٢١ — النقلة بين المراحل بخطوتين (إرسال ثم استلام)

> **استُبدلت بدورة اقتراح/قبول/تنفيذ/إنهاء/اعتماد الأغنى (ب.٢١) بعد جلسة تصميم الصلاحيات.** الآلية تحت باقية بالتوثيق للسياق التاريخي بس، لا تُبنى.

**قراري:** خطوتين هو الأصح لأرضية مصنع فعلية — العدد يلي بيتبعت مش
دايماً نفس العدد يلي بيوصل (قطع ضايعة، عدّ غلط، نسيان). خطوة وحدة
بتفترض دقة مثالية مو واقعية.

**التصميم:** `production_stage_executions_fac` (أ.٣) بينقسم لكيانين:

```
production_stage_transfers_fac
  id · order_id FK · variant_id FK
  · from_stage_id FK NULL · from_work_center_id FK NULL   (NULL = بداية الأمر)
  · to_stage_id FK · to_work_center_id FK
  · sent_qty DECIMAL(14,3) · sent_by FK · sent_at
  · status ENUM('pending','received')
  · received_qty DECIMAL(14,3) NULL · discrepancy_qty DECIMAL(14,3) NULL
  · discrepancy_notes VARCHAR(255) NULL · received_by FK NULL · received_at NULL
```

- **الإرسال:** بينقص الكمية من دفتر المصدر فوراً (القطعة فعلياً غادرت). الكمية **ما بتنحط** بدفتر الوجهة لسا — هي "بالطريق"، بلا مكان بالدفتر، مطابق للواقع الفعلي.
- **الاستلام:** الشاشة بتعرض `sent_qty` معبّاة افتراضياً بخانة الكمية المستلمة (قبول بضغطة وحدة بالحالة العادية)، وبتعدّلها بس لو في فرق فعلي. `discrepancy_qty` بيتسجّل تلقائياً للتقارير.
- **`production_stage_executions_fac` القديمة تصير مرتبطة بالاستلام**: عند تأكيد الاستلام، `input_qty` = `received_qty`، وبعدها نفس منطق الجودة والتكلفة (أ.٣) يشتغل عادي.
- **المقاول الخارجي:** "الإرسال" له = نقلة عادية لمحطة عمل خارجية. "الاستلام منه" = نفس الشاشة، وبيكتشف تلقائياً أي نقص (قطع ضاعت عند المقاول).

## ب.٢١ ✅ محسوم — دورة العمل الكاملة بين الأقسام لكل مرحلة (تستبدل ب.١٩)

> جلسة تصميم الصلاحيات كشفت إن النقلة الفعلية أغنى من إرسال/استلام بسيط:
> فيها تفاوض **قبل** البدء (قبول/رفض/تعديل)، وفيها اعتماد فعلي **بعد**
> الانتهاء (مو شكلي). الدورة بتتكرر **لكل مرحلة على حدة**، وما تبلش
> مرحلة N+1 إلا بعد ما اعتماد مرحلة N يخلص.

### الدورة (مؤكَّدة من المستخدم)

```
رئيس الإنتاج: اقتراح أمر مرحلة (محطة عمل + كمية لكل مقاس)
        ↓
رئيس القسم المستلم: قرار
   ├── رفض نهائي  → يتوقف. ما في إعادة تلقائية — رئيس الإنتاج لازم
   │                 يقترح من جديد (أمر جديد، حتى لو بنفس محطة العمل
   │                 أو بمحطة تانية) — بس بعد ما يشوف الرفض
   ├── طلب تعديل  → نقاش خارج النظام (ملاحظات)، ثم رئيس الإنتاج يرسل
   │                 اقتراح جديد يشاور على المرفوض
   └── قبول       → ↓
التنفيذ الفعلي (جودة + مواد فعلية + تكلفة)
        ↓
طلب إنهاء المرحلة (من القسم المنفّذ)
        ↓
رئيس الإنتاج: مراجعة فعلية (مو شكلية)
   ├── رفض  → يرجع للقسم المنفّذ يصحّح، ويعيد طلب الإنهاء (محاولة جديدة،
   │           مو تعديل على نفس المحاولة — كل محاولة سجل مستقل)
   └── اعتماد → المرحلة التالية تصير قابلة للاقتراح (تكرار الدورة)
```

### السكيما (تستبدل جدول `production_stage_transfers_fac` بب.١٩)

```
production_stage_work_orders_fac
  id · order_id FK · stage_id FK · sequence_order
  · assigned_work_center_id FK      (داخلي/خارجي — رئيس الإنتاج يحدده وقت الاقتراح)
  · status ENUM('proposed','accepted','rejected','revision_requested','completed','cancelled')
  · proposed_by FK · proposed_at · proposal_notes VARCHAR(500) NULL
  · supersedes_work_order_id INT NULL FK  (ذاتي المرجع — الاقتراح الجديد بعد رفض/تعديل)
  · responded_by FK NULL · responded_at NULL · response_notes VARCHAR(500) NULL

production_stage_work_order_lines_fac
  id · work_order_id FK · variant_id FK · requested_qty DECIMAL(14,3)

production_stage_completions_fac        -- محاولة إنجاز واحدة (كذا محاولة ممكنة لنفس أمر المرحلة لو انرفضت أولى)
  id · work_order_id FK
  · status ENUM('pending_verification','verified','rejected')
  · supersedes_completion_id INT NULL FK  (محاولة إنهاء جديدة بعد رفض التحقق)
  · completed_by FK · completed_at · completion_notes VARCHAR(500) NULL
  · verified_by FK NULL · verified_at NULL · verification_notes VARCHAR(500) NULL
```

**الربط مع الجداول الموجودة (الملحق أ):**

- `production_stage_executions_fac` يُضاف لها `completion_id INT FK` (بدل الارتباط المباشر بأمر/مرحلة) — التنفيذ الفعلي (جودة، مواد، تكلفة) بيصير **جوا** نافذة "قيد التنفيذ" بين القبول وطلب الإنهاء.
- `production_order_stage_qty_fac` (دفتر الكمية الحي) بيتحدّث **لحظة `verified`** بس — قبلها الكمية "معلَّقة" بحالة الأمر، مو موزّعة على مرحلتين بنفس الوقت.
- **آخر مرحلة بالمسار:** اعتمادها بيولّد مستند "استلام منتج جاهز" (ب.١٥) تلقائياً بدل الانتقال لأمر مرحلة تالي.
- `production_order_routing_changes_fac` (٥.١) يضل موجود لتوثيق **سبب** إضافة/حذف مرحلة كاملة من المسار، منفصل عن دورة التفاوض العادية لكل مرحلة موجودة أصلاً.

### تركيب القماش (من نقاش اليوم)

```
raw_materials_fac  + grammage DECIMAL(8,2) NULL   (غرام/م²)
raw_material_compositions_fac  (id, raw_material_id FK, component_name VARCHAR(50), percentage DECIMAL(5,2))
    -- قطن ٦٠٪ / بوليستر ٣٥٪ / ليكرا ٥٪ ...، مجموعها لازم = ١٠٠ (تحقق بالتطبيق)
```

يُدخلها **مسؤول مستودع المواد الأولية**، مو المصمم — المصمم بس بيختار من الكتالوج الموجود (يتماشى مع كل تصميمنا السابق: القماش مادة أولية حقيقية بخصائصها، مو حقل حر بالمسطرة).

### ⚠ نقاط لسا مفتوحة

1. **دور "رئيس القسم المستلم":** هل هو شخص واحد ثابت لكل مرحلة (مثلاً "رئيس قسم التفصيل")، أو ممكن يكون أكتر من شخص مخوَّل بنفس المرحلة (فأي واحد فيهم يقدر يوافق)؟ بيأثر مباشرة على تصميم الصلاحيات الجاي.
2. **الإشعارات:** "بيظهر عنده إشعار" — نظام إشعارات داخل النظام موجود أصلاً بالمشروع، أو هاي أول استخدام له؟
3. **رفض التحقق النهائي المتكرر:** لو رفض رئيس الإنتاج نفس المرحلة كذا مرة، في حد أقصى محاولات أو تصعيد؟ (افتراضياً: لا حد، فقط سجل تاريخي بكل محاولة).

## ب.٢٣ ✅ التثبيتات الخمسة النهائية قبل الانتقال لـSchema فعلي

> جلسة مراجعة معمارية أخيرة كشفت ٥ فجوات حقيقية قبل التنفيذ. **بعد هالبند
> المخطط مكتمل رسمياً — أي إضافة جديدة (MRP، تخطيط طاقة، جدولة متقدمة)
> تُبنى لاحقاً فوق هالأساس، مو الآن.**

### ب.٢٣.١ قيمة WIP: تسمية صريحة + معالجة الهدر الطبيعي مقابل غير الطبيعي

- **تسمية:** عمود `value` بدفتر الكمية الحي (ب.١٥) يتسمّى **`wip_value`** صراحة — لا غموض مستقبلي.
- **Scrap طبيعي مقابل غير طبيعي — أثر محاسبي مختلف تماماً:**

  ```
  production_quality_results_fac  + scrap_type ENUM('normal','abnormal') NULL   (إلزامي لو disposition='scrap')
  ```

  - **طبيعي** (هدر قص متوقَّع ضمن `waste_pct` المخطَّط بالمرحلة/المسار): **لا قيد خسارة، ولا سحب من `wip_value`.** الكمية تنتقص من `quantity` بالدفتر بس — نفس القيمة الإجمالية تضل موزّعة على كمية أقل، فترتفع التكلفة الفعلية للقطعة السليمة تلقائياً (امتصاص طبيعي، مطابق لمبدأ محاسبة التكاليف القياسي).
  - **غير طبيعي** (تلف، خطأ، تجاوز نسبة الهدر المخطَّطة): **قيد خسارة فعلي** (كما صمّمنا بأ.٥) + سحب نصيبها من `wip_value` فعلياً.
  - **الاقتراح الافتراضي بالواجهة:** النظام يقترح `normal` تلقائياً لو نسبة الهدر التراكمية بالأمر/المرحلة لسا ضمن `waste_pct`، و`abnormal` لو تجاوزتها — **قابل للتعديل اليدوي دائماً** (قرار بشري نهائي، يحتاج صلاحية `production.board.scrap`).

- **توضيح مهم — Rework ليس دائماً بلا تكلفة:** `is_free_of_charge` (ب.٢) **بيتحكم فقط بدفع المقاول الخارجي**، مو بوجود التكلفة من أساسها. أي تنفيذ لاحق (تمرير ثاني للمرحلة بعد Rework) بيولّد تكلفته الطبيعية (مواد/عمالة/تكلفة غير مباشرة) بنفس آلية أي تنفيذ عادي — **بشكل تلقائي، بدون حاجة لتصميم إضافي.** الفرق الوحيد: لو `is_free_of_charge=true`، القيد الدائن للتنفيذ الثاني ما بيروح لحساب المقاول (لأنه هو المسؤول عن غلطته)، وبيروح بدله لحساب "تكلفة إعادة تصنيع داخلية" أو ببساطة ما بيتسجل تعويض خارجي إطلاقاً حسب سياسة الفرع.

### ب.٢٣.٢ توزيع تكلفة القماش الفعلية على المقاسات (مفتاح توزيع، مو حساب مستقل)

**المبدأ:** الاستهلاك المخطَّط **مفتاح توزيع نسبي**، والفعلي يبقى مصدر القيمة الإجمالية الحقيقية. **ممنوع** حساب تكلفة أي متغيّر بضرب استهلاكه المخطَّط بسعر الوحدة مباشرة (هيك بيعطي مجموع مختلف عن التكلفة الفعلية الحقيقية).

**المعادلة:**

```
لكل متغيّر بمخطط القص:
  وزن التوزيع[متغيّر] = الاستهلاك المخطَّط للقطعة[متغيّر] × عدد القطع المقصوصة[متغيّر]
  إجمالي الأوزان = Σ وزن التوزيع لكل المتغيّرات بنفس المخطط
  نصيب المتغيّر من التكلفة الفعلية = (وزن التوزيع[متغيّر] ÷ إجمالي الأوزان) × التكلفة الفعلية الكلية للمخطط
```

مثال مطابق لمثالك: مخطط استهلك ١١٥٠م فعلياً بسعر ٥$/م = ٥٧٥٠$ تكلفة فعلية كلية. هاي الـ٥٧٥٠$ (مو رقم آخر) بتتوزّع على المتغيّرات حسب أوزانهم النسبية.

**جدول جديد (توثيق سبب كل توزيع — لا حساب صامت):**

```
production_cost_allocations_fac
  id · execution_id FK · variant_id FK
  · allocation_weight DECIMAL(14,4)   -- وزن التوزيع لهالمتغيّر
  · allocated_cost DECIMAL(14,4)      -- نصيبه الفعلي من التكلفة الكلية
```

**تأكيد مبدأ منفصل (تمّ الحفاظ عليه أصلاً):** `raw_material_stock`/مخزون الخط يعرف **أين** المادة (كمية إجمالية بالمستودع)، بينما `production_stage_execution_materials_fac` يعرف **لأي أمر إنتاج** استُهلكت. لا يوجد خلط — عشرة آلاف زر بمستودع الخط ممكن تخدم ٣ أوامر خياطة متزامنة، والتوزيع بينهم موثَّق بالكامل عبر جدول الاستهلاك، مو باستنتاج من رصيد المستودع.

### ب.٢٣.٣ العلاقة الدقيقة بين Good / Rework / Scrap / Remaining

**على مستوى التنفيذ الواحد** (معادلة تحقّق إلزامية):

```
production_stage_executions_fac  + scrap_qty DECIMAL(14,3) DEFAULT 0   (عمود صريح، كان ناقص)

input_qty = good_qty + rework_qty + scrap_qty
```

- `rework_qty` مفصَّل بصفوف `production_quality_results_fac` (disposition='rework')، ومجموعها لازم = `rework_qty`.
- `scrap_qty` مفصَّل بصفوف نفس الجدول (disposition='scrap')، ومجموعها لازم = `scrap_qty`.
- `disposition='accept'` **لا يخصم من good_qty** — هو مجرد ملاحظة جودة على جزء من الكمية المحتسبة أصلاً ضمن `good_qty` (بلا معادلة كمية منفصلة).

**على مستوى الأمر ككل** (تحدّد حالة الاكتمال، مش آخر مرحلة بس):

```
remaining_qty[أمر, متغيّر] = ordered_qty[متغيّر]
                            − Σ fg_receipt_lines.quantity[متغيّر]         (استُلم فعلياً)
                            − Σ quality_results.quantity[متغيّر, scrap]   (هلك نهائياً)
                            − Σ dispositions.quantity[متغيّر, move_wip]   (انتقل لأمر تاني)
```

**الأمر ما يصير `completed` إلا لو `remaining_qty = 0` لكل المتغيّرات بدون استثناء.**

**حالة جديدة بالآلة (بدل `in_production` غامضة أثناء الاستلام الجزئي):**

```
production_orders_fac.status ENUM('draft','released','in_production','partially_completed','completed','cancelled')
```

`in_production` = لا استلام بعد. `partially_completed` = في استلام جزئي و`remaining_qty` > صفر لبعض المتغيّرات. `completed` = محسوبة تلقائياً (فحص بعد كل تأكيد استلام/ديسبوزيشن)، مو حالة تُختار يدوياً.

### ب.٢٣.٤ حالة ترحيل محاسبي منفصلة عن الحالة التشغيلية + منع الترحيل المزدوج

**مبدأ:** حالة الأمر التشغيلية (Draft/Released/...) **لا تضمن** إن كل قيوده اتسجّلت. كل جدول بيولّد قيد محاسبي أو حركة مخزون يحتاج عمودين إضافيين:

```
+ posting_status ENUM('unposted','posted','reversed') DEFAULT 'unposted'
+ posting_reference VARCHAR(64) NULL   -- معرّف فريد للقيد المُنشأ، يمنع التكرار
```

**يُطبَّق على:** `production_stage_execution_materials_fac`، `production_quality_results_fac` (Scrap)، `production_stage_completions_fac` (عمالة/تكلفة غير مباشرة)، `production_fg_receipts_fac`، `production_order_dispositions_fac`.

**آلية منع الترحيل المزدوج (Idempotency):** أي إجراء "تأكيد" (زر Confirm بأي شاشة) لازم **أول خطوة** يتحقق `posting_status != 'posted'` **جوا نفس المعاملة (transaction)** قبل ما يبني القيد — لو ضغط المستخدم Confirm مرتين (دبل كليك أو تحديث صفحة)، المحاولة الثانية ما بتعمل شي (أو بترجع نفس المرجع الموجود). هاد نمط دفاعي إلزامي بكل شاشات القسم، مو استثناء.

### ب.٢٣.٥ سجل تدقيق موحَّد (إضافة، مو بديل)

```
production_audit_log_fac
  id · entity_type VARCHAR(50)   -- 'order','stage_work_order','completion','quality_result',...
  · entity_id INT
  · action VARCHAR(50)           -- 'status_change','created','rejected',...
  · old_status VARCHAR(50) NULL · new_status VARCHAR(50) NULL
  · user_id FK · created_at TIMESTAMP · notes VARCHAR(500) NULL
```

**ما بيلغي** أي جدول تفصيلي موجود (`production_order_routing_changes`، `production_stage_completions`، إلخ) — هدفه سؤال واحد بسيط بسرعة: _"مين غيّر شو، وإمتى؟"_ بدون UNION على عشر جداول. كل جدول تفصيلي بيكتب سطر هون كمان لحظة أي تغيير حالة. ⚠ ملاحظة حجم: هالجدول بينمو بسرعة (سطر لكل حدث بكل مكان بالقسم) — فهرسة `(entity_type, entity_id)` إلزامية من أول يوم.
